# T2.8a: Local garage and Ultium model-year picker

## Goal

Add an Android garage to the existing mobile app. A person can pick a sourced Ultium-family make, model, and model year, add multiple vehicles tagged `mine` or `checked`, change that tag, remove an entry, and see those choices after restarting the app. The 2024 Chevrolet Equinox EV is labeled `verified` because a same-model-year recording exists; every other catalog entry is labeled `beta` and clearly says that battery signals are unavailable pending profile and live-car checks. An unsupported make/model/year goes to a local interest form whose saved fields and beta-interest choice can be reopened. This is an executable, bounded first part of PLAN T2.8, not closure of all T2.8 acceptance gates.

## Non-goals

- No new OBD command, PID, DID, CAN header, scaling, vehicle profile, signal importer, battery data, first-connect match algorithm, or verified promotion without a same-model-year recording. Do not infer module behavior from another model year. The existing console/capture remains a 2024 Equinox-only debug path and must never write that car ID for a selected beta entry.
- No backend, account, delivered beta registration, email, analytics, export, cloud sync, report, charge log, or scan ownership migration. Those data producers and APIs are not present in mobile yet. A saved local interest choice must say that no request was sent.
- No VIN collection in this flow. The existing app must not transmit or export garage data. No Tesla, generic ICE, hybrid, or PHEV catalog entry. No edit to `packages/obd-core`, `tools/relay`, `tools/hil-bridge`, recordings, setup, lockfile, `app.json`, or `eas.json`.

## Interfaces

The mobile-owned catalog and flow use named exports; exact UI component structure is implementer choice. This public seam is exercised by Vitest without loading React Native or Expo native modules:

```ts
type Tier = "verified" | "beta";
type Ownership = "mine" | "checked";
type CatalogVehicle = {
  id: string; make: string; model: string; year: number; tier: Tier;
  recording?: string; // only 2024 Equinox
};
type GarageVehicle = { id: string; catalogId: string; ownership: Ownership; nickname?: string };
type Interest = { make: string; model: string; year: number; joinBeta: boolean };
type GarageState = { version: 1; nextId: number; vehicles: GarageVehicle[]; interests: Interest[] };
interface TextStore { read(): Promise<string | undefined>; write(text: string): Promise<void> }
export function createGarageFlow(store: TextStore): {
  load(): Promise<GarageState>;
  add(catalogId: string, ownership: Ownership, nickname?: string): Promise<GarageState>;
  changeOwnership(id: string, ownership: Ownership): Promise<GarageState>;
  remove(id: string): Promise<GarageState>;
  saveInterest(interest: Interest): Promise<GarageState>;
};
export const SUPPORTED_VEHICLES: readonly CatalogVehicle[];
```

`createGarageFlow` is the one mutation path for the UI and test. It validates both loaded JSON and each change; rejects unknown catalog IDs, invalid ownership, empty make/model, and implausible/non-integer year rather than storing them. A missing file yields an empty version-1 state. Malformed or future-version data yields a visible load error and must not be overwritten by an empty state. Mutations are serialized, update the in-memory state only after a successful write, and show storage errors in the UI. IDs are local and stable; duplicate vehicles of one model-year are allowed because a buyer may check several cars. The catalog tier comes from the catalog, never from saved JSON, and changes only after recorded evidence. `Paths.document` is used for a private `garage.json` file; no VIN field is present. Keep the existing Equinox console/capture path available only when the active garage selection is 2024 Equinox, or clearly separate it as an Equinox-only debug console. Selecting a beta entry cannot initiate that Equinox-labeled recording or show battery data.

The production app must derive picker/garage availability text, evidence text, and console permission from exported presentation/action values that `App.tsx` actually consumes. A verified picker detail shows the exact `recording` path on screen; do not substitute a generic “recorded session” claim. A beta selection has no enabled route to the Equinox console, and the `startRecording`/capture handler also checks the same production action permission before it can write hard-coded Equinox metadata. Keep the generic debug console clearly labeled Equinox-only. Define the saved-interest notice once in production code and render that exact value after saving; a test-local copy is not verification.

`garageDocumentStore.write` must create and write a temporary file in `Paths.document` (for example `garage.pending.json`) before touching `garage.json`. On success, move the completed temp file onto `garage.json` with `{ overwrite: true }`; on first write, move creates the destination only after the temp write succeeded. On retry, clear a stale temp file before creating the new one; a cleanup failure is reported and leaves the destination untouched. On temp create/write failure, report the original error, optionally clean the temp, and leave the destination absent (first save) or at its previous value (later saves). Never create `garage.json` before writing it. The installed Expo SDK 57 API exposes `File.move(destination, options?: RelocationOptions)` and `RelocationOptions.overwrite?: boolean` in `apps/mobile/node_modules/expo-file-system/src/internal/NativeFileSystem.types.ts` and `src/File.types.ts`. This sequence protects the first-write path and pre-move failures; the API does **not** promise an atomic replacement if the move itself fails or the process is killed. Keep visible load/write errors and do not claim crash-safe transactions.

The UI must expose: garage list with model/year/tier/ownership; Add vehicle picker by make, model, year; verified/beta explanation before Add; ownership choice; change ownership and remove; unsupported vehicle interest form with make/model/year and `joinBeta`; saved-interest reopening; a visible `Saved on this phone; no request sent` message. On app launch load before enabling mutations; a failed load shows an error/retry path. The UI may be a single screen within `App.tsx` with simple conditional views; no navigation dependency.

### Storage adapter failure modes recorded before repair

1. First save: destination is created before its content write, then that write fails; a later load sees an empty malformed `garage.json`. Required behavior: destination remains absent until a complete temp file is moved into place.
2. Later save: temp create/write fails; the previous valid `garage.json` must remain readable and the app must show an error, not publish the new in-memory state.
3. Stale temp cleanup fails; the destination must remain untouched and the error must be surfaced rather than silently replacing the old state.
4. Temp-to-destination move/overwrite fails or is interrupted; surface the error and never claim an atomic rollback or a successful save without observing native behavior.
5. Existing destination cannot be read or contains invalid/future JSON; surface the load error and do not reset it to an empty garage.

No isolated native-adapter Vitest test is requested: loading `expo-file-system` in Node would require mocking the native `File` operations whose behavior is at issue, and such a test would only mirror the specified call order. The implementer and reviewer must inspect the adapter's actual order against failures 1–3 and retain the existing flow write-error test for the public flow. The on-phone run below checks real document persistence. Native write/move failure behavior remains a phone-only residual until a reproducible device fault can be exercised; report that limit honestly.

## Risks / open questions

- Catalog `beta` means eligible for a garage entry and future profile work; it does **not** mean a known battery signal or compatible first-connect handshake. All battery data stays unavailable until sourced checks exist. This distinction must be obvious in the picker and garage.
- A local-only interest form cannot deliver a beta request. No recipient, backend, or intake path is authorized here. If delivered registration is required, obtain a destination and consent design in a later spec; do not imply signup succeeded.
- Temp-file staging protects the empty-destination first-write failure and preserves an existing destination when temp preparation fails. Expo's move API does not document atomic replacement or rollback on interrupted move; native persistence must be observed on a phone. Backup/recovery or migration beyond schema version 1 requires a later spec if this risk materializes.
- Year-list sources establish that a vehicle was offered, not what its BECM or other module answers. Never promote or show battery data from a year range extrapolation.

## Decisions

- Parent instruction for this architecture pass: Ultium family entries are garage-addable as clearly labeled `beta`; garage membership and battery-access authorization are distinct. Only 2024 Equinox is `verified` today.
- Local interest persistence is the implementable interpretation under the no-backend/no-destination scope; the UI states that no request was sent. Parent owns any later user decision about delivered registration.
- Existing EAS development client `0f877dca` must remain valid; this spec adds no native module or dependency.
