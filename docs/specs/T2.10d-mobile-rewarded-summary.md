# T2.10d: Opt-in phone summary and rewarded-ad flow

Order: after T2.10a–c, the parent's PLAN/ADR amendments, and release of any T2.9-owned root/mobile files. T2.10 is not complete until its mandatory live model and SSV gates have evidence; a development build alone is insufficient.

## Goal

From a saved battery diagnosis report, the Android user can read the offline template at any time, opt in to a clearly described DeepSeek summary, choose a rewarded ad for one bounded summary use, wait for a verified server credit, and view only an output that passes the local deterministic number/citation check. Failed/no-fill/cancelled ads, offline state, exhausted caps, provider failures and invalid output leave the template visible with an honest reason.

## Non-goals

- No subscription, billing, credit packs, automatic ad display, key entry, report export, assistant chat, or car command.
- No use of beta-upload consent as LLM consent; this is a separate opt-in decision.
- No promise that ad revenue covers model cost or that a future subscription is profitable.

## Interfaces

```ts
// pure app flow, injected adapters; no Expo import
export interface SummaryAccess {
  challenge(): Promise<{ ssvCustomData: string; expiresAt: string }>;
  balance(): Promise<number>;
  summarize(requestId: string, request: SummaryRequest): Promise<unknown>;
}
export interface RewardedAdPort {
  load(customData: string): Promise<"ready" | "no-fill">;
  show(): Promise<"earned-client-callback" | "closed" | "failed">;
}
export function createSummaryFlow(access: SummaryAccess, ads: RewardedAdPort): {
  summaryFor(report: BatteryDiagnosisReport, consent: boolean): Promise<SummaryView>;
  earnUse(): Promise<"credited" | "pending" | "unavailable">;
};
```

The screen asks separately for permission to transmit the **minimized VIN-free report facts** to DeepSeek, clearly naming DeepSeek and its People's Republic of China processing/storage before the first call. A user can decline or withdraw; no request is sent until explicit opt-in. Persist this separate consent version in private app storage; withdrawal stops future transmissions. The UI discloses the ad reward before show, uses a button the user taps for each ad, and never forces an ad to see the offline template. Ad SDK initializes only after applicable ad-consent handling. Server SSV, not `EARNED_REWARD`, supplies the credit. The phone polls only briefly; delayed SSV leaves a pending state and can be checked again later. The server returns one summary or a fallback reason. The phone always rechecks against its own typed report before display and never puts the provider key or credit authority in the APK. Do not send raw recording, garage ID, timestamp, VIN, notes, codes beyond the minimized projection, or beta upload token. Save the anonymous install secret in `expo-secure-store`; request IDs are persisted in private app storage until resolution to avoid double calls on retry. Ad no-fill and no network show the template and a retry option; no paywall on deterministic data.

New external dependencies: `react-native-google-mobile-ads`, required to load Android rewarded ads and pass `serverSideVerificationOptions.customData`; and `expo-secure-store`, required to protect the anonymous backend install credential on the device. Select current Expo-compatible **exact pinned versions before implementation** and record them in the dependency diff. ## Risks / open questions

- Largest risk: SSV timing and ad no-fill make a free summary unavailable even when the user opts in. The template must remain complete and usable throughout.
- Google ad revenue varies by audience, geography, fill and season. At the illustrative 3,000 input + 300 output tokens and current DeepSeek peak cache-miss rates, one call is about **US$0.00126**; break-even would be about **US$1.26 eCPM** for one paid impression per call before hosting, taxes, unfilled ads and invalid traffic. These are arithmetic hypotheses, not measured revenue or acceptance criteria. Measure real provider usage and AdMob earnings before choosing a production cap or a future subscription.
- A possible subscription with a recurring monthly use allotment is **future Phase 3 work**. It needs recurring value, Play Billing, entitlement and refund rules, and measured costs; no subscription path is implemented here. [Google Play subscription policy](https://support.google.com/googleplay/android-developer/answer/9900533).
- Native module/Expo compatibility and Google consent requirements must be checked against the exact versions and launch regions before installation. T2.9's mobile/root edits must be released before this stage touches shared files.

## Decisions

- Owner, 2026-09-26: no BYOK; DeepSeek real-report transmission only after clear opt-in with minimized VIN-free data; optional rewarded ad for one bounded summary use; US$5 total **live evaluation** cap, not a production budget. Subscription is a later possibility, not part of T2.10.
- Parent owns PLAN/ADR edits, production cap and launch region/consent decisions; the implementer does not infer them.
