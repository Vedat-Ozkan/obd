# T2.11b: Assistant turns on the local summary Worker, and a four-arm paid live eval

Order: after [T2.11a](T2.11a-assistant-tools-replay.md) (closed) and [X-2026-09-29-summary-reservation](X-2026-09-29-summary-reservation.md) (`reservationFor`, in progress) are reviewed. **Stage 1** (software, offline, one implementer session, files 1–6) can start then. **Stage 1b** (offline, small: returned-provider recording, the CLI label rule and two cleanups in files 1, 3, 4 and 5) follows Stage 1's review and is approved before Stage 2. **Stage 2** (the paid comparison run, then recorded replies and their CI replay, files 7–12) is a separate session. It runs only after T2.10's paid phone check (Decision 9) and the owner's answers under Risks. It needs no car. The phone chat is [T2.11c](T2.11c-phone-assistant-chat.md).

## Goal

The local development summary Worker (T2.10c C1) gains `POST /v1/assistant/turns`. One authenticated, consented turn makes at most one bounded OpenRouter call to one of four pinned arms (table below): C1's `deepseek/deepseek-v4.1-flash` and three comparison models, each pinned to one host.

Every arm uses the same system prompt (`assistantInstructions` plus one adapter preamble), the same JSON-mode request with `assistantReplySchema` enforced on the server, the same checker, `max_tokens` 1,024, reasoning off, and no retries or fallback routing.

Summaries and assistant turns draw on **one** budget: the T2.10 key, its US$1 cap and the existing D1 ledger. Each call reserves `reservationFor` its own request body.

An eval CLI runs the frozen T2.11a question set once per arm and writes a comparison of:
- number-check pass rate;
- citation resolution and correctness;
- the injection result;
- cost and latency per answer, against the owner's targets (about US$0.01 per cheap answer, about US$0.05 per thorough one).

Test-visible outcome: a dry run of all four arms against the harness with synthetic upstream replies (`/tmp/t2.11b-eval-dry.json`). After owner authorization: `/tmp/t2.11b-live-eval.json`, plus one reviewed recorded-reply file per arm that CI replays.

## Non-goals

- No arms beyond the four above. One run per arm, no repeats, no LLM judge, and no prompt, schema or question changes after seeing live rows (hard rule 11; BM5 owns the judge).
- Reasoning is never enabled for any arm, and no arm is swapped to another host or model mid-run.
- No native function calling, BYOK, deployment, rewarded-ad credit or production route (C2/T2.10b).
- No server-side tool execution. The Worker holds no user data and never runs tools.
- No notes in the assistant (Decision 4). Recording notes and names stay unread, as in T2.11a.
- No phone UI, chat history or multi-turn context (T2.11c).
- No separate assistant budget, key, D1 tables or use cap (Decisions 1–2).
- No change to the summary body, prompt, schema, consent or phone code.

`FlatAssistantReply` is T2.11a's flat `{version, kind, tool, sessionId, claims}` shape.

**Outgoing body.** It is identical for every arm except `model` and `provider: { order: [tag], only: [tag], allow_fallbacks: false, require_parameters: true }`. Every other field is shared: `stream: false`, `max_tokens: 1024`, `reasoning: { enabled: false }`, `response_format: {type: "json_object"}` (the server parser and checker enforce `assistantReplySchema`), a system message (the `t2.11-openrouter-v1` preamble plus `assistantInstructions`), and a user message holding the serialized turn. There are no `plugins`, `web_search_options`, `tools` or `:online` suffix. A private `complete()` is extracted and shared with C1. The C1 summary body differs only in its adapter prompt (`t2.10-openrouter-v2`) and in sending the same JSON mode.

**Request checks, before any D1 read.**
- Raw body at most 32 KiB via `readBounded`; unknown fields are rejected.
- `model` must be a pinned arm. Arms B–D are accepted only when env `SUMMARY_COMPARE_ENABLED === "1"`; otherwise → `unavailable`.
- `consentVersion` must equal the version bound to the model: `t2.11-openrouter-deepseek-v1` for A, and `t2.11-openrouter-compare-eval-v1` for B–D. Anything else → `consent-required`.
- Question 1–500 characters, at most `MAX_TOOL_CALLS` steps, at most 64 facts per step, C1's per-field bounds, unique fact IDs within a step.
- Then `prepared = prepareAssistantTurn(...)`. If `bodyBytes > maxAssistantBodyBytes` → `invalid-request`, with zero upstream calls.

Output bounds are C1's. On the server, `tool` must be in T2.11a's allowlist, and an answer must pass `checkFacts` against that turn's step facts; otherwise → `invalid-response` after settlement. The caller's `askAssistant` re-checks in any case.

**Returned provider.** On this route the response's `provider` field is evidence, not a gate. It is recorded as `usage.returnedProvider` and never causes a fallback. Routing is enforced by the request (`only: [tag]`, `allow_fallbacks: false`, `require_parameters: true`) and by the per-pin preflight. The response spelling is unsourced (Sources), and a rejection on it would turn every round of a one-run arm into a paid `invalid-response`. The summary route keeps C1's rule unchanged: a present `provider` other than `DeepSeek` → `invalid-response`, and an absent one is unknown (T2.10c §Verified API and closed numeric prompt). So that check moves out of the shared `complete()` into the summary caller.

**Preflight per pin.** C1's validator runs unchanged, with the pin's values:
- exact model ID and canonical slug in the catalog;
- endpoints matching exactly the pin's `provider_name` and tag;
- context and `max_completion_tokens` of at least 1,024;
- every base and override rate at or below the pin's ceilings, with C1's allowed pricing keys, override schedule handling and fail-closed rules.

Required parameters: one shared list for every pin, `max_tokens`, `response_format` and `reasoning`, which is exactly what the body sends. `structured_outputs` is not required on any arm.

**Budget: one ledger (Decisions 1–2).** The route calls the same `reserve`/`settle` as `/v1/summaries`, on `summary_budget` and `summary_requests`, with `R = prepared.reservation.microUsd`. It inherits X-2026-09-29's rules unchanged:
- pre-check `spent + R <= 1,000,000`;
- preflight key headroom at least `R`;
- same-ID rejection and the one-in-flight slot (shared with summaries);
- no refund after the paid boundary;
- unknown cost holds `R`;
- kill when `prompt_tokens > reservation.inputTokens`, output > 1,024 or cost > `R`;
- restart fails closed.

`uses` counts every paid call of either kind. Every arm uses `inputTokens = min(contextCeiling, 2 × bodyBytes + 4096)`, which is 69,632 at the cap. The cap keeps every `R` under the existing `reservation BETWEEN 1 AND 315802` CHECK, so there is no schema change:

| Arm | Ceilings (tenths of µUSD/token, in / out) | `R` at the 32,768-byte cap |
|---|---|---|
| A | 3 / 12 | 22,119 |
| B | 14 / 40 | 101,581 |
| C | 5 / 9 | 35,738 |
| D | 30 / 150 | 224,256 |

**Eval CLI** (`tools/summary-backend/assistant-eval.ts`):

```
node --env-file=tools/summary-backend/.dev.vars --import tsx tools/summary-backend/assistant-eval.ts \
  --url http://<SUMMARY_DEV_HOST>:8788 --questions fixtures/synthetic/t2.11-question-set.json \
  --models deepseek/deepseek-v4.1-flash,xiaomi/mimo-v2.6-pro,deepseek/deepseek-v4-pro-0813,moonshotai/kimi-k3 \
  --max-spend-usd 0.05,0.05,0.15,0.25 --out /tmp/t2.11b-live-eval.json --save-replies fixtures/model-output/
```

The CLI builds datasets with T2.11a's exported `buildDatasets` and runs `askAssistant` with a client that POSTs each round with a fresh UUID. It runs the arms one after another in the listed order, cheapest first, and asks every question once per arm in question-set order. It never retries.

Before each question it reads `/v1/status`. If that arm's spend since the arm started has reached its `--max-spend-usd` value, the remaining questions become `NOT RUN (spend cap)`. A `budget-exhausted` or `unavailable` fallback stops the arm; its later questions become `NOT RUN (budget)`. The CLI never prints or writes the token or the key.

Per question, per arm, it records:
- ID, dataset, dataTag;
- tool trace, kind and reason, displayed text, cited IDs;
- `citationsResolve`, `numbersMatch`, `missingHonest` and `expectationMet` (T2.11a definitions);
- per-round input, cached, reasoning and output tokens, `returnedProvider` and `upstreamStatus` (the Worker's numeric status for a `provider-error` round, else null);
- provider-reported cost, the C1-style estimate, the reservation, provider latency and client wall latency.

Injection, per arm: q10 vs q04. PASS if the model inputs are deep-equal at every round where the tool traces coincide and the traces are equal. Differing traces with identical inputs → FAIL (nondeterminism), and both traces are kept.

`comparison` block, one row per arm, with real and synthetic dataTags reported separately and every rate given with its denominator:
- number-check pass rate: answers accepted with no fallback / questions run;
- citation resolution rate; citation correctness: `expectationMet` true / questions with an expectation;
- missing-data honesty;
- injection PASS/FAIL;
- rounds with nonzero `reasoningTokens`;
- returned provider: rounds whose `returnedProvider` differs from the pin's `provider_name` / rounds that report one, rounds that report none, and the distinct values;
- cost per answer: median, max and total, plus the count of answers above US$0.01 and above US$0.05;
- latency per answer: median and max.

The header holds:
- code SHA, date, both prompt versions and the question-set path;
- each pin's catalog and endpoint snapshot (fetch time, SHA-256, validated rates), taken from the free metadata URLs at start; they gate only the LIVE label (Labels);
- shared-budget `spent` before and after each arm.

The CLI saves no raw provider body, key document or IP.

`--save-replies <dir>` writes `t2.11-live-<model-short>.json` for each **fully run** arm only: all 12 questions have status `RUN`. A question that ended in a fallback counts as run; its `reject` round is saved and replays to the same fallback. An arm with any `NOT RUN` question writes no file, because the CI replay asks every scripted question and a partial file cannot replay; its rows stay in the eval artifact. Each file uses T2.11a's `SavedResponses` shape with a header:
- `label` (Labels);
- model, canonical slug, provider tag, the distinct `returnedProvider` values, prompt versions, run date, code SHA and the eval artifact name.

It stores only replies and usage for the scripted questions (Decision 5), and it is never hand-edited.

**Labels.** Without `--synthetic-metadata-base`, the artifact is labeled `LIVE paid eval through the local summary Worker` and each replies file `RECORDED MODEL OUTPUT (live, scripted T2.11 questions; not synthetic, not an ELM327 recording)`. That label rests on more than the flag: before the first question, every arm's snapshot from `https://openrouter.ai/api/v1` must have been fetched, must contain an endpoint with the pin's `provider_name` and tag, and the catalog must list the pin's canonical slug. Otherwise the CLI exits nonzero with no question sent and no file written. The test-only flag `--synthetic-metadata-base <url>` labels both SYNTHETIC; a URL whose host is `openrouter.ai` is refused before any request.

## Experiment

- **Question.** On T2.11a's frozen question set (12 questions, prompt `t2.11-v1`), how do the three comparison arms differ from flash in deterministic pass rates, and at what cost and latency per answer?
- **Controlled.** Everything is identical across arms: prompt, adapter preamble, JSON-mode request, `max_tokens`, reasoning off, datasets, question order, checker, one attempt per question. Only `model` and the host pin change.
- **Data.** Two real redacted Equinox recordings plus labeled synthetic and synthetic-mutated charge logs (T2.11a). Rows are reported per dataTag and are never pooled with synthetic.
- **Held out.** The whole set is a test set: no tuning, no reruns to improve a number. A schema rejection, nonzero reasoning tokens or a low pass rate is a recorded negative result, not a reason to change an arm.
- **Spend estimate** (an estimate, not a measurement). The assumptions come from T2.11a's synthetic traces: about 3,600 input and 250 output tokens per typical question. A thorough answer is 5 rounds with about 20,000 input and 560 output tokens. A and B are priced at their ceiling (peak-hour) rates; off-peak is half.

  | Arm | Typical answer | Thorough answer | Expected arm total (12) | Stop rule |
  |---|---|---|---|---|
  | A flash | US$0.0014 | US$0.007 | US$0.017 | US$0.05 |
  | C MiMo V2.6 Pro | US$0.0018 | US$0.009 | US$0.022 | US$0.05 |
  | B V4 Pro 0813 | US$0.0057 | US$0.029 | US$0.068 | US$0.15 |
  | D Kimi K3 | US$0.015 | **US$0.068 (above the US$0.05 target)** | US$0.18 | US$0.25 |

  The four arms are expected to cost about **US$0.28** in total. The planned maximum is about **US$0.61**: the stop rules (US$0.50) plus at most one thorough question of overshoot per arm (about US$0.11). That leaves at least about US$0.39 of the shared US$1 for the T2.10 phone check, which runs first, and the owner's summaries (about US$0.003–0.01 each).

  If the owner drops C and D instead of replacing them, the expected cost is about US$0.09 and the maximum about US$0.24. The hard limits stay the durable US$1 ledger and the key's non-resetting US$1 cap. Compute: local WSL2 Worker only.
- **Artifacts.** `/tmp/t2.11b-live-eval.json` (local, not committed) and files 7–10 (committed after review).
