## Goal

Add a foreground relay mode to the existing Android BLE console. After the user connects to the Veepeak, they can enter the WSL2 relay URL and per-process token, connect the app's built-in WebSocket, and forward one server-authorized ELM command at a time over the existing `BleTransport`. The app independently applies T0.6a's policy, waits for a complete `>` response, reports the exact bytes and elapsed time, rejects malformed or concurrent requests, and presents an explicit native confirmation on the phone for each exact Mode 04 request before any BLE write.

T0.6a is an implementation prerequisite. Together the two specs satisfy T0.6; the owner-arranged HIL gate remains the final hardware evidence.

## Non-goals

- No MCP SDK or MCP protocol inside the app. The phone speaks only the small authenticated WebSocket protocol defined by T0.6a; MCP stays in Node.
- No new npm or native dependency, EAS config/plugin change, APK rebuild, background service, screen-lock prevention, reconnect loop, TLS, QR scanner, token persistence, secure-store work, navigation framework, or production UI.
- No local relay recording buffer or file export. The Node relay owns start/stop and the raw original; current one-button capture/codes and their automatic save remain available outside relay mode.
- No vehicle profile, signal display, DTC clear button, generic arbitrary-command UI, or automatic Mode 04 approval. Confirmation is per request and cannot be remembered.
- No UDS writes (`2E`, `31`, `2F`), session changes, unknown services, unknown AT commands, or arbitrary binary traffic, even if a malformed or compromised relay requests them.
- No simultaneous unsaved debug Send, capture/codes, battery diagnosis, foreground charge log, and relay mode. One BLE transport has one response reader at a time.
- No edits to recordings, the Node relay spec/implementation, planning/decision/task-run documents, native configuration, or the pre-existing T0.8c Metro/color baseline except where `App.tsx` must integrate relay controls.

## Interfaces

All new exports are named.

### Relay client

`apps/mobile/src/relay/RelayClient.ts`:

```ts
import type { Transport } from "obd-core/transport";

export interface RelayWebSocket {
  readonly readyState: number;
  send(data: string): void;
  close(code?: number, reason?: string): void;
  addEventListener(type: "open" | "message" | "error" | "close", listener: (event: unknown) => void): void;
  removeEventListener(type: "open" | "message" | "error" | "close", listener: (event: unknown) => void): void;
}

export interface RelayPhoneMeta {
  vehicle: "chevrolet-equinox-ev-2024";
  dongle: "veepeak-obdcheck-ble";
  writeChar: string;
  notifyChar: string;
  mtu: number;
}

export type ConfirmMode04 = () => Promise<boolean>;

export class RelayClient {
  constructor(
    socket: RelayWebSocket,
    transport: Transport,
    meta: RelayPhoneMeta,
    confirmMode04: ConfirmMode04,
    timeoutMs?: number,
    nowMs?: () => number,
    onTerminal?: () => void,
  );
  close(): void;
}
```

Behavior:

1. On WebSocket open, send the exact T0.6a `hello` with `protocol: 1` and BLE metadata. Reject/close on invalid URL setup before construction; never log, display in the transcript, or persist the token after it has been used to construct the URL.
2. Validate each inbound JSON object and permit one `command` request at a time. Call `authorizeRelayCommand(command)` from `obd-core/transport/relay` independently. Reject duplicate IDs, a second pending request, invalid JSON/schema, binary/non-string messages, pre-open traffic, or any policy mismatch without writing BLE.
3. For a normal allowed command, require `confirmMode04 === false`. For exact `04`, require `confirmMode04 === true`, then await the injected confirmation callback. Denial sends `confirmation-denied` and performs no BLE write. Approval applies only to that request; send exactly `04\r` once. A true flag on any other command, or false on `04`, is `invalid-command`.
4. Subscribe once to `BleTransport`, create a fresh `ElmLineReader`, send `{ type: "started", id }` immediately before calling `transport.write()` with the normalized command plus one `\r`, collect notification chunks byte-for-byte, and settle only at the first `>` prompt. Return all bytes through and including that prompt as standard base64 and elapsed monotonic milliseconds. A second completed response or bytes after completion are not attached to a later request; close the relay as a protocol/session error because response ownership is ambiguous. A denied/invalid command never sends `started`; a write failure after `started` returns `transport-error`.
5. Default command timeout is 20 seconds, matching the existing foreground console. On timeout, transport write failure, socket send failure, socket close/error, BLE disconnect, or `close()`, reject/clean the one pending request exactly once, unsubscribe, reset the reader, and prevent late callbacks from settling a later request. `close()` is idempotent and does not close the shared BLE transport; `App` owns BLE teardown.

The implementation may use the platform `WebSocket` through a small adapter matching `RelayWebSocket`; tests inject a fake. Use `base64-js`, already installed for BLE, for byte/base64 conversion. Do not use `Buffer`, `btoa`, or an assumed UTF-8 decoder for ELM bytes.

### App integration

`App.tsx` adds a compact “Relay mode” section visible only after BLE connection:

- blank editable relay base URL with a `ws://<WSL-host>:8765` placeholder, and a secure-text token field;
- Connect relay / Disconnect relay button and a status line with disconnected, connecting, connected, busy, or error state;
- starting relay is disabled while any current local mode owns BLE; all local command/run actions are disabled while relay connects or owns BLE; BLE disconnect tears down relay first;
- relay connect builds `/phone?token=...` with `URL`/`URLSearchParams` or equivalent safe encoding, then clears the token field after the socket opens; the rendered status/transcript never includes the URL query or token;
- each Mode 04 request invokes React Native `Alert.alert` on the physical phone. The message says clearing DTCs also clears freeze-frame data and asks the user to confirm this one operation. Cancel/deny resolves false; the destructive action button resolves true. Dismissing the alert is denial. No timeout, previous answer, MCP argument, or server message counts as approval;
- while the confirmation alert is open, the app remains busy and does not accept another relay command. Leaving relay mode or losing BLE denies/cleans the request;
- current console, capture/codes, diagnosis and charge-log behavior and artifacts, explicit light/dark colors, and Metro resolution remain intact.

The URL placeholder is application guidance, not an OBD constant. The user enters the WSL2 address printed by `pnpm relay`/`pnpm hil:smoke`; the app does not assume a host address is reachable.

## Risks / open questions

- **Largest risk: lifecycle ownership across all current BLE users, relay reader, disconnect, and WebSocket close.** Two readers would assign one dongle response to the wrong caller. `App` must make the modes mutually exclusive and tear down relay synchronously before reusing the transport.
- React Native's WebSocket event typings differ from DOM typings. The small injected adapter isolates that difference. If Expo SDK 57 lacks a needed event behavior on the physical phone, report the exact behavior and return to architecture; do not add a socket package.
- The phone must remain foregrounded with its screen on, as ADR-013 records. Background relay work belongs with later foreground-service scope.
- The relay token is transient but entered in UI. Clearing it after open and never copying the query into status/transcript reduces accidental disclosure; transport encryption remains outside this local-only task.

No material design question remains open. T0.6a fixes the wire and policy; this spec uses the existing Android stack and requires no dependency or native-build choice.

## Decisions

- Keep the Android half separate and ordered after T0.6a so the wire, server policy, and fake phone are stable before UI integration.
- Reuse `BleTransport` directly with a dedicated relay response reader. All current local modes and relay are mutually exclusive rather than sharing response buffers.
- Apply the shared allowlist on both server and phone. The server remains authoritative for MCP, while the phone refuses unsafe traffic if the network peer is malformed or compromised.
- Use a per-request native alert for Mode 04. Denial/dismissal is the normal physical acceptance path; no real DTC clear is required.
- Keep relay changes JavaScript-only. The existing development client can load them through Metro once the pending T0.8 acceptance baseline is valid.
