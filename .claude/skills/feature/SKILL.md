name: feature
description: Drive one task through the architect → implementer → reviewer loop. Usage: /feature T0.4 (a task id from docs/PLAN.md) or /feature "free-text request".
---

Run the three-agent loop for the task given in the arguments. You are the orchestrator; you do not implement.

0. **Record.** Read `docs/task-runs/<task-id>.md` if it exists (for free-text requests the id is `X-<date>-<slug>`). If it exists, reconcile it against the spec, `git status --short`, and the recorded evidence, and resume at the first incomplete or invalidated stage; do not redo valid stages, and do not inherit an approval. If it does not exist, create it with the headings of an existing record (`docs/task-runs/T0.1.md`) and the minimum contents listed in `docs/WORKFLOW.md`, Handoff section, starting from the baseline `git status --short`. Update the record after every step below, on every blocker, and before you stop. Codex uses the same record; it is the only handoff between the two tools.
1. **Architect.** Spawn the `architect` subagent with the task id or text. Questions about what a recording contains go to the `recording-analyst` subagent, so raw recordings are never read in the main conversation. When the architect returns, read the spec it wrote. If it lists open questions, put them to the user now with AskUserQuestion and record the answers in the spec's "Decisions" section before continuing. If the user is not available and a question is material, stop here and report.
2. **Confirm scope.** Show the user a condensed version of the spec's Goal, Non-goals, and Files sections and ask whether to proceed. Skip this step only if the user said "no confirmation" in the arguments.
3. **Implementer.** Spawn the `implementer` subagent with the spec path and the task id. It runs in its own worktree (made from `HEAD`, so uncommitted work on main is not in it; if the task depends on such work, stop and tell the user to commit it first) and commits on its branch. Relay its report verbatim to the user. Check its claims cheaply with `git -C <worktree> status --short` and `git diff main...<branch> --name-only` before review.
4. **Reviewer.** Spawn the `reviewer` subagent with the spec path, the branch and the worktree path. Relay its verdict and findings verbatim. Route any check you run yourself through the `test-runner` subagent so its output never floods the conversation.
5. **Loop.** On REQUEST_CHANGES, spawn a fresh `implementer` with the spec path, the reviewer's findings, and the instruction to continue on the same branch in the same worktree (`cd <worktree path>`), then review again. A minor with an exact fix can go to `quick-fix` instead, or to Codex (step 7). At most two loops in total across tools and resumptions (the record holds the count). If still not approved, stop and give the user the remaining findings; do not merge by fiat.
6. **Integrate.** On APPROVE, spawn the `integrator` with the branch, worktree path, task id and the approved head sha. It merges into main, runs `pnpm check` through `test-runner`, reverts on a failing gate, and removes the worktree. A reverted merge counts as a REQUEST_CHANGES loop.
7. **Close.** Summarize what changed, what was verified (with the recording paths if hardware was involved), and what remains hardware-only. Do not tick the task in `docs/PLAN.md` yourself; tell the user it is ready to tick. Set the record's stage to closed with the verdict, merge sha and any NOT RUN items. Record edits longer than a line or two go to `scribe` with the exact content. Then `/compact`.

Mechanical work with an exact spec (a reviewer minor with a given fix, a sweep of eslint fixes, record archiving) goes to the Codex CLI first, which uses no Claude usage: write the brief to a file under the scratchpad and run in the background, stdin closed, `codex exec -C <worktree> -s workspace-write -o <scratchpad>/codex-out.md "$(cat <brief>)" < /dev/null` (without `< /dev/null` it waits forever for input). Ask for a short final report. `quick-fix` is the fallback. A Claude reviewer checks Codex's change before merge.

Keep your own messages short. The subagents' reports are the content; your job is sequencing and surfacing decisions.
