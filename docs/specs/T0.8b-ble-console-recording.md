# T0.8b: Veepeak BLE console and recording export

## Goal

Turn the T0.8a Android development client into a foreground debug console that requests Android BLE permissions, scans and connects directly to the Veepeak OBDCheck BLE, discovers its write and notify characteristic roles by properties, implements the existing `Transport` interface with negotiated-MTU write chunking and notification delivery, sends one read-only ELM command at a time, displays each response only after the `>` prompt, and exports the exact transmitted and notification chunks as a standard `.jsonl` recording through Android's share sheet. Completion is one Equinox EV phone session: the console sends the sourced init sequence and `0100`, receives a `41 00` response, exports one immutable recording to `fixtures/recordings/chevrolet-equinox-ev-2024/2026-09-<dd>-phone-console.jsonl`, and the repository replay test passes on that file.

## Non-goals

- No Chrysler 200 or Hyundai Elantra capture or app run. ADR-015 makes both optional bench vehicles; they are not T0.8 or later Phase 0 gates.
- No `Elm327Session`, automatic init, retry policy, ISO-TP decoding, PID/DTC decoding, vehicle profile, report, garage, background operation, reconnect loop, relay/MCP mode, or persisted recording library.
- No Mode 04 support, UDS writes, coding, adaptation, arbitrary binary entry, or unrestricted console. This console accepts only the eight explicitly sourced AT commands and read-only services listed below; it rejects everything else before BLE write.
- No pairing through Android settings. No iOS, web, Expo Go, local Android build, Play Store build, or new native dependency beyond T0.8a.
- No edits to existing recordings. The phone session creates a new file; if the intended name exists, choose a `-2` suffix before capture rather than overwrite or edit.
- No claim that notification boundaries equal ELM response boundaries. `BleTransport` forwards decoded notification chunks; `ElmLineReader` reassembles them until `>`.

## Interfaces

All new exports are named. `App.tsx` may retain the default adapter required by `expo/AppEntry`.

### `src/ble/BleTransport.ts`

```ts
import type { BleManager } from "react-native-ble-plx";
import type { Transport } from "obd-core/transport";

export const VEEPEAK_SERVICE_UUID = "0000fff0-0000-1000-8000-00805f9b34fb";
export const VEEPEAK_CHARACTERISTIC_UUIDS: readonly string[]; // full FFF1, FFF2 UUIDs
export const REQUESTED_MTU = 185;

export interface ScannedDevice {
  id: string;
  name?: string;
  rssi?: number;
}

export function scanDevices(
  manager: BleManager,
  onDevice: (device: ScannedDevice) => void,
  onError: (error: Error) => void,
): () => void;

export interface BleConnection {
  transport: BleTransport;
  deviceId: string;
  deviceName?: string;
  mtu: number;
  writeCharacteristicUuid: string;
  notifyCharacteristicUuid: string;
}

export function connectVeepeak(manager: BleManager, deviceId: string): Promise<BleConnection>;

export class BleTransport implements Transport {
  write(bytes: Uint8Array): Promise<void>;
  onData(cb: (bytes: Uint8Array) => void): () => void;
  onError(cb: (error: Error) => void): () => void;
  close(): Promise<void>;
}
```

Behavior:

1. `scanDevices` scans without a service filter because the app must not assume the dongle advertises `FFF0`. It de-duplicates by Android device ID and updates name/RSSI when the same ID appears. The returned function stops the scan. `App` stops scanning before connect and on unmount.
2. `connectVeepeak` calls `manager.connectToDevice(deviceId)`, then `discoverAllServicesAndCharacteristics()`. It finds service `FFF0`, restricts candidates to `FFF1`/`FFF2`, chooses write-without-response first or write-with-response second by characteristic properties, and independently chooses notify or indicate by properties. UUID identity never decides the role. Missing/ambiguous roles fail with a user-visible GATT property summary.
3. After discovery, request MTU 185 on Android. If the request rejects, continue with the connected device's reported MTU (23 is the library default). The connection reports the actual MTU. Per-write payload size is `max(1, actualMtu - 3)`, mechanically preserving the documented 23 → 20 relationship; every slice is base64-encoded with `base64-js` and awaited in order using the characteristic's supported write method.
4. Start the notification/indication monitor before returning the connection. Each non-null base64 value is decoded to a fresh `Uint8Array` and delivered to current `onData` subscribers unchanged; `BleTransport` does not search for `>` or combine notifications. Monitor errors go to `onError` and never masquerade as data.
5. `close()` is idempotent: mark closed, remove the monitor, clear subscribers, and cancel the device connection. Writes after close reject; callbacks after close are ignored. It does not destroy the app-owned `BleManager`.

### `src/recording.ts`

```ts
import type { RecordingLine } from "obd-core/recording";

export interface RecordingMeta {
  car: "chevrolet-equinox-ev-2024";
  dongle: "veepeak-obdcheck-ble";
  note: string;
  writeChar: string;
  notifyChar: string;
  mtu: number;
}

export class RecordingBuffer {
  constructor(nowSeconds?: () => number);
  start(meta: RecordingMeta): void;
  tx(data: string): void;
  rx(bytes: Uint8Array): void;
  meta(note: string): void;
  lines(): readonly RecordingLine[];
  toJsonl(): string; // one JSON object + "\n" per line, including the final newline
}
```

`start` resets the monotonic origin and creates the first `meta` line. `tx` and `rx` throw until started. Every `t` is non-negative seconds since `start`, rounded to three decimals. `rx` uses `latin1Decode`, preserving all byte values. `lines()` returns a defensive copy. `toJsonl` uses `JSON.stringify`; it does not normalize or merge data chunks.

### `src/console.ts`

```ts
import type { Transport } from "obd-core/transport";
import type { RecordingBuffer } from "./recording.js";

export const READ_ONLY_SERVICES: readonly string[]; // 01, 02, 03, 06, 07, 09, 0A, 22
export const ALLOWED_AT_COMMANDS: readonly string[]; // ATZ, ATE0, ATL0, ATS0, ATH1, ATSP0, ATDPN, ATRV
export function normalizeReadOnlyCommand(input: string): string;

export class ConsoleSession {
  constructor(transport: Transport, recording: RecordingBuffer, timeoutMs?: number);
  send(input: string): Promise<string>; // raw response, without the terminating '>'; App displays raw + ">"
  close(): void;
}
```

`normalizeReadOnlyCommand` trims, uppercases, collapses internal ASCII whitespace, and rejects control/non-ASCII characters. It accepts an AT command only when the entire normalized input is exactly `ATZ`, `ATE0`, `ATL0`, `ATS0`, `ATH1`, `ATSP0`, `ATDPN`, or `ATRV`; there is no prefix/wildcard AT allowance. It otherwise accepts a hexadecimal command whose first byte is exactly one of `01`, `02`, `03`, `06`, `07`, `09`, `0A`, `22`. It explicitly rejects `04`, `2E`, `2F`, `31`, unknown/parameterized AT commands, empty input, odd hex, and every other service. It returns the display/send form without `\r`; the caller appends exactly one `\r`.

`ConsoleSession` subscribes once, records each notification as one `rx` line before pushing it to `ElmLineReader`, and permits exactly one pending `send`. `send` validates, records the `tx` line before awaiting `transport.write`, and resolves only when `ElmLineReader` emits the next complete response. A second send rejects as busy. Default timeout is 20,000 ms; timeout records meta note `timeout waiting for '>' after <cmd>`, resets the reader, rejects, and unlocks the console. Transport write failure records meta note `write failed after <cmd>: <ErrorName>`, rejects, and unlocks. `close` unsubscribes and rejects any pending send.

### `App.tsx`

One screen, no navigation dependency:

- Requests `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` on Android API 31+; requests `ACCESS_FINE_LOCATION` on older supported Android releases. Denial leaves scan disabled with a clear message.
- Owns one `BleManager`, destroys it only on application component cleanup, lists de-duplicated scan results (name, ID, RSSI), and connects only after a user tap.
- Displays connection state, actual MTU, selected characteristic UUIDs, command input, Send button, scrollable timestamp-free console transcript, recording Start/Stop state, note input, and Export button.
- Send is disabled unless connected, recording is active, and no command is pending. The recording requirement ensures acceptance evidence cannot omit the transmitted command.
- Start requires a non-empty vehicle-state note and fixes `car`/`dongle` to the `RecordingMeta` literals. Stop freezes the current buffer. Export writes a new `File(Paths.cache, filename)`, failing rather than overwriting, then calls `Sharing.shareAsync(file.uri, { mimeType: "application/x-ndjson", dialogTitle: "Export OBD recording" })`.
- Filename is local date `YYYY-MM-DD-phone-console.jsonl`; if it already exists, add `-2`, `-3`, etc. The repository destination is chosen explicitly in Verification and is not inferred by the app.
- Disconnection, scan error, notification error, timeout, and write error are visible; none leave Send permanently busy. No automatic reconnect.

## Risks / open questions

- **Largest risk: Android GATT variability.** The dongle may reverse FFF1/FFF2 roles, refuse MTU 185, split `>` from preceding bytes, or disconnect during a write. Property discovery, fallback to actual MTU, raw notification preservation, and the real recording make each behavior visible; no UUID role or chunk boundary is assumed.
- The app records in memory until export, so a process kill loses the current short debug session. Durable streaming storage belongs with long-running logging, not this acceptance console.
- Only the eight adapter commands required for generic init/status are allowed; unknown or parameterized AT input is rejected. The relay's broader but still explicit server-side allowlist belongs to T0.6.
- Android device ID can identify the adapter and is unnecessary for replay. Keep it on the live connection screen only; do not put it in immutable recording metadata. T2.9 owns the broader consent/redaction design for beta exports.

## Decisions

- ADR-015: only the Equinox EV is the T0.8 hardware gate; no ICE capture or run is required.
- `BleTransport` preserves notification chunks and `ElmLineReader` performs prompt reassembly. This satisfies the `Transport` contract and prevents two competing response buffers.
- Request MTU 185 but calculate chunks from the actual returned/reported MTU; a rejected request is not a connection failure.
- The debug console is read-only by construction and has no Mode 04 confirmation UI. Mode 04 is therefore unavailable, not merely discouraged.
- Use an in-memory recording for this short acceptance session and the system share sheet for user-directed export; persistence and consent workflows remain T2.9.
- Omit Android BLE device ID from exported recording meta; characteristic UUIDs and actual MTU are sufficient transport provenance for this task.
