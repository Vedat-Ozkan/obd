# T2.15: Report-derived red-flag screen

## Goal

Every saved Equinox battery diagnosis opens with a verdict card and a coverage list derived deterministically from that report. The verdict checks the 80 cell-group voltages at rest against their set median and total spread, and checks reported diagnostic codes. It says **No red flags found** only when the scan is complete and both core checks ran; otherwise it says **Check incomplete** unless an observed finding warrants **Ask about this** or **Red flag: get it inspected**. The list always says what ran, what did not, and why. The rendered report and a replay artifact show the same result.

## Non-goals

- No battery-health score, grade, certification, estimated capacity, 12 V diagnosis, temperature scaling/agreement, or new vehicle read. The BMS capacity figure, 12 V supply and raw `2AF1` bytes remain informational.
- No change to existing rating chips, the `health: not-assessed` and `capacity: not-measured` fields, assistant facts/prompts/checker, or report schema/version. The verdict is derived on opening and rendering a report, including older saved reports.
- No drive verdict yet. T2.13 Stage B and Stage C are NOT RUN; Stage C has no approved report interface. The parked verdict must not treat an unrelated drive recording's group sets as rest readings. Map a future report's checked under-load finding and codes rescan in T2.13 Stage C/T2.18 after those interfaces are approved.
- No manufacturer per-module UDS `19` code read (T2.16), no charge-log redesign, no fixture recording edit, car session, new dependency, or commit in this task.

## Interfaces and behavior

```ts
// packages/obd-battery/src/report.ts; pure, named export
export type RedFlagOutcome = "no-red-flags" | "ask-about-this" | "red-flag" | "check-incomplete";
export interface RedFlagFinding {
  severity: "ask-about-this" | "red-flag";
  check: "cell-groups-at-rest" | "codes";
  detail: string; // group number/module and measured mV or code/ECU, no invented diagnosis
}
export interface RedFlagCoverage {
  check: "cell-groups-at-rest" | "codes" | "bms-capacity-figure" | "twelve-volt-supply" | "raw-temperature";
  status: "checked" | "shown-only" | "not-checked";
  reason?: string; // required for not-checked; shown-only says why it is not judged
}
export interface RedFlagScreen {
  outcome: RedFlagOutcome;
  headline: "No red flags found" | "Ask about this" | "Red flag: get it inspected" | "Check incomplete";
  findings: readonly RedFlagFinding[];
  coverage: readonly RedFlagCoverage[];
  scope: "Among the checks listed. This does not certify battery health.";
  policy: { groupAskMv: number; groupRedMv: number; spreadAskMv: number; spreadRedMv: number; label: "Project policy" };
  limitation: "Limits come from one car; self-comparison can miss even pack-wide degradation or reflect a sensor offset.";
}
export function redFlagScreen(report: BatteryDiagnosisReport): RedFlagScreen;
```

`redFlagScreen` takes only the already validated `BatteryDiagnosisReport`; it does not replay, query the vehicle, or mutate/persist the report. `renderBatteryDiagnosis` calls it and prints a `## Red-flag screen` section with headline, scope, ordered findings, all four numeric limits labeled **Project policy**, the one-car limitation, and all five coverage rows. `reportSummary` adds the returned screen as `verdict`, leaving its existing `soc` and four `rows` values and ratings unchanged. `ReportSummary` renders an actual visible verdict card (headline, scope, findings, numeric limits, limitation and coverage, including reasons), ahead of the four rows; its accessibility text includes the same headline and incomplete reasons. No new navigation route is needed.

**Rest groups.** Only `report.parked?.groupVoltages` qualifies. It is T2.14's latest complete 80-record set with bracketing current within `REST_CURRENT_A`, from the one report recording; `cellSpread` from community `2AF5`, unbracketed drive sets, and BMS capacity never substitute. The 80 entries are in recorded order; display group numbers 1–80 with the provided module IDs. Convert each decoded voltage once to an integer 0.1 mV tick with `Math.round(volts × 10000)`, matching the sourced group-record resolution. Compute the median as the midpoint of sorted ticks 40 and 41; it may have half-tick precision. For each group use `abs(ticks[g] − medianTicks) / 10` mV; spread is `(maxTicks − minTicks) / 10` mV. Compare integer/half-integer ticks to the named mV limits times ten; round only display to 0.1 mV. A group above `REST_GROUP_ASK_MV` gets an ask finding; above `REST_GROUP_RED_MV` gets a red finding. The set spread above `REST_SPREAD_ASK_MV` gets an ask finding and above `REST_SPREAD_RED_MV` a red finding. Comparisons are strict `>`; exactly at a limit is unflagged. Report group and spread findings separately, so the user can see both signals, but the worst severity alone sets the headline. If group data is absent, coverage says `not-checked` and names the missing complete/rest-bracketed set; a legacy `cellSpread` does not change that status.

**Codes.** A core codes check counts as checked only when at least one `CodesReport.modules` entry has a successful `read` for each of stored, pending and permanent modes. They may be different responding modules; coverage says that this is standard OBD code coverage, not every vehicle module. Failed or not-read modes keep codes `not-checked` with the missing mode names. Any actual DTC in any successful stored/pending/permanent reply is an **Ask about this** finding with mode, ECU and code; de-duplicate identical mode/ECU/code triples. A `recentlyCleared.verdict === "indicated"` is also an ask finding with that exact qualified wording. These observed findings display even if other code modes failed. No reported code plus a failed mode is incomplete, never a clean result. This does not replace or recalculate `codesRating`.

**Outcome and coverage.** Precedence is red finding, then ask finding, then incomplete core coverage or `scanStatus === "partial"`, then no red flags. A partial scan without a finding is always **Check incomplete**. Findings from partial data remain visible with their severity, alongside incomplete coverage and a partial-scan note. Coverage always has the five rows above, in that order. BMS figure present, 12 V observation present, and raw `2AF1` present are `shown-only`, each explicitly saying no verdict limit exists; absent items are `not-checked` with a concrete absent/not-recorded reason. These three never promote a report to complete and never create a finding. The card says the policy was set from one car and may miss uniformly degraded groups or a sensor offset; a flag calls for inspection, not a diagnosis.

### Named project-policy limits

These are product policy, not OBD constants or calibrated fault thresholds. Freeze them in this spec before implementation or synthetic injection results are evaluated:

| Name | Limit | Rationale from committed Equinox evidence |
|---|---:|---|
| `REST_GROUP_ASK_MV` | 5 mV | Above the 2.1 mV maximum absolute median deviation among 13 rest-bracketed targeted-watch sets. |
| `REST_GROUP_RED_MV` | 10 mV | A second, larger departure on the same scale; an inspection prompt, not a proven fault. |
| `REST_SPREAD_ASK_MV` | 6 mV | Above the 2.8 mV maximum spread in those 13 rest sets. |
| `REST_SPREAD_RED_MV` | 12 mV | A second, larger spread departure; inspection prompt only. |

The 5/6 mV ask limits are more than twice the observed rest maxima after rounding up to whole mV; the 10/12 mV red limits are twice those ask limits. Do not tune them using the synthetic injected case or future recordings. The one-car sample supports only a low false alarm observation on these captures; it does not establish sensitivity, specificity or a battery-health boundary. Keep untouched real and synthetic results in separate artifact tables.

## Risks / open questions

- Largest risk: one owner's car supplies all rest policy evidence. A uniformly weak pack can compare normally with itself; sensor offset, SOC and temperature can affect individual groups. The verdict copy must state this limit and direct a strong finding to inspection rather than assert a fault.
- The targeted watch is a development recording, not the pending T2.14 upgraded app scan. Its 13 rest-bracketed sets test the report path and anchor policy, while the owner-phone capture gate remains separate. The two bounding current samples are 98.309 seconds apart; T2.14 has no maximum bracket gap. State the operational bracket criterion plainly and avoid claiming current was continuously low throughout those sets.
- A code mode can answer on one module and fail on another. The coverage row must explain that a successful standard mode does not guarantee every ECU was queried or answered. T2.16 adds manufacturer module codes later.
- T2.13 Stage C has no stable `BatteryDiagnosisReport.drive` field yet. Do not invent one here; integration is a prerequisite to a drive finding on this card.
- If the analyst finds a committed recording with an actual rest-group or code finding beyond the targeted watch, correct its fixed expected row before implementation; do not tune limits to make it pass.

## Decisions

- Owner authorized routine policy choices for this spec. Freeze 5/10 mV group and 6/12 mV spread limits from the committed targeted-watch rest sets before applying them; label all four **Project policy**.
- Code presence and a reported recently-cleared indication warrant **Ask about this**. A strongly outlying rest group or spread warrants **Red flag: get it inspected**. Findings outrank incomplete coverage in the headline, but coverage and partial status remain visible.
- Core codes coverage requires one successful stored, pending and permanent read each. Core rest coverage requires the T2.14 complete, bracketed 80-group field. `scanStatus: "partial"` prevents a no-flags headline.
- Keep verdict derived from the current report (including saved version-1 reports). Ratings and assistant facts remain governed by their existing rules; no schema migration or new dependency is needed.
