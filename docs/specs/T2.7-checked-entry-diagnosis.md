# T2.7: Battery diagnosis for a `checked` garage entry (acceptance E2E)

## Goal

Prove, with a replay through the public entry points, that a garage entry tagged `checked` gets the same battery diagnosis as a `mine` entry. The redacted Equinox spike recording becomes a report saved under the `checked` entry's ID and read back from a fresh history instance. The test asserts every field the recording supports: SoC, cell spread, 12 V, codes and "recently cleared". It asserts every missing-data state: capacity NOT MEASURED, health not assessed, "recently cleared" unknown, and PIDs that were not read or not supported. It also asserts that the report does not show up under a same-model `mine` entry. A second case runs the production scan action (`runAndSaveBatteryDiagnosis`) for the `checked` entry, using the labeled synthetic combined scan.

**Gap assessment: the software gap is essentially zero.** T2.6d (commit `80853ab`) and the redesign stages A to C4 already deliver the per-entry fresh scan, private-scan-first saving, history, detail and deletion guard. They do this for any verified Equinox entry whatever its ownership (`docs/specs/T2.6d-in-app-diagnosis-flow.md` §Goal; ADR-018). Nothing in `batteryDiagnosisFlow.ts`, `batteryReports.ts`, `reportView.ts`, `CarScreen.tsx` or the `ConsoleScreen.tsx` check path branches on `ownership`. `CarScreen` gates "Run check" on the catalog row (`canUseEquinoxConsole`), not on the tag. The report already has the T2.5 12 V section and the T0.7 codes and "recently cleared" section. What is missing is test evidence. Existing tests run the production action only for the `mine` entry (`battery-diagnosis-flow.test.ts` `setup().first`). They use the `checked` entry only for history isolation, through `history.save` directly. `report-view.test.ts` asserts the fields only on in-memory reports with `garageVehicleId: "1"`, never on a report persisted under a `checked` entry. So this task adds one test file and no source change.

## Non-goals

- No source change in `apps/mobile/src`, `packages/obd-battery` or `packages/obd-core`. If an assertion fails on current code, stop and report it (see Verification). Do not fix it in this task.
- No capacity or charge-estimate enrichment. That needs T2.4 data and an estimator (PLAN T2.6 gate, still open).
- No "pre-purchase report" product, PDF, export or share action (ADR-018).
- No ownership-specific wording, badge or report field. The report is tied to its entry by `garageVehicleId`, and ownership belongs to the entry (see open question 2).
- No per-car charge logs. `ReportHistory` says that comes later.
- No new OBD command, signal or threshold, and no new recording.
- No re-test of what T2.6d already covers: ownership-toggle retention, the removal guard, cancel and close races, storage errors, unsupported-entry rejection.

## Verification

Shared checks: `pnpm -F mobile test`, `pnpm -F mobile typecheck`, `pnpm check` and `git diff --check` pass. The diff contains only the new test file. The tests are acceptance E2Es over code that already exists, so they are expected to pass the first time. **If an assertion fails, do not change source or relax the assertion.** Record the failing assertion and the artifact, and hand back to the orchestrator. The architect then amends this spec with the repair.

- [ ] **E2E 1, real recording, `checked` entry.**
  - Setup: a garage with Equinox `mine` (ID 1), then Equinox `checked` (ID 2). Build the spike report with `batteryDiagnosisFromRecording` for `garageVehicleId: "2"`, `scanStatus: "complete"` and a fixed `scannedAt`, then `history.save` it.
  - Reload: create a **new** `createGarageFlow` and `createBatteryReportHistory` over the same stores.
  - Assert association: `list("2")` has exactly one report with `garageVehicleId === "2"` and recording equal to the spike path. `list("1")` is empty. The reloaded garage still has entry 2 as `checked`.
  - Assert fields on the **reloaded** report, using the Sources literals. From `reportSummary`: SoC 69.8 verified, and rows in the order cells "3.0 mV", capacity "Not measured", 12 V "12.7 V", codes "No codes"/`ok`. From `sectionDetail`: the SoC readings, cell min/avg/max and spread (community tier), the capacity hero "Not measured", and the 12 V adapter-supply label with power state `ready`. From `codesView`: recently cleared legs yes/no/unknown/no, modules 17/28/40/45/CB, zero codes. From `moduleRows(codes, "17")`: PID 4E "not supported" and Mode 0A "not answered (negative response 11)".
  - Assert missing data: `report.capacity.status === "not-measured"` and `report.health.status === "not-assessed"`. `renderBatteryDiagnosis` output contains `Garage vehicle: 2`, `capacity: NOT MEASURED`, `battery health: not assessed` and `Recently cleared: unknown`.
  - Artifacts: `/tmp/t2.7-checked-report.md` (the rendered persisted report) and `/tmp/t2.7-checked-real.json`. The JSON records garage IDs and ownership, per-ID report counts, the recording path, the summary rows, the recently-cleared verdict and legs, and the capacity and health statuses. No VIN, no raw bytes. The reviewer reads both files and checks them against the list above.

## Risks / open questions

- Risk: E2E 1 repeats some literals from `report-view.test.ts`. That is deliberate. Here they are read from a report persisted and reloaded under a `checked` ID, which no existing test does. If the builder output changes, both tests have to be updated.
- Risk: no committed real recording follows the app's combined scan sequence, so the production action can only be replayed on the synthetic fixture. The owner run is the only evidence from the real app on the car.
- Open question 1 (owner): may PLAN T2.7 be ticked on this software evidence plus the owner's manual `checked` run? The manual run also needs to be arranged: combine it with the pending T2.6d phone checklist, or do it separately?
- Open question 2 (owner): should a saved report record the ownership tag at scan time? For example, a car checked before purchase and later switched to Mine. Recommendation: no. The report belongs to the entry (ADR-018), and switching ownership already keeps the reports. Adding a field would change the persisted report schema.
