# T0.9b: One-and-done captures (Run capture and Run codes report save their own files)

## Goal

The owner's requirement (2026-09-24, verbatim): "when doing these sorts of data captures i want it one and done. no start/export recording buttons. the run capture button should run what it needs to, and then export cleanly. similarly with run report."

When this is done, the Equinox console has two data buttons, **Run capture** and **Run codes report**. Each one runs its fixed command list, freezes the recording, and saves every output by itself:
- **Run capture** saves the raw recording (`<date>-phone-console[-N].jsonl`).
- **Run codes report** saves the raw recording first, then the report (`<date>-codes-report[-N].md`), and shows the report on screen.

Saving works in the same way for every run:
1. Each file is first written to the app's private documents directory, under `captures/`. That copy survives app restarts and is never overwritten, so a recording is never lost again the way the codes-scan recording was on 2026-09-24 (docs/task-runs/T0.9.md, "Equinox phone run").
2. Each file is then written into a folder the owner picks **once**, with the Android folder picker (Storage Access Framework). The app remembers the folder, and later runs write there with no dialog.
3. If no folder is available, the app falls back to the current share sheet, one file at a time: the recording first, then the report after the recording's sheet closes. That happens when the picker is cancelled or the folder write fails, for example because the permission was revoked or the folder was deleted.
4. The status line says what happened to each file: saved to the folder, share sheet opened, or `NOT SAVED` with the reason and where the private copy is.

The **Start/Stop recording**, **Export recording** and **Share report** buttons are removed. Manual **Send** stays as a debug tool. It uses its own session, which is not saved, and the button says so.

What a test sees:
- The existing fake-transport E2E tests (`codes-scan.test.ts`, `capture.test.ts`) run the real runner and console and then call the new `finishRun` with fake save targets.
- For a codes run, both files reach the folder, the recording first. Their contents equal `recording.toJsonl()` and the heading plus the committed T0.7 artifact block.
- An early stop or a disconnect still delivers the recording.
- Isolated tests cover the listed failure modes of the save path.

## Non-goals

- No native change: no `app.json` edit, no new dependency, no lockfile change, no new native module. Dev client `0f877dca` stays valid (Sources: the SAF picker is already in the installed native module).
- No change to the command lists, the stop rules, `ConsoleSession`, `runCapture`, `RecordingBuffer`, or the report text (`codesScan.ts` unchanged).
- No change to the file names or MIME types. The codes run's recording keeps the `phone-console` slug, and the owner still renames it to `-codes-scan` when copying it into `fixtures/recordings/` (T0.9 hardware step 5).
- No VIN request, and no redaction on the phone. Raw files stay local until `tools/spike/redact_vin.py` makes the committable copy (ADR-017).
- No saving of manual Send traffic. No automatic retry queue for files that failed to save. No pruning of the private `captures/` copies.
- No PDF (T0.9 Decision 1). No relay-mode work (T0.6b).
- No change to the T2.5b unplug notice line in `App.tsx` (Codex, uncommitted). It must be kept byte for byte.

## Interfaces

### `apps/mobile/src/runFiles.ts` (create; pure, no Expo or React Native import)

```ts
import type { ReportHeading } from "./codesScan.js";

export interface RunFile {
  slug: "phone-console" | "codes-report";
  extension: ".jsonl" | ".md";
  mimeType: "application/x-ndjson" | "text/markdown"; // unchanged from today's exportJsonl / shareReport
  content: string;
}

/** The phone's storage. App.tsx implements it with expo-file-system and expo-sharing; tests use a fake. */
export interface SaveTargets {
  /** Writes a new file under the app's private documents directory, captures/<date>-<slug>[-N]<ext>, never
   *  overwriting. Returns the name used. Throws on failure. */
  keep(file: RunFile): string;
  /** The remembered capture folder, or the folder picker when none is remembered (the choice is remembered).
   *  Rejects when the picker is cancelled or the folder cannot be opened. */
  folder(): Promise<{ write(name: string, file: RunFile): void }>;
  /** Forgets the remembered folder, so the next run shows the picker again. */
  forgetFolder(): void;
  /** Opens the share sheet for the private copy `name`; resolves when the sheet closes. */
  share(name: string, file: RunFile): Promise<void>;
}

export interface RunOutcome {
  /** The report markdown, for display; only for a codes run that produced one. */
  report?: string;
  /** One sentence per file, plus a leading report sentence for a codes run without a report. */
  status: string;
}

/** After a run's recording is frozen: keeps and delivers the recording, and for a codes run builds, keeps and
 *  delivers the report. Never throws. Every file ends in exactly one status sentence. */
export function finishRun(kind: "recording" | "codes", jsonl: string, heading: ReportHeading, targets: SaveTargets): Promise<RunOutcome>;
```

Rules for `finishRun`, in this order:
1. `keep(recording)`. The recording is kept before the report is built, so a report failure can never cost the recording.
2. For `"codes"`: `codesReportMarkdown(jsonl, heading)`.
   - If it throws, the report sentence is `Report error: <message>.`
   - If it returns `undefined`, the report sentence is `No module answered; no report.`
   - If it returns a string, `keep(report)` is called and the string becomes `report`.
3. Delivery covers every file that `keep` accepted, recording first. `await targets.folder()` is called once, and only if at least one file was kept.
   - For each file, when a folder is available, `folder.write(name, file)` is called.
   - If `folder()` rejected, or a write threw, that file and every later file go to `share(name, file)`. Each `share` is awaited before the next one starts. After a write throws, `forgetFolder()` is called once and no later file is written to the folder.
4. The status sentences come in this order: the report sentence, if any, and then one sentence per file.
   - `Saved <name> to the capture folder.`
   - `Share sheet opened for <name> (capture folder: <message>).` Here `<message>` is the `folder()` rejection or the write error.
   - `NOT SAVED <name>: <message>. A copy stays in app storage (captures/<name>).` This is used when `share` rejects.
   - `NOT SAVED <slug><extension>: <message>.` This is used when `keep` throws. Nothing else is tried for that file.

## Risks / open questions

### Risks

- **Largest risk: SAF naming by the document provider.** `createFile(name, mime)` passes the MIME type to the provider. Some providers append an extension they derive from the MIME type (`….md.txt`), or add ` (1)` when the name already exists. This could not be checked from the installed code, because it is in Android's provider, not in Expo. Hardware steps 2–3 check it.
  - If it happens with `application/x-ndjson` or `text/markdown`, the one-line follow-up is `application/octet-stream` for the folder write only. The share MIME stays unchanged.
  - The private `captures/` names are always exact.
- **The dev client may not contain the picker's native code.** The native code of expo-file-system 57.0.7 was in the lockfile when `0f877dca` was built (`45ca92c`), and the manifest query ships with the module. If the picker still does nothing on the phone, the run falls back to the share sheet, as in I2. Nothing is lost, and hardware step 2 shows it at once.
- **Picker or share sheet over a lost connection.** The save starts only after the run has ended, so no BLE traffic is pending while a system dialog is up. Disconnect stays enabled.
- **Leaving the console mid-run.** "Back to garage" unmounts the console. The cleanup closes the session, the run ends as `disconnected`, and `finishRun` still keeps the file privately and delivers it. The status is then not visible. This is acceptable for a debug screen, and it is not a regression.
- **Private copies accumulate.** A recording is roughly 5–50 KB, so a year of daily runs is a few MB. Deleting evidence automatically is worse (open question 4).
- **Coordination.**
  - T0.9 Decision 5 (manual export) and T0.9 hardware steps 3 and 5 are superseded by this spec. The orchestrator notes this in `docs/task-runs/T0.9.md`, and T0.9 Stage B then uses hardware step 8 here.
  - T0.6b's line "mutual exclusion with manual console recording" should now read "with the debug session and runs".
  - Codex T2.5b's `App.tsx` line must survive the rewrite (static check).
- **Size: M (small).** About 60 lines of `runFiles.ts`, a net −15 lines in `App.tsx`, about 40 lines of fake targets and about 150 lines of tests. One implementer session, no split.

### Open questions (recommendations; the orchestrator or owner decides)

1. **How files leave the phone.**
   - (a) SAF folder picked once, remembered, share sheet as the fallback. This is the design above, and it is JS-only with what is installed.
   - (b) Share sheet only, one sheet per file (a codes run shows two sheets in a row).
   - (c) One multi-file share. expo-sharing 57.0.21 has no such API (`shareAsync(url: string)`), so it would need a different native module and a rebuild.

   **Recommendation: (a).** It is the only one-step option without a rebuild.
2. **Share report button.** Remove it, as specified, or keep it to re-send the on-screen report (for example by email)? The saved `.md` can be shared from the Files app. **Recommendation: remove.** The owner asked for no export buttons.
3. **Manual Send.**
   - (a) A debug session that is not saved, as specified.
   - (b) Remove Send and the command field.
   - (c) Record Send traffic and save it on disconnect. Saves could then pop up at disconnect or car-off, and it interacts with runs and with T0.6b.

   **Recommendation: (a).** It keeps the console useful and the unknown-state rule intact, with the least code.
4. **Picker cancelled.** Ask again on every run until a folder is chosen (as specified), or remember "use the share sheet"? **Recommendation: ask again.** The owner wants the folder, and a cancel is more likely a mis-tap.
5. **Private copies.** Keep all of them (as specified), or delete each one after a successful folder write? **Recommendation: keep.** They are small, they are the recovery path, and deleting is a new failure mode.
