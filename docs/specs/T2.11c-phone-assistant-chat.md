# T2.11c: Phone assistant chat with saved, resumable chats (outline)

**Status: outline, not implementable yet.** The architect writes the full spec after the T2.11b Stage 1 review and the owner's answers below. Expected size: L. Planned split: **c1** is the single-question chat screen and on-device storage; **c2** is resume with history, which needs a new prompt version and its own small live check. c1 goes first. Decision 6 in T2.11b makes this screen required for T2.11 to close.

## Goal (c1 + c2)

In the garage, each car has an Assistant chat. Answers come from `askAssistant` over that car's saved checks, through the local Worker route from T2.11b. They are checked on the device, and every number shows which check it came from. Chats are saved on the phone per garage car and can be reopened and continued later: a chat about today's checks can be resumed a week later. When it is, the tools see the car's newer checks as well. Test-visible outcome: a mobile E2E that runs a saved chat, restarts the app, resumes the chat, and gets a checked answer that cites a newer check. The on-device paid tap is a phone check, run through the owner.

## Non-goals

- No upload of any kind. Chats never go into beta uploads (T2.9), relay recordings or exports.
- No notes in the assistant (Decision 4), no BYOK, and no model picker. The phone uses the flash pin unless the owner chooses otherwise after T2.11b's comparison.
- No chat summarisation by a model: its output could not be number-checked.
- No sync or backup across devices.

## Design points to settle in the full spec

**Storage.**
- One document per garage vehicle ID, through the existing `TextStore`/document-store pattern (`apps/mobile/src/garage/documentStore.ts`).
- Each chat holds: `id`, `createdAt`, `promptVersion`, `model`, and turns. A turn is `{ askedAt, question, kind, text, claims[{text, factIds}], citedFacts[{id, label, value, unit, checkRef}], reason? }`.
- `checkRef` is the local, stable ID of the saved report or charge log. It is never sent to the model.
- Stored answers are exactly what was shown after the check. On load, `checkFacts` is re-run over the stored claims and `citedFacts`. A turn that fails is shown as "could not be verified", never as its text.

**Deletion.**
- The user can delete a single chat.
- Chats are part of the car's data. `removeGarageVehicleWithReports` currently refuses removal while reports exist. Chats join that guard, and the future reviewed car-data delete removes them in the same step (open question 1).
- Garage-reset and uninstall paths clear them with the rest of the car's documents.

**Stable session IDs across a week.**
- T2.11a numbers sessions by list position. The phone must list sources oldest first, so earlier `sN` IDs stay the same when newer checks are added (the `sN` form allows up to 99). The alternative is a persisted per-car sequence number (open question 2).
- `list_sessions` gains a check-kind fact and a date fact such as `sessions/s3/checked-on`, so the model can say "your newer check".
- Dates are not eligible numeric values under the checker grammar. They appear only in digit-free prose or through the local citation display. This changes the tool facts and the prompt, so it is a new prompt version. It needs new synthetic replay cases and new saved replies, and T2.11a's v1 saved replies stay valid for v1.

**Where each number came from.**
- The UI, not the model, renders the source of every cited fact. The `sN/` prefix maps to `checkRef`, which maps to "Battery check, 29 Sep 2026" (or charge log, test-drive check under ADR-022 when it exists).
- A claim whose cited facts span two checks shows both.
- The model's prose is never trusted to name the check.

**Sources are rebuilt from recordings.** Per T2.11a Risks, typed reports restored from JSON carry unconstrained free text. Tool sources are rebuilt from the private recordings kept per check, or those strings are checked against the signalset first. The full spec picks one, and rebuilding is preferred.

**Fact field bounds.** The Worker's assistant route keeps C1's per-field bounds, so a fact value over 256 characters is `invalid-request` with no call (T2.11b §Interfaces, request checks). Long gate-reason facts from charge logs can exceed that. The full spec picks one: shorten them at the tool source, or change the bound together with the body-cap and reservation check.

**History sent on resume (c2).** The options, and their effect on cost:

| Option | Body growth per prior turn | Effect on reservation and cost | Number-check effect |
|---|---|---|---|
| Resend the full history | Unbounded, up to 16 claims × 512 chars each | Pushes toward the 32 KiB assistant body cap, then `invalid-request` | Prior text is context only |
| **Recommended: last K prior turns, question plus checked claim texts only, trimmed oldest first to fit a history byte budget** (K = 3, about 6 KB) | About 0.3–2 KB per turn | `R` grows with bytes, at most 22,119 µUSD per flash call at the cap. A typical resumed round adds a few hundred tokens, about US$0.0002 on flash | Unchanged: see below |
| Model-written summary of old turns | Small | An extra paid call per resume | Summary text cannot be checked, so rejected |

- The request gains `history: {question, answerText}[]` under prompt version `t2.11-v3` (`t2.11-v2` is the placeholder prompt from X-2026-09-29-summary-placeholders Stage 4). The Worker bounds it (count and bytes) and counts it inside `maxAssistantBodyBytes`.
- Cited fact IDs from earlier turns are never sent as citable facts.

**Number check across turns.**
- Each new answer is checked only against facts returned by tool calls made in that turn (T2.11a `receivedFacts`). Numbers in history are data, never evidence.
- A follow-up like "and what was it last week?" must fetch again, so a week-old number cannot pass unless the tool returns it again from the stored check it came from.
- The Worker's server-side check and the phone's check stay the same.
- Replay cases: a history containing a number, followed by an answer that repeats it without a fresh tool call, falls back to `unverified-answer`. A resumed chat after a new check has been added cites the new `sN`.

**Cost and consent.**
- Every turn draws on the one shared US$1 budget (T2.11b Decision 1). The screen shows remaining headroom from `/v1/status` and disables sending when `enabled` is false.
- A separate assistant consent screen uses the version approved in T2.11b Q4. Its wording adds "your question, recent questions and answers in this chat, and facts from several checks".
- Withdrawing consent keeps saved chats readable but stops new sends.

## Verification sketch

- **E2E (mobile tests).** Replay recordings into garage checks, run a chat against a harness Worker with synthetic replies, restart, resume, add a newer check, and ask again. The artifact is a JSON transcript of the screens' visible text, showing citations with check names and dates.
- **Adversarial cases.** A tampered stored answer is not shown. An injection in a note has no effect. A history number cannot be re-cited. A chat is deleted together with its car.
- **Phone.** One paid resumed chat on the owner's phone against the local Worker. Artifact: `/tmp/t2.11c-phone-chat.json`. NOT RUN until then; it is not a vehicle hardware-only exception.

## Open questions for the owner

1. Car deletion is blocked today while reports exist. Should chats follow the same rule until the reviewed car-data delete exists, with only single-chat delete available meanwhile?
2. Stable session IDs: oldest-first positional IDs (simplest; renumbers only if a check is ever deleted), or a persisted per-car sequence number?
3. History policy: last 3 turns, question plus checked answer text, about 6 KB. Accept, or resend more at higher cost?
4. The phone model after the comparison: keep flash, or offer the stronger model? That would need its own consent and cost display.
