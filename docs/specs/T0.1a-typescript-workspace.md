# T0.1a: TypeScript workspace scaffold

## Goal

Create the minimal pnpm workspace for the three planned TypeScript packages. The repository has strict ESM TypeScript, ESLint, and Vitest wiring; `pnpm test` and `pnpm -F obd-core test` succeed while honestly reporting that the empty packages contain no tests; and a committed lockfile makes the JavaScript toolchain reproducible. This is the first of two ordered T0.1 specs and does not complete T0.1 by itself.

## Non-goals

- Do not add OBD protocol code, constants, public library exports, fixtures, recordings, application code, or the mobile workspace.
- Do not add placeholder tests or claim test coverage for empty packages.
- Do not create the Python bridge or GitHub Actions workflow; T0.1b owns both and extends the root `pnpm check` command.
- Do not edit existing planning, workflow, agent, task-run, README, or decision files.
- Do not commit, push, publish packages, or mark T0.1 complete.

## Interfaces

The root command surface after this sub-spec is:

```text
pnpm check       # typecheck, lint, then run all workspace tests
pnpm typecheck   # strict no-emit TypeScript check over workspace sources
pnpm lint        # ESLint over the TypeScript workspace
pnpm test        # Vitest in each TypeScript package, allowing an empty suite
pnpm -F obd-core test
```

The workspace contains private ESM packages named exactly `obd-core`, `obd-diagnose`, and `obd-eval`. Each package is manifest-only in this sub-spec: it has no source entry point and exports nothing. `pnpm-workspace.yaml` includes `packages/*` and reserves `apps/*`; it must not include `tools/*`, because the HIL bridge is not a pnpm package.

The root manifest declares the existing package-manager version (`pnpm@9.15.9`) and the supported Node line (`>=22.13.0`). Use root scripts rather than duplicating TypeScript and lint configuration per empty package. `pnpm test` must execute the package test scripts recursively; each uses Vitest's explicit empty-suite option so output remains honest.

## Files

Eight implementation files, all created:

- `package.json` — private ESM workspace manifest, toolchain versions, root scripts, and development dependencies.
- `pnpm-workspace.yaml` — workspace globs for `packages/*` and the future `apps/*` directory.
- `tsconfig.json` — shared strict, no-emit ESM configuration; explicitly permits the initial zero-input scaffold while including future package TypeScript files.
- `eslint.config.js` — flat ESLint configuration for TypeScript under `packages/` and future `apps/`; ignore generated and dependency directories.
- `pnpm-lock.yaml` — lockfile generated by pnpm, never hand-authored.
- `packages/obd-core/package.json` — private ESM package manifest with the empty Vitest test script.
- `packages/obd-diagnose/package.json` — private ESM package manifest with the empty Vitest test script.
- `packages/obd-eval/package.json` — private ESM package manifest with the empty Vitest test script.

## Dependencies

All dependencies are root development dependencies. Add them with pnpm so both manifest ranges and exact lockfile resolutions come from registry metadata rather than guessed versions.

| Dependency | Reason |
|---|---|
| `typescript` | Strict ESM typechecking for all TypeScript packages. |
| `vitest` | Repository-standard test runner; empty suites are allowed only for this scaffold. |
| `eslint` | Required lint command and flat-config runtime. |
| `typescript-eslint` | TypeScript parser and recommended strict lint rules for ESLint. |

Do not add `zod` yet: T0.1 defines no package boundary or schema. Do not add formatters, coverage tools, Node type declarations, build tools, or package-local copies of the root tools unless a concrete configuration error proves one necessary; such an error is a spec conflict to report, not permission to expand dependencies silently.

## Verification

- [ ] `pnpm install` succeeds and generates `pnpm-lock.yaml` without modifying files outside this spec.
- [ ] `pnpm install --frozen-lockfile` succeeds immediately afterward.
- [ ] `pnpm typecheck` succeeds with strict mode and no emitted files.
- [ ] `pnpm lint` succeeds and uses the TypeScript-aware flat configuration.
- [ ] `pnpm test` succeeds; its output makes clear that all three package suites are empty.
- [ ] `pnpm -F obd-core test` succeeds with the same explicit empty-suite behavior.
- [ ] `pnpm check` succeeds locally.
- [ ] `git status --short` shows no edits to pre-existing setup files and only the eight implementation files from this spec plus the architect-authored specs and orchestrator-owned task record.

Network access to the package registry is an implementation prerequisite for the initial dependency resolution. If it is unavailable, dependency installation and all dependent checks are NOT RUN, not PASS.

## Risks / open questions

- The main risk is accidentally making an empty scaffold look tested. Vitest must say there are no tests, and this exception ends when a later task adds source behavior.
- The repository begins with every file untracked. A true clean-clone check is impossible before an initial commit exists; T0.1b defines the honest pre-commit substitute and the still-pending post-commit gate.
- No material design question is open. Package publishing, source entry points, and cross-package dependencies belong to later tasks.

## Decisions

- Split T0.1 into ordered T0.1a and T0.1b so each implementation stage touches fewer than ten files. T0.1b may begin only after T0.1a passes its local checks.
- Keep the three requested packages manifest-only. Do not create fake exports, placeholder source, or placeholder tests merely to satisfy tools.
- Resolve compatible tool versions through pnpm during implementation and commit the generated lockfile; do not manually guess exact transitive versions.
- Routine scope is authorized by the selected automatic architect → implementer → reviewer workflow. No user choice is required before implementation.
