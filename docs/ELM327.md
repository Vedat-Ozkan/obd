# ELM327, the Veepeak dongle, and vehicle quirks

The reference agents cite when writing protocol code (AGENTS.md rule 1). Sections marked **(verify)** are from the ELM327 datasheet or community reports and have not yet been confirmed on our hardware; T0.2 Equinox recordings replace them with recording line references where available. Once a recording exists, cite the recording, not this file. Chrysler and Elantra notes are optional bench context under ADR-015.

## Framing

- Commands are ASCII, terminated by `\r`. The ELM echoes the command unless `ATE0`.
- A response is complete when the `>` prompt arrives. Everything before it may arrive in any number of chunks. Never parse on newline alone.
- Lines end with `\r` (`ATL0`) or `\r\n` (`ATL1`). Use `ATL0` and split on `\r`.
- `ATS0` removes spaces between hex bytes. Use it; it shrinks BLE traffic. Parse hex in pairs.
- Only one command may be in flight. Sending a character while the ELM is busy aborts the current operation and returns `STOPPED`.

## Init sequence (generic 11-bit CAN)

```
ATZ        reset; wait for '>' (~1 s); prints "ELM327 v1.5" (clones lie about the version)
ATE0       echo off
ATL0       linefeeds off
ATS0       spaces off
ATH1       headers ON (we reassemble multi-frame ourselves and need the ECU id)
ATSP0      auto protocol (or ATSP6 for ISO 15765-4 CAN 11/500 to skip searching)
ATDPN      describe protocol number; "A6" = auto-detected 6
ATRV       battery voltage, e.g. "12.6V"
0100       first real request; may return "SEARCHING..." first on ATSP0
```

Optional, tolerate `?`: `ATAT1` (adaptive timing), `ATST 32` (timeout 50×4 ms = 200 ms), `ATCAF1` (auto formatting, default on).

## Responses and how to handle each

| Response | Meaning | Handling |
|---|---|---|
| `SEARCHING...` | auto protocol search in progress | wait; data or `UNABLE TO CONNECT` follows before `>` |
| `NO DATA` | no ECU replied within timeout | valid outcome; PID unsupported or ECU asleep; not an error at the session level |
| `UNABLE TO CONNECT` | no protocol found | ignition off, wrong protocol, or dongle not seated; surface to user |
| `CAN ERROR` | bus error | retry once after 500 ms; then surface |
| `BUS INIT: ...ERROR` | K-line init failed | not expected on our cars |
| `BUFFER FULL` | ELM's 256-byte buffer overflowed | response truncated; reduce with `ATS0`, filter with `ATCRA`, or use flow control |
| `STOPPED` | a byte was sent mid-operation | our bug: the queue let two commands overlap |
| `?` | unrecognized AT command | for optional init commands: continue; for required: fail init |
| `LV RESET` | low-voltage reset | dongle browned out during crank; re-init |
| `DATA ERROR`, `<DATA ERROR` | checksum problem | retry once |
| `ERR94` etc. | fatal CAN errors on some firmware | surface |
| `OK` | AT command accepted | |

## Multi-frame responses (ISO 15765-2 / ISO-TP) with `ATH1`

With headers on, each CAN frame is one line: `7E8 10 14 49 02 01 31 43 34` then `7E8 21 ...`, `7E8 22 ...`. First nibble of the PCI byte: `0` single frame (low nibble = length), `1` first frame (next 12 bits = total length), `2` consecutive frame (low nibble = sequence 0–F wrapping), `3` flow control. The ELM sends flow control automatically for standard addressing. Reassemble per ECU header; multiple ECUs may answer the same request (e.g. `7E8` engine and `7E9` transmission on `0100`).

With `ATH0` the ELM instead prints a length line (`014`) and `0:`, `1:` prefixed lines. We do not use that mode; it hides which ECU answered.

## J1979 conventions

What OBDb's signalset does not encode, for `src/obd/`. OBDb `bix` counts from the MSB of byte A: bix 0 = A7, bix 8 = B7, bix 16 = C7, bix 24 = D7.

- **Positive response.** Service + 0x40, then the PID or infotype echoed (`41 <pid>`, `49 <infotype>`), then the data. Source: Wiki §CAN bus format / Response; spike line 32 (`41 00`), line 73 (`49 02`), lines 107–113 (`43`), line 116 (`47`), line 123 (`4A`).
- **Negative response.** `7F <service> <code>`; decoders report the code byte only. Source: T0.4 `Frame.negative`; spike line 124.
- **Supported-PID bitmaps.** PIDs 00, 20, 40, 60, 80, A0, C0 each answer 4 bytes. The MSB of byte A flags `base+1`, the LSB of byte D flags `base+0x20`; that last bit says the next bitmap PID is supported. Source: Wiki §Service 01 PID 00; PLAN T0.5 row; consistent with spike lines 32–61 (exactly the modules whose `0100` LSB is set answered `0120`).
- **PID 01 layout.** A7 = MIL, A6–A0 = count of stored emission DTCs. B3 = ignition type (0 spark, 1 compression). B0–B2 = misfire, fuel system, and comprehensive-component monitors available; B4–B6 = the same three incomplete. Byte C = the ignition-specific monitors available, byte D = the same monitors incomplete, bit for bit. Source: Wiki §Service 01 PID 01; bit positions equal OBDb `01/01` bix 0 (MIL), 1–7 (`DTC_CNT`), 9–15 (B), 12 (`CIM_SUP`), 16–31 (C and D).
- **Completeness polarity.** In bytes B and D, for PIDs 01 and 41, a set bit means the monitor is not complete; 0 means complete. Source: Wiki §PID 01; OBDb `01/41` `*_CMPL` (`yesno`) and OBDb `01/01` B-byte `*_RDY` (`yesno`). **Conflict:** OBDb `01/01` D-byte `EGR_RDY`…`CAT_RDY` (bix 24–31) are `noyes` (1 = ready). Resolved for Wiki; the upstream OBDb report is tracked in the T0.5 task record (ADR-010).
- **Spark-ignition C/D map, bit 0 to 7.** Catalyst, heated catalyst, evaporative system, secondary air, gasoline particulate filter, O2 sensor, O2 sensor heater, EGR/VVT. Source: Wiki (spark table); order matches OBDb `01/01` bix 23 down to 16. **Conflict:** at bit 4 OBDb says A/C refrigerant (`ACRF_SUP`/`ACRF_RDY`); Wiki (rev 1374011962) says bit 4 was reserved before it was defined as the gasoline particulate filter, and calls the A/C-refrigerant reading a misconception. Resolved for Wiki (`gpf`). The Equinox sets no C/D bits, so no recording decides it.
- **Compression-ignition C/D map, bit 0 to 7.** NMHC catalyst, NOx/SCR aftertreatment, reserved, boost pressure, reserved, exhaust gas sensor, PM filter, EGR/VVT. Source: Wiki (compression table) only; OBDb has no compression layout. Synthetic tests only.
- **PID 41.** Same B/C/D layout as PID 01, with "available" read as "enabled this drive cycle"; byte A is always 0 and is not read. Source: Wiki §PID 41; OBDb `01/41` (`*_ENA`, `*_CMPL`, same bix).
- **Equinox readiness.** Every answering module sends `41 01 00 04 00 00`: MIL off, 0 DTCs, spark layout, only the comprehensive-component monitor, complete. Source: spike lines 63–70; spike-2 lines 63–70.
- **DTC lists (Mode 03/07/0A on CAN).** `43`/`47`/`4A`, a count byte, then count × 2 bytes. Source: §Standard modes above; spike lines 107–127 (`43 00`, `47 00`, `4A 00`).
- **DTC 2-byte encoding.** Bits A7–A6 select P/C/B/U (0–3), A5–A4 the first digit (0–3), then A3–A0, B7–B4, B3–B0 as three hex digits; `00 00` is padding. Source: §Mode 01 footer above ("DTC decoding (CAN)"); Wiki §Service 03 (example `C1 58` → `U0158`).
- **VIN (`0902`).** `49 02 01` then 17 ASCII bytes. Source: ADR-017; §Standard modes above; spike lines 73–82. Committed recordings carry `000000` at positions 12–17 (ADR-017; `tools/spike/redact_vin.py` `MASK`).
- **VIN check digit.** Characters are digits and the letters 49 CFR 565.15(c) Table III assigns a value to (every letter except I, O, Q). Each character's value (digits as themselves, letters per Table III) is multiplied by its position weight (Table IV; position 9 weighs 0), the products are summed, and the remainder of the sum divided by 11 gives position 9: 0–9 as the digit, 10 as `X` (Table V). Worked example (Table VI): `1G4AH59H45G118341`, check digit `4`. Source: 49 CFR 565.15(c) Tables III–VI (eCFR `title-49/part-565/section-565.15`, public domain). The rule binds US-market vehicles only. Values copied from the regulation (US government work, public domain, 17 U.S.C. §105), retrieved 2026-09-23 from https://www.ecfr.gov/current/title-49/subtitle-B/chapter-V/part-565/subpart-B/section-565.15 (via the eCFR versioner API, `title-49.xml?part=565&section=565.15`, content up to date as of 2026-09-22):
  - Table III, assigned values: A=1, B=2, C=3, D=4, E=5, F=6, G=7, H=8, J=1, K=2, L=3, M=4, N=5, P=7, R=9, S=2, T=3, U=4, V=5, W=6, X=7, Y=8, Z=9. Digits keep their own value (565.15(c)(1)).
  - Table IV, weight factor by position 1–17: 8, 7, 6, 5, 4, 3, 2, 10, 0, 9, 8, 7, 6, 5, 4, 3, 2. Table IV lists position 9 as "(check digit)"; Table VI uses weight 0 there.
  - Check: the Table VI products sum to 411; 411 mod 11 = 4.
- **CAL IDs (`0904`).** `49 04 <n>` then n blocks of 16 ASCII bytes, NUL padded. Source: Wiki §Service 09 PID 04 (16 bytes each, NUL padding); the count byte by analogy with `0902`'s `01` (ADR-017). Local discovery recordings (gitignored, not CI evidence) agree on count against length.
- **ECU name (`090A`).** `49 0A 01` then 20 ASCII bytes, NUL padded. Source: Wiki §Service 09 PID 0A; spike lines 85–90 (module 45, 23-byte message).
- **Mode 02 reply layout.** Not sourced. Only the request form `02 <pid> 00` (§Standard modes) is known; no recording has a positive `42` reply yet (T0.5 Stage C prerequisite).

## Write safety

Why `packages/obd-core/src/elm/guard.ts` allows what it allows. Sources: Elm Electronics ELM327 datasheet `ELM327DSJ` (firmware v2.1; "DS", with page; URL and SHA-256 in `docs/specs/X-2026-09-23-write-safety.md`; copyrighted, paraphrased, not checked in); Wikipedia "Unified Diagnostic Services" `oldid=1334951853` ("Wiki-UDS", **secondary**, ISO 14229-1 is paywalled); Wikipedia "OBD-II PIDs" `oldid=1374011962` ("Wiki", as in §J1979 conventions) §Services / Modes. The datasheet describes a genuine ELM327; clones may differ, so where a clone matters a recording is cited.

**Input rules.**
- A bare CR repeats the previous command, AT or OBD (DS p.9, p.12). The ELM ignores spaces and control characters and is case-insensitive (DS p.9), so a whitespace-only command is a bare CR. The guard compares normalized forms and refuses empty ones.
- With CAN auto formatting on (CAF1, the default), the ELM builds the PCI byte on send, even with headers on. With CAF0 the caller's first byte becomes the PCI, so `0104` would go out as a single frame carrying service `04` (DS pp.13–14, p.44). Our Veepeak sends with CAF1 after `ATZ`: spike line 32. `ATCAF0`, `ATCAF1` and all `ATPP` commands are refused, because PP 24 sets the power-on CAF default (DS p.23, p.72).
- Headers set with `ATSH`/`ATFCSH` persist until `ATD`/`ATWS`/`ATZ`, and on 11-bit CAN only their rightmost 11 bits are used (DS p.25). So a 29-bit header followed by an 11-bit protocol would send on an arbitrary 11-bit ID. The sequence rule allows header commands only after `ATSP7` was answered `OK`. After a header is set, it allows no protocol other than 7 until `ATZ`.
- Flow control mode 1 sends user-defined FC frames (DS p.17, p.60). The FC data is pinned to `30 00 00` (spike line 140) and the FC header to `18DA<tt>F1`.
- A character that arrives while the ELM is busy interrupts it and is discarded (DS p.9, p.48). The ELM then prints `STOPPED` (§Responses). A write into a busy ELM can therefore lose its first character and turn an allowed request into a refused one: `014FFFFFF1` would run as `14 FF FF FF`. So after a timeout or a failed write, the session writes nothing, `ATZ` from `init()` included, until a `>` shows the ELM is idle. If no `>` arrives within the resync window, the command is rejected as a timeout and the session stays in that state until a `>` arrives.
- An `ATZ` answered with an error (`STOPPED`, `?`) resets nothing: the busy ELM discarded it (DS p.9, p.48; §Responses, `STOPPED` row), so headers and protocol are treated as unchanged.
- A relay connection cannot see a late `>`. So `tools/relay` accepts only `ATI` or `ATZ` on a new phone connection, and after any exchange that did not end in a `>`-terminated reply without an error line, until one gets such a reply. If the ELM was busy, the dropped `A` leaves `TI` or `TZ`, which it answers with `?` and does not act on (DS pp.8–9); the datasheet does not bound how many characters are dropped, and neither command leaves hex behind.

**Services.** First byte of an OBD request, CAF1 in effect. Allowed: `01 02 03 06 07 09 0A 22`. Everything else is refused, including IDs not listed here. Each allowed service has exactly one request length, in hex characters with spaces removed: `01` 4, `02` 6, `03` 2, `06` 4, `07` 2, `09` 4, `0A` 2, `22` 6. Any other length is refused, so a request has no spare payload that could become a refused service if its first character were dropped (DS p.9, p.48). Multi-PID requests are not sent.

## BLE specifics (Veepeak OBDCheck BLE)

- GATT service `FFF0` (`0000fff0-0000-1000-8000-00805f9b34fb`), characteristics `FFF1` and `FFF2`. Reports disagree on which is write vs notify; **discover by characteristic properties** (`write`/`writeWithoutResponse` vs `notify`) at connect time. **(verify in T0.2)**
- Default MTU 23 → 20 data bytes. Request a larger MTU on Android (`requestMTU(185)` or so) and still chunk; do not assume it was granted.
- Write commands as `cmd + "\r"`, chunked; wait for `>` in the notification stream before the next command.
- Do not pair the dongle in Android Bluetooth settings; connect directly from the app. Pairing in settings makes it invisible to BLE scans on some phones.
- The dongle stays powered from the OBD port with ignition off. On the EV this is a 12 V drain concern; on the ICE cars it is a slow one.

## Per-car notes (to be replaced by spike recordings)

**2013 Chrysler 200:** ISO 15765-4 CAN 11-bit 500k. Engine ECU `7E0`/`7E8`, transmission `7E1`/`7E9`. Chrysler ECUs of this era generally answer Mode 06 over CAN. **(verify)**

**2019 Hyundai Elantra:** ISO 15765-4 CAN 11-bit 500k. Same standard headers. Mode 06 support varies. **(verify)**

**2024 Chevrolet Equinox EV:** Standard Mode 01 will answer from at most one or two modules with a short PID list; `0902` VIN expected to work; Mode 03 may return nothing meaningful (no emissions modules). Module diagnostics use **29-bit CAN** (`ATSP7`, ISO 15765-4 29/500). OBDb notation `DA1D` means tester `F1` → module `1D` with 29-bit header `18DA1DF1`, response `18DAF11D`. ELM setup pattern **(verify)**:

```
ATSP7
ATCP 18          CAN priority byte for 29-bit headers
ATSH DA1DF1      header: DA <target> <source F1>
ATCRA 18DAF11D   receive only the reply from module 1D
ATFCSH 18DA1DF1  flow-control header for multi-frame replies
ATFCSD 300000
ATFCSM 1
22 33E5          Mode 22, DID 33E5 → expect "62 33E5 ..."
```

The OBDb signalset lists `DA1D` DID `33E5` (all years) and `DACB` DIDs `27C6`, `2AF5`, `2B43` (filtered 2025+). Upstream test data (commit `15ee122`, `tests/test_cases/2024/command_support.yaml`) reports the reverse on a 2024: the three `DACB` DIDs answered and `33E5` did not; `33E5` scales to at most 25.5 V, so it is not the HV pack voltage. Unverified on our car until the T0.2 recording. What module `1D` and `CB` are on this platform is not documented in the signalset; the spike records what answers.

## Clone quirks seen in the wild

- Reports `v1.5`, which the real ELM never shipped; treat version strings as decoration.
- Some ignore `ATAT`, `ATST`, `ATFC*`; respond `?`. Tolerate on optional commands.
- Some drop the last line before `>` under load; retry once on malformed data.
- First command after `ATZ` may return garbage bytes; discard until the first `>`.
- Slower than a genuine ELM. Budget 100–300 ms per Mode 01 request; batching PIDs (`010C0D0405`, up to six per request on CAN) helps a lot for the drive logger. **(verify per car: not all ECUs honor multi-PID requests)**
