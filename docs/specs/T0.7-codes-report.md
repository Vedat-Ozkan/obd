# T0.7: write-safety follow-ups, then the codes report and the "recently cleared" heuristic

## Goal

Two stages, each with its own implementer session and review gate.

- **Stage A: write-safety follow-ups.** These are the three owner-accepted findings from `docs/task-runs/X-2026-09-23-write-safety.md` round 3.
  - The session guard refuses Mode `06`. Its request length has no source, and nothing sends it.
  - The guard allows Mode `02` only as `02 <pid> 00`.
  - The app console refuses `06` as well.
  - `docs/discovery-2026-09.md` warns that a full `pnpm replay` of the local discovery file takes about 1.5 h.
  - `docs/ELM327.md` §Write safety states the real residual of the length rule. The old claim was "no spare payload". This doc edit is the **last step of the whole task**. It waits until the T0.6 worktree is merged into `main` (see Order).
- **Stage B: codes report.** It lives in `obd-core` and is pure: it imports only type definitions from `elm/` and `obd/`. `buildCodesReport(exchanges)` turns the responses of one scan into a typed `CodesReport`. It holds, per module:
  - stored, pending and permanent DTCs;
  - MIL and readiness;
  - PIDs 21/30/31/4D/4E, each read, unsupported, failed, or not read;
  - the freeze frame.

  The report also holds the "recently cleared" verdict. `renderCodesReport(report)` renders it as a markdown section from templates. This is the section T0.9 shares and T2.6/T2.7 embed.

What a test sees when this is done:

- `pnpm codes-report <recording…>` replays each recording through `Elm327Session` and prints the rendered reports. Its output for the three tracked Equinox recordings and four new synthetic fixtures equals the committed artifact `packages/obd-core/test/codes-reports.md`.
- On all three Equinox recordings the verdict is **unknown**, never "not indicated":
  - No tracked recording reads PID 30 or 31.
  - PID 4E is unsupported by every module (`0140` bitmaps, spike L52–61).
  - The one readiness monitor the Equinox has, `components`, is complete.
- On the phone recording, module `17` shows "no freeze frame stored" (PID 02 = `00 00`, L42).
- Each synthetic fixture drives one verdict branch that the recordings lack: indicated, indicated-strong, not indicated, and unknown-because-evidence-conflicts.
- After Stage A, `allowedCommand("0600")` and `allowedCommand("020201")` are `undefined`. Every tracked and synthetic replay output is byte-identical to before.

## Non-goals

- **No request orchestration.** Nothing here decides which commands to send, walks bitmaps over the wire, or talks to BLE. T0.9 does. The builder takes exchanges that already happened.
- **No Mode 04 path.** T0.7 adds no clear. The §Write safety table cell "04 … T0.7 adds a confirmed path" is stale. A2 corrects it (Interfaces, Stage A).
- **No change to `Elm327Session` behaviour.** In particular, this task does not add a rule that blocks OBD requests on a fresh session before `init()` (Q7 proposes a separate task).
- **No alignment of the app console allowlist with `guard.ts`** beyond dropping `06`. The console still accepts any even-length hex request for its listed services. That is noted in Risks.
- **No VIN, CAL ID or ECU name in the report** (Q6). `0902`/`0904`/`090A` exchanges are ignored.
- **No PID 41, 1C, 42, 46, 5B, A6 or B2 in the report.** Those are drive-cycle or battery context and belong to T2.x. No Mode 02 bitmaps are shown either.
- **No zod schema for `CodesReport`.** The T0.5 spec left the schema to T0.7. Nothing parses a serialized report yet, so the schema goes to the first consumer that does (T2.9 export or T2.10 LLM input). This keeps the package free of a schema nobody validates against.
- **No change to the `.replay-label.json` schema** (T0.10b). The expected verdict of each synthetic fixture lives in the T0.7 E2E test and the rendered artifact. The label's `notes` names the branch.
- **No `package.json` `exports` change in `obd-core`.** T0.9 adds `./report` when the app first imports it.
- **No NRC interpretation.** A negative response is rendered with its code byte only, as in T0.5.
- **No hardware session, and no vehicle code clear** (PLAN T0.7 verify; `docs/EVAL.md` §Faults and safety).

### Stage B2: `packages/obd-core/src/report/codes.ts` (create)

```ts
import type { ElmResponse } from "../elm/session.js";
import type { Monitor } from "../obd/readiness.js";
import type { PidReading, Unit } from "../obd/j1979.js";
import type { DecodeFailure } from "../obd/response.js";

/** One command sent during a scan and its response, in send order. T0.9 builds these; replay builds them in tests. */
export interface CodesExchange { command: string; response: ElmResponse }

export type Tri = "yes" | "no" | "unknown";

type Failed = { status: "failed"; reason: DecodeFailure["reason"]; code?: number };
type NotRead = { status: "not-read" };      // not requested, or requested and this module sent no frame
type Unsupported = { status: "unsupported" }; // the module's bitmap covering this PID was read and does not flag it

export type DtcRead = { status: "read"; dtcs: string[] } | Failed | NotRead;
export type PidValue = { status: "read"; value: number; unit: Unit } | Unsupported | Failed | NotRead;
export type ReadinessRead = { status: "read"; mil: boolean; dtcCount: number; monitors: Monitor[] } | Unsupported | Failed | NotRead;
export type FreezeFrame =
  | { status: "none-stored" }                                   // PID 02 = 00 00: nothing else from Mode 02 is shown
  | { status: "stored"; dtc: string; readings: PidReading[] }   // readings: frame-0 MODE01_PIDS values, ascending PID
  | Failed | NotRead;

/** PIDs the codes report shows: MIL distance/time and the three "since codes cleared" counters. */
export type CodesPid = "21" | "30" | "31" | "4D" | "4E";

export interface ModuleCodes {
  ecu: string;                      // Frame.ecu: "17", "7E8"
  stored: DtcRead;                  // Mode 03
  pending: DtcRead;                 // Mode 07
  permanent: DtcRead;               // Mode 0A
  readiness: ReadinessRead;         // PID 01
  pids: Record<CodesPid, PidValue>;
  freezeFrame: FreezeFrame;         // Mode 02 frame 0
}

export interface ClearLegs {
  noStoredDtcs: Tri;
  monitorsIncomplete: Tri;
  countersLow: Tri;
  permanentDtcs: Tri;
}

export interface RecentlyCleared {
  verdict: "indicated" | "not-indicated" | "unknown";
  /** The permanent-DTC path fired (docs/ELM327.md §Standard modes, row 0A). */
  strong: boolean;
  legs: ClearLegs;
}

export interface CodesReport {
  modules: ModuleCodes[];           // ascending by ecu
  recentlyCleared: RecentlyCleared;
}

/** POLICY values (Decisions, Q1), not from a standard: a counter below its value is "low". */
export const LOW_COUNTER: Readonly<Record<"30" | "31" | "4E", number>>;

export function buildCodesReport(exchanges: readonly CodesExchange[]): CodesReport;
/** The verdict from the four legs; exported for the one isolated test (Verification, failure 10). */
export function recentlyCleared(legs: ClearLegs): RecentlyCleared;
```

**Builder rules.**

- **Recognized commands.** The command is normalized (spaces removed, uppercase). The builder recognizes:
  - `0100`, `0120`, `0140`: bitmaps, via `decodeSupported`;
  - `0101`: `decodeReadiness`;
  - `0121`, `0130`, `0131`, `014D`, `014E`: `decodePid`;
  - `03`, `07`, `0A`: `decodeDtcList`;
  - `020200`: `decodeFreezeDtc` with frame 0;
  - `02<pid>00` for a pid in `MODE01_PIDS`: `decodeFreezePid`.

  Everything else is ignored, including AT, `09xx`, `22xx`, and the Mode 02 bitmaps. If a command occurs twice, the later exchange replaces the earlier one.
- **Modules.** Every ECU that sent a frame in a recognized exchange, sorted ascending. Only `response.frames` are used, whatever `response.kind` is; dropped frames are ignored. If one ECU sent several frames for one command, the first frame is used.
- **Status per field.** A decoder success gives `read`, `none-stored` or `stored`. A decoder failure gives `failed`, carrying the reason and the NRC code. No frame from that ECU gives `not-read`, except in this case: a Mode 01 PID (01, 21, 30, 31, 4D, 4E) whose covering bitmap was decoded for that ECU without flagging it is `unsupported`. The covering bitmap is `0100` for 01, `0120` for 21/30/31, and `0140` for 4D/4E. A flagged PID that was never answered is `not-read`, never a value (T0.5 Risks: bitmaps promise more than modules deliver).
- **Freeze frame.** `stored` only when PID 02 decodes to a DTC. Its `readings` are that ECU's `02<pid>00` values. With `none-stored`, `failed` or `not-read` for PID 02, no Mode 02 value is carried into the report, even if one was read (T0.5 Stage C decision).
- **Legs**, across all modules:
  - `noStoredDtcs`:
    - `no` if any module's `stored` lists a DTC;
    - otherwise `unknown` if any module's `stored` is `failed`;
    - otherwise `yes` if at least one is `read`;
    - otherwise `unknown`.
  - `permanentDtcs`: `yes` if any `permanent` lists a DTC. Otherwise `no` if at least one is `read`. Otherwise `unknown`. A negative `0A` reply is `failed` and does not count as "none".
  - `monitorsIncomplete`: over modules whose `readiness` is `read`. `yes` if any available monitor has `complete: false`. Otherwise `no` if at least one such module lists at least one monitor. Otherwise `unknown`. Monitors that are not available are absent from `Readiness.monitors` and are never read as incomplete (T0.5 Risks, "Readiness on EVs").
  - `countersLow`: over every `read` value of PIDs 30/31/4E in every module. `yes` if any value is `< LOW_COUNTER[pid]`. Otherwise `no` if at least one was read. Otherwise `unknown`.
- **Verdict** (`recentlyCleared`):
  - `standard = noStoredDtcs==="yes" && monitorsIncomplete==="yes" && countersLow==="yes"` (PLAN T0.7 row).
  - `strong = noStoredDtcs==="yes" && permanentDtcs==="yes" && monitorsIncomplete==="yes"` (`docs/ELM327.md` §Standard modes, row 0A: "strong … signal when present with monitors incomplete").
  - `verdict = standard || strong ? "indicated" : countersLow === "no" ? "not-indicated" : "unknown"` (policy, Q2).
  - Only a counter read at or above its policy value can say "not indicated", because only the counters measure time or distance since a clear. A missing, unsupported or unread counter, or evidence that disagrees, gives `unknown`, never a clean result.

The template follows. The verdict sentences are exact. The per-field words are exact. Layout details such as blank lines are the implementer's, but they are fixed once the artifact is committed.

```
## Diagnostic codes

Observed data from <n> modules: <ecu, …>. Each value is shown as the module reported it.

### Recently cleared: <indicated | not indicated | unknown>

<verdict sentence>

| Check | Result |
|---|---|
| No stored codes (Mode 03) | <yes|no|unknown> |
| A readiness monitor incomplete (PID 01) | <…> |
| A counter since codes cleared below policy (PIDs 30, 31, 4E) | <…> |
| Permanent codes present (Mode 0A) | <…> |

Policy thresholds, set by this project and not taken from a standard: warm-ups below <v30>, distance below <v31> km, time below <v4E> min.

### Module <ecu>

- Stored codes (Mode 03): <codes | none | …>
- Pending codes (Mode 07): …
- Permanent codes (Mode 0A): …
- MIL (PID 01): <on|off>; stored emission codes: <n>
- Readiness monitors (PID 01): <id complete|incomplete, …> | none available
- Warm-ups since codes cleared (PID 30): <n>
- Distance since codes cleared (PID 31): <n> km
- Time since codes cleared (PID 4E): <n> min
- Distance with MIL on (PID 21): <n> km
- Time with MIL on (PID 4D): <n> min
- Freeze frame (Mode 02): none stored | stored for <DTC>[; <id> <value> <unit>, …]
```

- **Status words.** `not-read` → "not read". `unsupported` → "not supported". A negative `failed` → "not answered (negative response <hh>)". Any other `failed` → "unreadable reply (<reason>)". For readiness, `not-read`, `unsupported` and `failed` replace both the MIL line and the monitors line with one "Readiness (PID 01): <status word>" line.
- **Verdict sentences** (exact):
  - Indicated, strong: "Codes appear to have been cleared recently (strong signal): permanent codes are present, no stored codes are, and a readiness monitor is incomplete. A scan tool cannot clear permanent codes."
  - Indicated, not strong: "Codes appear to have been cleared recently: no stored codes, a readiness monitor incomplete, and a counter since codes cleared below the policy threshold."
  - Not indicated: "No sign of a recent clear: every counter since codes cleared that was read is at or above the policy threshold."
  - Unknown, `countersLow` `unknown`: "Unknown: no counter since codes cleared (PID 30, 31 or 4E) was read, so the data cannot show when codes were last cleared."
  - Unknown otherwise: "Unknown: the checks disagree, so the data does not show whether codes were cleared recently."
- **Numbers.** `String(Math.round(v * 1000) / 1000)`, as `pnpm replay` does. Freeze readings print `<id> <value> <unit>`, as the replay does. No other number appears. The word "clean" never appears.

## Risks

- **Largest risk: the verdict reads as a health or honesty claim it cannot support.** On the Equinox, the readiness leg carries almost nothing: one always-complete monitor. The strongest evidence, PID 31, is not in any tracked recording. That is why only counters can produce "not indicated". The rendered text always shows the legs, the raw values, and the policy thresholds.
- **The length-rule residual is wider than the round-3 finding.** The 4-character forms are affected too. `0140`, which the codes flow sends, leaves `14` (a UDS clear service ID, as one byte) if its first character is dropped. The resync rule prevents that in the session. The first write of a fresh session that skips `init()` is uncovered (Q7). This is unverified on hardware, and must not be tested on a car.
- **Doc lag between A1 and A2.** The code refuses what §Write safety still lists, which is the safe direction. If T0.6 stays unmerged for long, A2 waits and T0.7 stays open.
- **T0.6 relay's separate `06` refusal becomes redundant** once the guard refuses `06`. T0.6 may keep or drop it; this spec does not touch the worktree.
- **The app console still accepts any even-length request** for its services, for example `020201` or `0100FF`. Aligning it with `allowedCommand` is a separate follow-up. Only `06` is removed here.
- **Multi-module disagreement.** One module can read low while another reads high (local discovery: `0130` gave 149 from 17 and 150 from 28). `countersLow` is `yes` if any value is low. The report shows every module's value.

## Open questions

1. **"Low" thresholds (policy).** No checked-in source defines "recently". Options:
   - (a) Owner-set policy values, stated in the report.
   - (b) No thresholds: the verdict fires only on the counter at zero.

   **Recommendation: (a)**, with the owner confirming or replacing these proposed values: warm-ups `< 10`, distance `< 100` km, time `< 600` min. Rationale: they are meant to catch a clear within roughly the last few days of ordinary use before a sale. They are round numbers chosen for that intent, not measured and not from a standard. Revisit them with beta recordings. (b) misses a clear followed by one drive to the meeting.
2. **When may the verdict say "not indicated"?**
   - (a) As designed: only when a counter was read at or above policy. Otherwise "unknown".
   - (b) The PLAN AND rule: "not indicated" whenever any leg is `no`. On the Equinox this yields "not indicated" from the components monitor alone, even with no counter read. That is the "clean" result the task forbids.

   **Recommendation: (a).**
3. **Strong path.** `docs/ELM327.md` row 0A makes permanent codes strong "with monitors incomplete".
   - (a) Follow it. Permanent codes with no stored codes but complete or unknown monitors give "unknown", and the table shows "Permanent codes present: yes".
   - (b) Permanent codes with no stored codes are enough on their own.

   **Recommendation: (a)**, because (b) has no checked-in source.
4. **Mode 06.**
   - (a) Refuse it in the guard and in the app console, until a recording shows a request.
   - (b) Source the length first. That needs a Mode 06 capture on a car that answers it; the Equinox is untested.

   **Recommendation: (a).** Nothing uses Mode 06, and the relay already refuses it.
5. **Pin Mode 02 to frame `00`.** **Recommendation: yes.** Frame 0 is the only frame recorded. The pin narrows the second byte of a shifted request, not its service. So it is hygiene, not a fix for the residual.
6. **VIN in the codes report.** **Recommendation: leave it out.** The report is embedded in reports that may go to an LLM (T2.10: "VIN never sent"). T2.7 decides whether the shareable pre-purchase report shows it.
7. **Fresh-session residual in `Elm327Session`.** A caller that sends an OBD request before `init()` writes into a possibly busy ELM. **Recommendation:** a separate `X-` task mirroring the T0.6 relay rule (AT only until a `>`-terminated reply).
