## Goal

A beta tester sees one plain-language consent screen with a single "Share my data to improve the app" switch, default OFF. The switch records a consent version. Once it is on, every run the app already saves also gets queued for upload. That covers Run capture, Run codes report, battery diagnosis and, once T2.4 B2 exists, the charge log. Before a file is queued, the phone scrubs it:
- The VIN serial is masked, with the `redact_vin.py` rules ported to TS and checked against the Python script.
- Identification DIDs `F180`–`F1FF` are masked.
- Mode 09 infotypes with no sourced layout are masked.
- The odometer is masked.
- Any note the user typed is removed.

The only date left is the month. The file gets a final provenance meta line: consent version, app version, month, the garage entry's catalog model/year, and random tester and vehicle keys. The queue uploads in parts to a small Cloudflare Worker in front of an R2 bucket. If an upload fails, the file stays queued and is retried when the app next runs or comes to the foreground. The tester does nothing more.

A Garage section has:
- a switch to stop sharing;
- a beta ID, for deletion requests if the app is gone;
- **Delete my data**, which removes every uploaded object and leaves a tombstone.

On the owner's side, `pnpm beta:intake` does four things:
- It downloads complete files and re-runs the scrubber. A file that changes on re-scrub is refused.
- It writes each accepted file as a gitignored local original under `fixtures/recordings/<model>-beta-<key>/` and runs `redact_vin.py` on it.
- It deletes local copies for tombstoned testers.
- It deletes local copies past retention.

Test-visible outcome: a committed Equinox recording goes through `finishRun` → outbox → HTTPS client → Worker handler → intake → `redact_vin.py`. It replays through `Elm327Session` into the same codes report as the original. The uploaded bytes contain no VIN serial, no `F18x` payload and no typed note. The manifest and provenance parse with zod. After Delete my data, the bucket and the local intake copies hold nothing for that tester.

## Non-goals

- **No accounts, logins, email, or payments.** Auth is a per-install secret (ADR-019).
- **No upload of the codes-report `.md`.** It is derived from the recording, which is uploaded, and it carries the heading date.
- **No upload of runs made before consent**, and none while sharing is off. Files queued before the switch is turned off are deleted from the queue unsent.
- **No upload from `checked` garage entries** (open question 3, recommended). Those cars are not the tester's.
- **No committing of beta recordings.** Intake writes into gitignored directories. Publishing a beta recording needs that tester's separate written OK (open question 8). No git history is involved.
- **No GPS or location code.** The app has no location feature. Android below 12 asks for location only because the OS requires it for BLE scans (`apps/mobile/App.tsx` line 36), and the app never reads it. Nothing here adds a location API.
- **No change to the recording format, `RecordingBuffer`, the command lists, `Elm327Session`, the guard, or `redact_vin.py`.** The phone scrub is an extra layer. At intake, `redact_vin.py` stays the only way a copy becomes `.redacted.jsonl` (ADR-017).
- **No redaction at source in the console, relay, or `hil:smoke`** (the ADR-017 follow-up). Only the upload copy is scrubbed. Private phone copies and the capture folder stay raw, as today.
- **No compression.** R2 storage is cheap at this scale. Revisit if a live charge log upload proves slow.
- **No iOS, no Play Store listing, no public dataset (BM9), no ML pipeline (BM1).** BM1 later reads the intake index and tombstones; this task only produces them.
- **No `docs/PLAN.md`, `docs/ARCHITECTURE.md` or `fixtures/README.md` edits by any implementer.** The orchestrator applies the proposed PLAN row and the ARCHITECTURE "What is deliberately not here" change once ADR-019 is accepted and Codex's edits to those files are committed.
- **Nothing is written to the vehicle.** This task sends no command to a car.

## Backend choice (the main design decision)

**Scale assumptions.** 10–50 testers. Per tester per month: about 4 charge logs at about 40 MB each (T2.4 §Risks: 35–45 MB per charge) plus about 10 scans at under 0.2 MB. That comes to about 160 MB per tester per month: 1.6 GB/month at 10 testers and 8 GB/month at 50.

**Price caveat.** Every price below is the architect's recollection. Nothing was fetched in this session. **The owner confirms each one on the provider's pricing page before creating an account** (owner step 2), and the Decisions section records the checked figures with the date.

| IP addresses | The Worker never stores them. Workers logs stay off (owner step). | The platform keeps logs. | The reverse proxy logs by default and must be turned off. |

**Recommendation: A.** It is the cheapest (a few dollars a year at 50 testers), and it is the only option where retention is enforced by the platform. It needs no client SDK and no native module, and no secret ever touches the repo or the APK. The costs: a hand-written Worker of about 200 lines, and the Workers request-body limit (~100 MB on the free plan, unverified). The limit is handled by splitting files into 16 MiB parts on the phone, which also makes uploads resumable on flaky mobile data. Firebase was also considered and not listed as an option. Cloud Storage for Firebase now needs a billing (Blaze) project, and App Check needs native modules.

## Design

### Flow

```
run ends (finishRun / battery diagnosis / charge log)
  → outbox.queue(kind, garageEntry, recording lines)
      sharing off, consent outdated, or entry is "checked"   → nothing (no sentence)
      UploadScrubber pass 1 (streaming) → beta-outbox/<fileId>/part-NNN.jsonl (≤ PART_BYTES, line-aligned)
      + final provenance meta line in the last part
      UploadScrubber pass 2 (safety net) over the parts        → refusal deletes the parts; status says why
      state.outbox += {fileId, kind, parts, provenance}        → "Queued for beta upload."
  → outbox.drain()   (also on app start and AppState "active")
      register once (POST /v1/installs) if not yet registered
      per file: PUT parts in order, then PUT manifest (manifest present = file complete)
      network error / 429 / 5xx → backoff (1 min × 2^attempts, cap 6 h), stays queued
      400 / 409 / 413 → failed permanently: parts deleted, status shows it
      success → parts deleted locally
Garage > Beta data sharing:  switch (stop) · status line · beta ID · Delete my data
  Delete my data → queue emptied → DELETE /v1/installs/me (retried like uploads until 204)
                 → local consent wiped (a later opt-in gets a new installId)
owner: pnpm beta:intake
  → admin list of manifests → download parts → zod-validate → re-scrub must be identical
  → fixtures/recordings/<catalogId>-beta-<vehicleKey8>/<YYYY-MM>-<kind>-<fileId8>.jsonl  (gitignored, "wx")
  → uv run tools/spike/redact_vin.py <that file>  → .redacted.jsonl beside it (also gitignored)
  → tombstones: delete that installId's local files; retention: delete files older than 24 months
```

### Scrub rules (Stage A; every rule has a source in §Sources)

The scrubber is streaming. It holds one exchange at a time: a `tx` line and the `rx` lines up to the next `tx`. It reassembles ISO-TP per header inside the exchange, tracking where each hex digit sits in the file, as `redact_vin.py` `messages()` does. It masks a payload byte in place by writing ASCII `0`, which is hex `30`, the same `MASK` as ADR-017. Output keeps every input line in the same order, so the line count and line citations are unchanged. Unchanged lines are emitted verbatim. Changed lines are re-serialized in the Python `json.dumps` form that `redact_vin.py` requires.

| Rule | Applies to | Masks |
|---|---|---|
| `vin-0902` | reply to normalized `0902` whose payload starts `49 02 01` | VIN characters 12–17 (payload 14–19). Port of `RULES["0902"]` |
| `vin-4193` | reply to `224193` whose payload starts `62 41 93` | characters 12–17 of each of the four copies (payload 14–19, 31–36, 48–53, 65–70). Port of `RULES["224193"]` |
| `vin-check-digit` | every other reassembled payload, any command | any 17-byte window of VIN characters `[0-9A-HJ-NPR-Z]` whose position-9 character equals `vinCheckDigit()` of the window → its characters 12–17 |
| `did-f180-f1ff` | positive Mode 22 reply `62 F1 xx`, `xx` = `80`–`FF` | every payload byte after the 3-byte echo |
| `mode09-infotype` | positive Mode 09 reply `49 <i>`, where `<i>` is not `00`, `02`, `04` or `0A` | every payload byte after the 2-byte echo |
| `odometer-01a6` | positive Mode 01 reply `41 A6` | the 4 data bytes |
| `user-note` | the `note` of the **first** meta line (the start meta; typed by the user in the console) | value replaced by `"removed before upload"` |
| `date-in-note` | any other kept meta `note` | substrings matching `\d{4}-\d{2}-\d{2}([T ][0-9:.]+Z?)?` replaced by `"[date]"` |
| `meta-key` | every meta line | keys other than `t dir car dongle note writeChar notifyChar mtu` dropped (fail-closed; this also drops `redact_vin.py`'s marker keys, whose `source` holds a dated file name) |

Refusals throw `ScrubRefusal`. Nothing is queued, and the status line gives the reason:
1. A line that is not valid JSON, not a `recordingLineSchema` line, or not in Python `json.dumps` form.
2. Inside a `vin-0902`/`vin-4193` reply: a CF with the wrong sequence number, or a CF with no FF for its header (as `redact_vin.py`).
3. Inside a `vin-0902`/`vin-4193` reply: a VIN byte outside `0-9A-Z` (as `redact_vin.py`).
4. The safety net. Every serial learned by `vin-0902`, `vin-4193` or `vin-check-digit` is searched for in pass 2 in every form `redact_vin.py` `_safety_net` checks:
   - ASCII anywhere in the text;
   - hex, upper or lower case, anywhere in the text;
   - hex in each exchange's concatenated `rx` with `\r` and spaces removed;
   - raw bytes in any reassembled payload.

   Any hit refuses the file.

Negative replies (`7F …`), `NO DATA`, and non-frame text are left unchanged by every rule. Scrubbing is idempotent: scrubbing a scrubbed file returns identical bytes. Intake depends on that.

### Provenance and keys (Stage A schema; Stage B values)

- `testerKey`: a random UUID v4, created at opt-in. It goes into every file.
- `installId` and `secret`: generated the same way, and never written into a file.
  - `installId` names the server folder. Keeping it separate from `testerKey` means a published file never reveals an auth identity.
  - `secret` is two UUID v4s joined, 244 random bits.
  - Randomness comes from `expo-modules-core` `uuid.v4()`. On Android that is `java.util.UUID.randomUUID()`, which uses `SecureRandom` (installed `CoreModule.kt` line 51).
- `vehicleKey`: one random UUID v4 per garage entry, created on that entry's first upload and stable afterwards. It is never derived from the VIN. A hashed VIN can be brute-forced over the 6-character serial once the first 11 characters are known.
- `month`: `YYYY-MM` from the phone's local date at queue time. No file carries anything finer. Every `t` stays seconds since the run start, which the measurements need.
- `catalogId`: the garage entry's `catalogId`, for example `chevrolet-equinox-ev-2024`, giving model and year.
- `appVersion`: `app.json` `expo.version`. The owner bumps it per beta build (owner step 8).
- `consentVersion`: `CONSENT_VERSION` from `apps/mobile/src/beta/consent.ts`. It must be one of `CONSENT_VERSIONS` in the schema.

ML split isolation (`docs/ML.md` §Data and labels) groups by `vehicleKey`, then by `fileId` (session). Known leak: a reinstall, a second phone, or two garage entries for the same car produce two `vehicleKey`s for one car. See Risks.

## Interfaces

### Stage A: `packages/obd-core/src/recording/scrub.ts` (create)

```ts
export const SCRUB_VERSION = 1;
export type ScrubRule =
  | "vin-0902" | "vin-4193" | "vin-check-digit" | "did-f180-f1ff" | "mode09-infotype"
  | "odometer-01a6" | "user-note" | "date-in-note" | "meta-key";
export interface ScrubReport { version: typeof SCRUB_VERSION; masked: Record<ScrubRule, number> } // messages or lines touched per rule
export class ScrubRefusal extends Error { readonly line: number } // 1-based input line; message never contains a VIN or serial

/** One instance per file. Lines are passed without their "\n". */
export class UploadScrubber {
  /** Pass 1. Returns the output lines that are final (it holds back at most one exchange). Throws ScrubRefusal. */
  push(line: string): string[];
  /** Pass 1 end: the held-back lines and the report. */
  end(): { lines: string[]; report: ScrubReport };
  /** Pass 2 (safety net) over the complete pass-1 output, in order. Throws ScrubRefusal if a learned serial survives. */
  verify(line: string): void;
  verifyEnd(): void;
}

/** Both passes over a whole text (small files, intake, tests). Throws ScrubRefusal. */
export function scrubRecording(text: string): { text: string; report: ScrubReport };
```

`vin-check-digit` reuses `vinCheckDigit` from `../obd/vin.js`. The Python-form serializer is a private helper, the same three lines as `apps/mobile/src/recording.ts` `pythonJsonLine`. That helper is not exported there, and changing `recording.ts` is out of scope (T2.4 B1 is also editing it).

### Stage A: `packages/obd-core/src/recording/provenance.ts` (create)

```ts
import { z } from "zod";
export const CONSENT_VERSIONS = ["beta-1"] as const;
export const UPLOAD_KINDS = ["capture", "codes-scan", "battery-scan", "charge-log"] as const;
export const PART_MAX_BYTES = 17 * 1024 * 1024; // the phone targets 16 MiB, line-aligned, so one long line may overshoot

export const betaProvenanceSchema = z.strictObject({
  schema: z.literal(1),
  fileId: z.uuidv4(),
  kind: z.enum(UPLOAD_KINDS),
  consentVersion: z.enum(CONSENT_VERSIONS),
  appVersion: z.string().regex(/^\d+\.\d+\.\d+$/),
  scrubVersion: z.literal(SCRUB_VERSION),
  month: z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/),
  catalogId: z.string().regex(/^[a-z0-9]+(-[a-z0-9]+)*-\d{4}$/),
  testerKey: z.uuidv4(),
  vehicleKey: z.uuidv4(),
  synthetic: z.literal(false),
  scrub: z.strictObject({ /* one nonnegative int per ScrubRule */ }),
});
export type BetaProvenance = z.infer<typeof betaProvenanceSchema>;

export const betaManifestSchema = z.strictObject({
  provenance: betaProvenanceSchema,
  parts: z.array(z.strictObject({ bytes: z.int().positive().max(PART_MAX_BYTES), lines: z.int().positive() })).min(1).max(64),
});
export type BetaManifest = z.infer<typeof betaManifestSchema>;

/** The file's last line: {"t": <t>, "dir": "meta", "beta": <provenance>} in Python json.dumps form. */
export function provenanceLine(t: number, provenance: BetaProvenance): string;
```

The implementer confirms `z.uuidv4`, `z.int` and `z.strictObject` against the installed zod 4.6.5 typings. If a name differs, use the installed equivalent. The schema's meaning does not change.

### Stage C1: HTTP contract (`tools/beta-backend/worker.ts`, create)

| Method, path | Auth | Body | Success | Errors |
|---|---|---|---|---|
| `POST /v1/installs` | none | `{installId, secret, consentVersion}` | 201; writes `installs/<installId>.json` = `{secretSha256, consentVersion, month}` | 400 bad body or unknown consent version; 409 exists; 429 over `REGISTRATIONS_PER_DAY` |

## Risks

- **Unknown identifier DIDs on other makes.** Rules cover the VIN (`0902`, `4193`, any check-digit-valid VIN), `F180`–`F1FF`, unreviewed Mode 09 infotypes, and the odometer. A non-standard DID on a future make could carry a serial the rules miss. Mitigations:
  - beta files stay private and uncommitted;
  - intake refuses anything the current scrubber would change;
  - each new make's profile task should list its identifier DIDs and add rules (a `SCRUB_VERSION` bump).
- **Check-digit rule limits.** 49 CFR 565.15(c) binds US-market vehicles. Canadian-market VINs are expected to follow it, but no source in the repo says so. The rule is a safety net behind the two sourced VIN locations, not a guarantee.
- **Vehicle-key leakage across installs.** A reinstall, a second phone, or a duplicate garage entry splits one car into two `vehicleKey`s, and ML could then put one car in both train and test. Mitigations:
  - BM1 checks for duplicates by comparing the 11-character VIN prefix plus near-identical `CB` values, and asks the owner before merging;
  - Android auto-backup may restore `beta.json` and keep the keys.

  Stated in `docs/ML.md` terms: vehicle identity is best-effort.
- **Upload time.** R2 records when a file arrived, which is roughly when the run happened. The month-only rule covers the file content, not the server metadata. The privacy note says so.
- **Charge-log upload size and phone work.** A 16 h hard-stop log can pass ~90 MB. That is fine with 16 MiB parts, but the JS scrub of a 40–90 MB file on the phone is unmeasured. Stage D measures it, or the first real T2.4 log does. Without open question 5's Wi-Fi rule, a 40 MB log can use mobile data.
- **Prices and limits are unverified** (see the caveat above). If a limit is lower than recalled, for example the Worker body size, `PART_BYTES` goes down. That is a constant change, not a redesign.
- **`UploadTask` in the installed dev client.** The JS typings are 57.0.7. Stage D confirms the native side exists in `0f877dca` before relying on it.
- **Third-party data.** `checked` entries are someone else's car. Recommended: never upload them (open question 3).
- **Consent text drift.** The pinned digest test (C-1) forces a version bump. A bump pauses sharing until the tester sees the new text again, so the owner should expect that re-consent step.
- **`appVersion` is uninformative if never bumped.** Today it is `1.0.0`. Owner step 8.
- **Registration is open to anyone with the APK and the URL.** Caps bound the cost: 20 registrations/day, 500 MB per install per day, 60 GB total (≈ $0.75/month worst case at the recalled price). Garbage uploads cost the owner intake time, not money. Open question 4 offers an invite code instead.
- **Legal.** The owner is the data controller. The consent and privacy text is a plain-language draft, not legal advice.

## Open questions (recommendations in bold)

1. **Backend.** (A) Cloudflare R2 + one Worker; (B) Supabase; (C) self-hosted VPS. **Recommend A**: ~$0–1.30/month at 50 testers in year one, lifecycle retention enforced by the platform, JS-only client, no secret in the repo.
2. **Retention.** **Recommend 24 months after upload** for server files, tombstones and local intake copies. That is long enough for BM1–BM3 and a second season of charge data. Shorter (12 months) is kinder to testers but loses cross-season comparisons.
3. **`checked` garage entries.** **Recommend never uploading them.** The tester is not the car's owner and cannot consent for the seller. The cost is losing pre-purchase scans, which are the product's main use case, as training data.
4. **Registration abuse.** (a) Open registration with the caps above; (b) a per-tester invite code typed once on the consent screen, which is a second field on the "one choice" screen. **Recommend (a).** Switch to (b) if junk registrations appear.
5. **Mobile data.** (a) Upload on any network, disclosed in the consent text, JS-only; (b) add `expo-network` so `charge-log` parts wait for an unmetered network while scans upload anywhere. (b) is a native dependency and needs a new dev client. **Recommend (b)**, built in the same dev-client rebuild as T2.4 B2 if the timing allows. Otherwise ship (a) first and add (b) later with a `CONSENT_VERSION` bump.
6. **Scrub strictness.**
   - (i) Typed notes are removed. The T2.4 owner protocol puts the dash SOC and ambient temperature in the note, but a free-text field can hold anything.
   - (ii) The odometer (`01 A6`) is masked. Mileage is a useful aging covariate, but combined with model, year and month it can match a used-car listing.
   - (iii) CAL IDs (`0904`) and ECU names (`090A`) are kept. They are shared across the fleet and useful for spotting drift after an OTA update in BM4.

   **Recommend all three as listed.** Structured fields (dash SOC, temperature, mileage rounded to 5,000 km) would be a later task with their own consent line.
7. **Consent placement.** **Recommend once, before the garage, on first launch of a T2.9 build**, and reachable again from the Garage section. The alternative is only inside the "join beta" interest flow, which today exists only for unsupported cars.
8. **Publishing beta recordings.** T2.8's verify line wants "one other Ultium model promoted to `verified` by a beta recording", and ADR-014 defines verified as "a recording … in the repo". **Recommend** keeping beta recordings local by default, and committing a specific redacted file only with that tester's separate written OK, recorded in the task run. The consent text does not cover publication. ADR-019 amends ADR-014 to allow this.
9. **Vehicle identity.** **Recommend a random `vehicleKey` per garage entry.** A VIN hash (BM9's "hashed VIN") is brute-forceable over the 6-character serial once the first 11 characters are known. A keyed hash would need a secret on the phone. Accept the reinstall leak described in Risks.
10. **Contact address and the deletion promise.** Which address goes in the privacy note, and is "working copies deleted within 30 days", tied to a monthly `pnpm beta:intake`, acceptable? **Recommend yes, with a dedicated address rather than a personal one.**

## Decisions
Orchestrator, 2026-09-25. The owner answered 1, 2, 3 and 5; 4 and 6–10 are decided as recommended under the owner's standing delegation.
1. Backend: **Cloudflare R2 + one Worker** (owner). The owner checks the prices and limits (owner step 2) before creating the account.
2. Retention: **24 months** after upload (owner).
3. `checked` garage entries **upload like `mine` entries** (owner: "they tested it, they consented, upload"). The consent text says in plain words that scans of cars the tester checks but does not own are shared too. Provenance keeps the `mine`/`checked` tag so the ML work can separate them.
4. Open registration with byte and registration caps. An invite code comes only if junk registrations appear.
5. Mobile data: **upload on any network, disclosed in the consent text** (owner). There is no `expo-network` and no native dependency, so T2.9 needs no dev-client rebuild. Waiting for Wi-Fi can be added later, with a `CONSENT_VERSION` bump.
6. Scrub: drop typed notes, mask the odometer (`01 A6`), keep CAL IDs and ECU names.
7. The consent screen shows once, before the garage, on the first launch of a T2.9 build, and can be reopened from the Garage section.
8. Beta recordings stay local. A specific redacted file is committed only with that tester's separate written OK, recorded in the task run.
9. A random `vehicleKey` per garage entry, not a VIN hash. The reinstall leak is accepted.
10. A dedicated contact address, not a personal one, and the 30-day deletion promise tied to a monthly `pnpm beta:intake`. The owner picks the address (owner step 7).
