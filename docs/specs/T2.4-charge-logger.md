# T2.4: Charging-session logger and first capacity estimate

Plan row: `docs/PLAN.md` T2.4 (ADR-016). Verify line (the definition of done): *one charge log on the Equinox with no gaps > 10 s in current and group voltages and rested windows at both ends; both estimates and error bands printed from replay.*

This task is larger than one implementer session. It is split into one prerequisite and four stages. Each stage has its own file list, verification and review. Order and file ownership are in "Ordering and ownership" below.

## Goal

The owner taps **Run charge log** once, with the car at rest, and puts the phone down with the screen off. The app first logs a rest window. It then tells the owner (on screen and in the notification) to plug in, logs the charge, and logs a rest window after charging ends. It then stops by itself and saves the recording to the capture folder the owner already picked. On the desktop, `pnpm charge-log <recording>` replays the recording and prints a summary: sample counts and the largest gaps, the three phase windows, a gate line, the two capacity figures with error bands and method labels, and the cell-group spread. The two capacity figures are:

- **integrated current ÷ ΔSOC.** Current integrated over the session, divided by the change in BMS SOC. It is labeled *BMS-SOC-referenced, not independent of the BMS*, and it stays that way until BM1 supplies an OCV curve.
- **The BMS figure `27AF` ÷ SOC.** Labeled *comparison, not reference*.

Neither figure is called truth. What a test sees: the synthetic charge log and the committed P1 recording both replay through `pnpm charge-log` into a committed markdown artifact that the reviewer regenerates byte for byte. The synthetic estimate's band contains the generator's known capacity. The P1 recording reproduces the decoded values already published in `docs/discovery-2026-09.md` §7.4.

- No OCV curve, no OCV-anchored SOC, no dQ/dV, no resistance, no Bayesian trend, no per-group fault scoring (BM1, BM2, BM3, BM8).
- No temperature decode. `2AF1` is polled raw only (see Sources, gaps).
- No decode of `27C6`, `276D` or `2AF7` in the estimates. They are polled raw for BM1 (open question 7).
- No charger-kWh fallback (Gate B GO; `docs/PLAN.md` Gates).
- No rotation or priority schedule. Every polled DID is read every cycle.
- No start, stop or export buttons (owner rule: one-and-done captures). The existing **Disconnect** button still ends any run. A run ended that way is saved as partial.
- No BLE auto-reconnect logic outside the charge-log run. No change to Run capture, Run codes report, `finishRun`, `SaveTargets` or `runCapture`.
- No change to `obd-core` source (`scanMode22Profile`, `Elm327Session` and the guard are reused as they are), and no change to `Elm327Session.init()`'s error policy. Codex's in-flight T2.6c (`docs/specs/T2.6c-init-retry-policy.md`) adds an optional `init(profile, { onInformationalReply })` hook. B1 uses it once it is committed; see Risks.

- No iOS. No relay-mode logging. No release or preview EAS profile unless open question 6 says otherwise.
- No edits to `docs/ARCHITECTURE.md`, `docs/PLAN.md` or `fixtures/README.md` by any implementer. The orchestrator updates them once Codex's in-flight T2.6 edits to the same files are committed.

### Stage B1: `apps/mobile/src/chargeLogger.ts` (create; pure, no Expo or React Native import)

```ts
import type { Transport } from "obd-core/transport";
import type { RecordingBuffer } from "./recording.js";

// Policy values (open question 3).
export const CYCLE_S = 5;            // one cycle starts at most every 5 s
export const FLUSH_S = 30;           // recording lines appended to the private file at least this often
export const RECOVERY_WAIT_S = 5;    // pause before a new session after a failure
export const SILENT_STOP_S = 600;    // no decoded current (or no transport) for this long: stop, partial
export const WAIT_FOR_CHARGE_S = 3600; // pre-rest done and no charge for this long: stop, partial
export const MAX_RUN_S = 16 * 3600;  // hard stop, partial

export interface ChargeLogDeps {
  /** First call returns the connected transport; later calls reconnect to the same device (B2 wraps connectVeepeak). Rejects on failure. */
  connect(): Promise<Transport>;
  recording: RecordingBuffer;        // already started (meta line written by the caller)
  signals: readonly ObdbMode22Signal[];
  now(): number;                     // seconds, same clock as recording
  sleep(ms: number): Promise<void>;
  onStatus(line: string): void;      // one plain sentence, e.g. "Resting 4:12 of 10:00. Do not plug in yet."
  stream: StreamTargets;
  /** True once the caller wants the run to end now (Disconnect pressed). */
  stopRequested(): boolean;
}

export interface StreamTargets {
  /** Creates captures/<date>-charge-log[-N].jsonl in app storage, never overwriting; returns its name. Throws on failure. */
  create(): string;
  /** Appends to that file. Throws on failure. */
  append(name: string, text: string): void;
  /** Copies the private file into the already remembered capture folder. Never shows a picker. Rejects when no folder is remembered or the copy fails. */
  copyToFolder(name: string): Promise<void>;
}

export interface ChargeLogResult {
  file: string;                      // private name
  complete: boolean;                 // true only when a post-charge rest of POST_REST_S was logged
  stopReason: string;                // "post-charge rest logged" | "disconnect pressed" | "no current for 10 min" | ...
  saved: string;                     // one status sentence: saved to folder, or NOT SAVED to folder with the private path
}

/** Never rejects. Ends with a final flush, the copy to the folder, and a last meta line naming the stop reason. */
export async function runChargeLog(deps: ChargeLogDeps): Promise<ChargeLogResult>;
```

## Dependencies

- **Stage B2 only:** `react-native-background-actions@4.1.0` (MIT; npm last modified 2026-04-07; repository `Rapsssito/react-native-background-actions`).
  - **Why it is needed.** React Native pauses JS timers when the activity pauses (screen off, app in background), unless a headless JS task is running: `JavaTimerManager.kt` lines 72–75 (`onHostPause` sets `isPaused`), 91–95 (`onHeadlessJsTaskStart`) and 291/323 (`doFrame` returns early when paused with no task). Installed React Native 0.86.3, `ReactAndroid/src/main/java/com/facebook/react/modules/core/JavaTimerManager.kt`. `Elm327Session` timeouts, the 500 ms `CAN ERROR` retry, the resync wait and the 5 s cycle pacing all use timers, so a screen-off run without a headless task would hang on the first lost reply.
  - React Native's own `HeadlessJsTaskService` keeps timers running while its task is active, and it holds a `PARTIAL_WAKE_LOCK` from task start until the service is destroyed (`HeadlessJsTaskService.kt` lines 67–70 and 174–186).
  - The library subclasses it (`RNBackgroundActionsTask.java`). It starts the task with `HeadlessJsTaskConfig(taskName, data, 0, true)`, meaning no timeout and allowed in the foreground, and calls `ServiceCompat.startForeground(..., foregroundServiceType)`. Its README documents the `foregroundServiceType` option, with `connectedDevice` requiring `FOREGROUND_SERVICE_CONNECTED_DEVICE`.
  - Its manifest declares the service without a type, so the local config plugin adds it.
  - Android's documentation describes `connectedDevice` as "interactions with external devices that require a Bluetooth ... connection". It needs the manifest permission `FOREGROUND_SERVICE_CONNECTED_DEVICE` and a granted runtime `BLUETOOTH_CONNECT`, which the app already requests (developer.android.com, "Foreground service types", fetched 2026-09-25).
- **Why a native change is unavoidable.** The ble-plx plugin's `isBackgroundEnabled` only adds the BLE hardware feature on Android (`react-native-ble-plx/plugin/build/withBLEAndroidManifest.js` lines 8–15), and nothing installed provides a foreground service. So B2 changes the native project, and **the installed dev client (EAS `0f877dca`) stops being valid for B2. The owner must build and install a new dev client before the B2 hardware check and before Stage C.** Stages A and B1 are JS-only and do not need it.
- The alternatives are in open question 2: a local Expo module of about 60 lines of Kotlin (no npm dependency, more native code to own), or Notifee (npm last modified 2024-12-20).
- No new dependency in Stages A or B1. `expo-file-system` 57.0.7 is already installed and has `File.write(..., { append: true })` (`build/File.types.d.ts`, `FileWriteOptions.append`), `File.open()`/`FileHandle`, and SAF append mode (`FileMode.Append`, "for SAF files, this is a strict append-only mode"). `expo/config-plugins` ships with the installed `expo` 57.0.24 (`expo/config-plugins.js`).

## Policy values

These are policy values, not vehicle constants. They are justified here, and the owner decides them in open question 3. The same `chargePhases` code drives the phone's automatic stop and the replay.

- **Current classes.** A current sample is *rest* if |I| ≤ 2.0 A. The idle draw in Ready was ≈ 1 A, and 2 A is about C/150 on a ≈ 300 Ah pack (§7.4). A sample is *charging* if I ≤ −5 A; the owner's AC charge draws ≈ −26 A. Anything else is *other*.
- **Runs.** A run is a maximal sequence of consecutive current samples in the same class. A gap > 10 s between two samples ends a run.
- **Windows.**
  - `charge` is the longest charging run lasting at least 60 s.
  - `preRest` is the last rest run of at least 600 s that ends before `charge.start`, with at most 300 s between its end and `charge.start` (walking to the charger).
  - `postRest` is the first rest run that starts within 300 s after `charge.end`, clipped to its first 1800 s. On the phone, reaching 1800 s is the normal stop.
- **Gate span.** From `preRest.start` to `postRest.end`. The largest current gap and the largest group-voltage gap (between complete `2AE1`–`2AE7` sets) inside it must both be ≤ 10 s.
- **Phone cycle.** A cycle starts every 5 s, or right after the previous one if that took longer. The recording is flushed at least every 30 s, so a crash loses at most 30 s. The run stops as partial after 10 min without a decoded current, after 60 min without a charge once the pre-rest is done, or after 16 h. Size estimate: about 150 lines of about 50 bytes per cycle, so ≈ 5 MB per hour and ≈ 35–45 MB for a 7–9 h session.

## Estimates and error budgets

**Integrated current ÷ ΔSOC** (`integrated-current-bms-soc`). Label, printed verbatim: *"BMS-SOC-referenced: divides by the BMS's own SOC, so it is not independent of the BMS (ADR-016). Not truth."*
- It needs `preRest`, `charge` and `postRest`, and no current gap > 10 s between the SOC endpoints. Otherwise it is `not-estimated`, with the reason (for example "no post-charge rest window" or "current gap of 97 s at t=…").
- SOC endpoints: the last `2B43` sample in `preRest` (t0, SOC0) and the last in `postRest` (t1, SOC1).
- Q = −∫ I dt from t0 to t1, integrated with the trapezoid rule over the current samples, linearly interpolated at t0 and t1, in Ah. Capacity = Q ÷ ((SOC1 − SOC0)/100).
- Bounded terms, added linearly (worst case, stated as such):
  - current resolution: 0.025 A × (t1 − t0)/3600 Ah;
  - integration: ½ Σ |I_k+1 − I_k| Δt_k / 3600 Ah (half the gap between the left and right Riemann sums);
  - SOC resolution: ±(100/255)/2 % at each end, so ±0.392 % on ΔSOC.
- Relative band = (current + integration)/|Q| + 0.392/ΔSOC. Band = capacity × relative band.
- Unbounded, named: current sensor gain and offset; BMS SOC model error and lag; temperature (not measured).
- The summary prints "BM2 selection: pass" only when ΔSOC ≥ 30 % and both endpoints are rested. Otherwise it prints "BM2 selection: fail (<reason>)". The estimate is printed either way.

**BMS figure** (`bms-energy-over-soc`). Label: *"BMS figure: 27AF energy remaining ÷ SOC. A comparison, not the reference (ADR-016). Not truth."*
- Value = E ÷ (SOC/100) in kWh, at the first and last cycle that has both `27AF` and `2B43`, plus the min–max over all such cycles with n.
- Relative band = 0.005/E + ((100/255)/2)/SOC.
- Unbounded, named: the BMS energy model; whether the SOC basis is displayed or raw.

**Power check.** Mean I × V against the `27AF` slope over the `charge` window, printed as a ratio. It re-applies the Gate B plausibility check (§7.5) in every session. It is not an estimate and has no pass threshold.

**Imbalance.** The `2AF5` spread (max − min, in mV) at the end of `preRest`, at the end of `postRest`, and at its maximum during `charge` (with SOC). The 80-group extremes (index and module of the minimum and maximum) at the same points. The count of cycles where the group minimum and maximum equal `2AF5`'s. All of it is community tier, with no fault verdict.

## Risks / open questions

Risks:
- **Modules asleep with the car off.** Nobody has recorded whether `17` or `CB` answer during an unattended charge, and the Lyriq notes say `CB` sleeps fast when idle (`reports/Ultium battery app trajectory review.md`). The B2 check measures it before the charge. If they are silent, Stage C runs in Ready (as T2.3b did), and that session's idle draw is part of the log.
- **`init()` with the car off.** `init(genericProfile)` needs a Mode 01 `0100` responder. If none answers with the car off, init fails every time and the run stops after 10 min. The B2 check finds out. Changing `init()` is out of scope; it would be a separate task.
- **Init error policy.** Today an `LV RESET` during `init()`'s `ATI`/`ATDPN`/`ATRV` does not stop init, so the next command can reach a reset ELM. Codex's T2.6c adds `init(profile, { onInformationalReply })`, which is called after core's own retry. B1 passes a hook that throws on a final `error` reply, and the logger treats that as a recovery (B1 case 3b). If T2.6c is not committed when B1 starts, B1 waits for it; it does not copy T2.6b's rejected notification-level interception.
- **Library on the New Architecture.** `react-native-background-actions` is a legacy-style native module. It should run on React Native 0.86 through the interop layer, but nobody has tried it on this app. The B2 hardware check is the test. Fallback: the local Expo module (open question 2).
- **OEM battery managers** (Samsung, Xiaomi and others) can kill foreground services. The phone model is not recorded anywhere in the repo (open question 4).
- **File size.** ≈ 35–45 MB per charge (§Policy values). The streaming append and the chunked copy are designed for it; the B2 check measures real sizes. Replaying one in `recordings.test.ts` would take minutes (open question 5).
- **Synthetic fixture blind spot.** The synthetic fixture shares the scaling constants with the decoder. Only the P1 recording checks them. Without P1 there is no scaling check at all.
- **BMS-SOC circularity.** The integrated-current figure divides by the BMS's SOC, so agreement with the BMS figure is expected and proves little (ADR-016). The labels say so.
- Doc follow-ups for the orchestrator after Codex's T2.6 commit: `docs/ARCHITECTURE.md` (`obd-battery/src/session.ts` exists as specified; `apps/mobile` logger lives in `src/chargeLogger.ts`, not `logger/`), `fixtures/README.md` inventory, and `docs/EVAL.md` label `reference.method` (the synthetic label uses `"synthetic-generator"`).
