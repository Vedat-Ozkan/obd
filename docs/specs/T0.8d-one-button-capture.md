# T0.8d: One-button capture in the phone app

## Goal

The owner connects to the Veepeak and taps one button, **Run capture**. The app then does the rest by itself:
- It starts a recording.
- It sends a fixed, sourced command sequence one command at a time through the existing `ConsoleSession`, waiting for each `>`.
- It keeps going past error replies and timeouts, which it records as evidence. The one exception: after a timeout, it continues only once the ELM shows it is idle again (Decision point 2).
- It stops early only on disconnect, or when the ELM never becomes idle again.
- It stops the recording, writes the file the way the existing export does, and opens the Android share sheet automatically.

Android still needs the user to choose where the file goes in the share sheet. The app cannot save it to a user-visible folder silently. While the capture runs, the screen shows `Step n of N`, the command in flight, and the last command's outcome. The manual console (Start/Stop recording, Send, Export) keeps working. What a test sees: `apps/mobile/test/capture.test.ts` drives the runner over a fake transport with scripted replies, including an error reply, a timeout followed by a late `>`, a timeout with no `>`, a write failure, and a disconnect mid-run. It checks the exact wire order and the recording lines.

## Non-goals

- No change to the console allowlist (`READ_ONLY_SERVICES`, `ALLOWED_AT_COMMANDS`, `normalizeReadOnlyCommand`). Every capture command already passes it unchanged. The per-service exact request lengths from `docs/specs/X-2026-09-23-write-safety.md` are not ported into `console.ts`. That spec's Follow-ups say the console moves to the `obd-core` guard when it next grows, and this task does not grow it.
- No `obd-core` change, no use of `Elm327Session` in the app (it is not a package export), no new package export.
- No `app.json`, native, plugin, EAS, dependency, or lockfile change. `expo-sharing` (~57.0.21) and `expo-file-system` are already dependencies and already used by `App.tsx`. The installed dev-client APK (EAS build `0f877dca`) stays valid.
- No user-editable command list, no per-vehicle sequences, no retries, no cancel button other than Disconnect, no keep-awake, no background execution.
- No `0902`, `22 4193`, or any other VIN-bearing request. No `ATDPN`/`ATRV` (not requested).
- No redaction at source (ADR-017 follow-up). No change to `tools/spike/redact_vin.py`.
- No Mode 02 decoding. That is T0.5 Stage C, and it runs only if this capture records a positive `42` reply.
- No automatic save into `fixtures/recordings/` and no committing. The owner moves the file (Verification).

## Interfaces

### `apps/mobile/src/capture.ts` (new)

```ts
import type { ConsoleSession } from "./console.js";
import type { RecordingBuffer } from "./recording.js";

/** Fixed sequence; every entry is already in normalized form for normalizeReadOnlyCommand. Sources: this spec §Sources. */
export const CAPTURE_COMMANDS: readonly string[]; // ["ATZ","ATE0","ATL0","ATS0","ATH1","ATSP0","0100","020000","020200"] (+ "03" if open question 1 = yes)

/** Policy value, mirrors obd-core RESYNC_MS (packages/obd-core/src/elm/session.ts:72): how long to wait for a late '>' after a timeout or write failure. */
export const PROMPT_WAIT_MS = 1000;

export interface CaptureProgress {
  step: number;       // 1-based
  total: number;      // CAPTURE_COMMANDS.length
  command: string;
  /** Undefined while the command is in flight. After it: "data" | "ok" | "nodata" | "error: <ElmErrorKind>" from parseElmResponse, or the thrown error's message. */
  outcome?: string;
  /** The complete response text (without '>') when one arrived. */
  response?: string;
}

export interface CaptureResult {
  sent: number;           // commands whose tx was recorded
  total: number;
  /** Set when the run ended before the last command, e.g. "disconnected" or "no '>' within 1000 ms after: <message>". */
  stoppedEarly?: string;
}

export function runCapture(session: ConsoleSession, recording: RecordingBuffer, onProgress: (progress: CaptureProgress) => void): Promise<CaptureResult>;
```

Runner behavior, in order:
1. Record `meta` note `capture start: <commands joined by " ">`.
2. For each command: call `onProgress` with no outcome, then `await session.send(command)`.
   - **Resolved.** Classify with `parseElmResponse(response, command).status` from `obd-core/elm`. Report the outcome and response, then continue. Error replies (`?`, `NO DATA`, `CAN ERROR`, `UNABLE TO CONNECT`, `STOPPED`, `LV RESET`, …) all arrive with a `>`, so the ELM is idle and the next command is safe.
   - **Rejected, `session.closed` is true.** Stop: `stoppedEarly = "disconnected"`, and write no `meta`, because the recording has already been frozen by teardown.
   - **Rejected otherwise** (timeout or write failure; `ConsoleSession` has already recorded its `meta` note). Report the error message as the outcome, then `await session.waitForPrompt(PROMPT_WAIT_MS)`. If that returns true, continue. If it returns false and `session.closed` is true, stop as disconnected. Otherwise stop: `stoppedEarly = "no '>' within 1000 ms after: <message>"`.
3. If the session is not closed, record `meta` note `capture complete: <sent> of <total> sent` or `capture stopped at step <n> (<command>): <stoppedEarly>`.
4. Never throw, except for a programming error such as a busy session.

### `apps/mobile/src/console.ts`: no write without a prompt

Before: after a timeout or a write failure, the next `send()` writes at once. The reader was reset, so a late `>` from the old command can also complete the new one.

After:

```ts
export class ConsoleSession {
  // unchanged: constructor(transport, recording, timeoutMs = 20_000), send(input), close()
  /** True after close(). */
  get closed(): boolean;
  /** Resolves true at once when no timeout/write failure is outstanding; otherwise true on the next '>', false after `ms` or on close(). */
  waitForPrompt(ms: number): Promise<boolean>;
}
```

- The timeout path and the write-failure path set a private `stale = true`.
- In `onData`, if the reader returns at least one response while nothing is pending, clear `stale` and resolve every `waitForPrompt` waiter with true. Every chunk is still recorded as `rx`, as today.
- `send()` order: busy check, `normalizeReadOnlyCommand`, then, if `closed`, throw `Console session closed`, then, if `stale`, throw `Waiting for '>' after a timeout or failed write`. None of these writes a `tx` line or calls `transport.write`.
- `close()` sets `closed` and resolves every waiter with false. Otherwise it behaves as today.

This applies to the manual console too (open question 2). After an unanswered timeout, Send shows the error until a late `>` arrives. Stop recording plus Start recording (a fresh session) or Disconnect is the way out, as today.

### `apps/mobile/src/recording.ts` (only if open question 3 = app-side)

`toJsonl()` writes each line in the form Python's `json.dumps` produces by default: `", "` and `": "` separators, keys in insertion order, and every character above U+007F written as a lowercase `\u00xx` escape. Other values keep `JSON.stringify`'s escaping, which already matches Python's for `"`, `\`, `\b\f\n\r\t`, and `\u00xx` for other control characters. `parseRecording` is unaffected: it is still valid JSON. Signature unchanged.

### `apps/mobile/App.tsx`

- A **Run capture** button, enabled only when connected, the note is non-empty (open question 4), no recording is active, and nothing is pending or capturing.
- On tap, it runs the existing start-recording logic (`startRecording` returns the new `ConsoleSession`), shows `Capturing…`, and calls `runCapture`:
  - Each progress event shows `Step n of N: <command>` and `Last: <command> → <outcome>`.
  - It appends `> cmd` and `response>` to the transcript, or `-- <outcome>` on a failure.
- Then it freezes the recording (unless teardown already froze it) and exports it automatically.
- The export goes through the existing export code, refactored to take the JSONL string: `exportJsonl(jsonl)`. The Export button calls it with the frozen state.
  - The capture passes the string returned by the freeze (`endRecording()` returns it; teardown's freeze keeps it in a ref). It must not read `frozenJsonl` React state from the async closure, where it is stale.
- The filename is unchanged (`YYYY-MM-DD-phone-console.jsonl`, `-2`…), and nothing is ever overwritten.
- The final status is `Capture complete: n of N sent.` or `Capture stopped at step n of N (<cmd>): <reason>.`, followed by `Share sheet opened for <file>; choose where to save it.`
- An early stop still exports: the partial file is evidence.
- While capturing: Scan, Start/Stop recording, Send, Export, and Run capture are disabled. **Disconnect stays enabled**, as the abort path.
- `teardown(message)` records `meta` note `<message>` before freezing when a session is active, so a file truncated by a disconnect says why. This applies to the manual path too, and it is purely additive.

## Risks / open questions

### Open questions

1. **Add `03` to the sequence?** T0.5's Stage C capture list (its spec line 417) is `ATZ … 0100 020000 020200 03`, and the owner's request omits `03`. `03` shows whether a DTC is stored, which explains a `020200` answer of `00 00` or `NO DATA`. It is a read, and it is already on the console allowlist. **Recommendation: yes, append `03` (10 steps).**

2. **Continue past a timeout only when the ELM is idle again, and apply the same rule to the manual console?** This departs from the owner's "continue past timeouts".
   - The console gives up after 20 s and then writes the next command at once. If the ELM is still busy, that character interrupts it and is discarded (docs/ELM327.md §Write safety).
   - In this sequence the only dangerous case is `0100`. Losing its first character leaves `100`, which could reach the bus as service `10` (DiagnosticSessionControl), a service §Write safety refuses. A dropped first character on the AT commands leaves text the ELM rejects with `?`. The first command, `ATZ`, is harmless even into a busy ELM.
   - The rule also fixes a late `>` from the old command completing the new one.
   - Error replies still continue, because they come with a `>`.
   - **Recommendation: yes to both.** After a timeout, wait up to 1000 ms for a late `>`. Continue if one arrives; otherwise stop, record why, and export. Put the rule in `ConsoleSession` so manual Send obeys it too. This is the app-side equivalent of the obd-core "no write without a prompt" amendment in the write-safety spec. The alternative is capture-only, leaving manual Send as today.

3. **Make the export redactable.** Today the committed copy cannot be produced. `redact_vin.py` refuses the app's compact `JSON.stringify` lines (checked on 2026-09-23). This already applies to the plain T0.8 console export.
   - (a) App-side: `RecordingBuffer.toJsonl()` writes Python `json.dumps` form, as specified above. That is about 8 lines plus R1, and all recorders then share one line form.
   - (b) Script-side: a separate `tools/spike` task teaches `redact_vin.py` to accept compact lines. Its strict check exists to guarantee the line lengths when it masks. That is outside `apps/mobile`, needs its own spec, and needs pytest cases.
   - (c) Neither for now: the capture file stays local, and T0.8 acceptance uses the local original, as the T0.8b gate already allows.
   - **Recommendation: (a) in this task.**

4. **Keep the non-empty note requirement for Run capture?** The note is the only record of vehicle state (Ready, Park, SOC). It is typed once and kept between runs. **Recommendation: keep it.** The alternative is a default note when empty, for a true one-tap run.

### Risks

- **Share sheet.** Android shows a chooser, and the user must pick where the file goes. `shareAsync` resolving does not prove the file was saved, so the status says "share sheet opened", not "saved". If the sheet fails (for example, the app went to the background), the frozen JSONL stays available through the Export button.
- **Foreground only.** BLE notifications and the share sheet need the app in the foreground with the screen on. The run takes well under a minute unless commands time out (at most 20 s each, and after an unanswered timeout the run stops).
- **Fresh-session bypass.** The stale state lives in one `ConsoleSession`. Stop plus Start recording, or a new capture, starts clean even if the ELM is still busy. The capture starts with `ATZ`, which is harmless in that case. Manual Send after a restart is the owner's direct action. Closing this fully means the console adopting the obd-core session or guard (the write-safety spec's Follow-ups), which is out of scope here.
- **Truncated files fail replay.** A disconnect mid-reply leaves a tx with no `>`. Such files are evidence for the owner only, not fixtures (hardware step 7).
- **T0.8 acceptance equivalence.** This capture sends the T0.8b gate sequence plus `020000`/`020200`(/`03`) without the owner typing each command. Whether its file satisfies the T0.8b hardware gate is for the orchestrator and reviewer to rule. The file does contain each required tx once with a complete `4100…>` after `0100`.
- **Mode 02 may answer `NO DATA`.** The Equinox reported 0 DTCs in the spike (§J1979 conventions, Equinox readiness), so frame 0 may not exist. That is a valid result: it defers T0.5 Stage C (T0.5 Decision 2). It is not a failure of this task.

Size: **M.** About 60 lines of runner, 25 in the console, 40 in `App.tsx`, optionally 8 in the recording, and about 180 lines of tests. One implementer session, no split.

## Decisions

Orchestrator, 2026-09-24, under the owner's delegation ("go ahead as you see fit to complete the work", 2026-09-23) and the owner's request for a hands-off run:

1. **Yes, append `03`** (10 steps). `CAPTURE_COMMANDS` = `ATZ ATE0 ATL0 ATS0 ATH1 ATSP0 0100 020000 020200 03`.
2. **Yes to both.** Stale-until-prompt rule in `ConsoleSession` (manual Send too); after a timeout or write failure the capture waits up to `PROMPT_WAIT_MS` for a late `>`, else stops, records why, and exports.
3. **(a) App-side.** `toJsonl()` writes Python `json.dumps` form; R1 and the `redact_vin.py` run are required verification items.
4. **Changed from the recommendation, to honour "one tap":** the note field is prefilled with `Equinox Ready, Park; one-button capture` when it is empty at app start, so Run capture needs no typing. The note must still be non-empty to enable the button (the owner can edit it). No other change.
