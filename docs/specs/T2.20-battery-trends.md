# T2.20: Battery trend analytics (deterministic step before BM2/BM3)

Plan source: `docs/ANALYTICS.md`. Not yet in `docs/PLAN.md`; the lead adds the row.

## Goal
Turn the sessions the app already has (saved battery check reports, charge logs, test drives) into a per-car series and a significance-gated trend, with a shareable Markdown trend report. The output is a BMS-referenced capacity index and a cell-group spread series, never state of health (ADR-016, ADR-023). It says "Not enough data yet: n sessions over d days" until n >= 5, span >= 90 days and |beta| > 2 SE. This is the deterministic step that supplies series and tests to BM2 (Bayesian capacity trend) and BM3 (per-group faults); it uses no Kalman/GP, no OCV anchoring, no fault injection, so it neither pre-empts nor contradicts them. Visible outcome: `pnpm trend-report <paths>` prints a trend report; Stage B shows a Trends section on the Car screen.

## Staging
- Stage A (desk, this session): pure library plus script, verified on committed recordings and seeded synthetic series.
- Stage B (desk, after A): persist `ChargeSessionSummary` on the phone, Trends section on the Car screen. Separate implementer session.
- Stage C (owner, hardware-gated): charge power by SOC on a real charge log (OWNER-QUEUE C2). NOT RUN until a real log exists; the Stage A code only computes the bins.

Stage A is the only stage with a full Files list below; Stage B and C get a short list and are re-checked against main before they start.

## Non-goals
- No SOH, no "capacity: measured", no change to `capacity`/`health` fields of the report (ADR-016).
- No charge-rate-versus-temperature; temperature scaling is unverified (T2.17). No guessing a scaling.
- No Kalman, GP, conformal, OCV-anchored capacity, injected faults (BM2/BM3).
- No usage analytics, events, funnels, A/B tests; no new network calls; trend summaries are not uploaded (ANALYTICS.md "Privacy defaults", "first choice: no client events").
- No change to `obd-core`, `fixtures/recordings/`, the committed synthetic fixture or its generator, beta upload code, or T2.19 accessibility files.
- No charger-type tagging UI (Stage C decides, with a real log). No flag on charge power in Stage A.
- No new dependencies.

Before/after for existing code: `capacity.ts` `bmsFigure` (currently module-private, `capacity.ts:80`) becomes exported as `bmsFigure(energy, soc)` so the report-derived point can recompute its band from `parked.bmsFigure.energyKwh`/`socPercent` (the stored report holds no band). No other existing signature changes. `summariseChargeLog` reuses `integratedCurrentCapacity`, `chargePhases`, `gateFailures`, `groupImbalance`, `groupsUnderLoad`, `MAX_GAP_S`; the text renderer `chargeLogSummary` in `scripts/charge-log.ts` is not changed.

Rules, stated once (ANALYTICS.md Steps 1-5 are the reasoning):
- Points: report -> `bms-kwh`, only `scanStatus: complete`, only `parked.bmsFigure.socPercent` inside `socBin` 40-80 %; summary -> `integrated-ah`, only if `gateFailures` empty. Unit kWh and Ah fits are separate, never pooled. Everything else goes to `rejected` with a reason string. `at` for recordings comes from the filename date `YYYY-MM-DD`; for reports from `scannedAt`.
- Index `x = y / cRef`, `cRef` = median of the first three accepted points of that method ordered by time. Fewer than three accepted: not-enough-data.
- Fit: WLS with sigma = band/2 (assumption printed in the report), SE inflated by `max(1, sqrt(chi2/(n-2)))`, `t` in years, `fade %/yr = -100*beta`. Gate: n >= 5, span >= 90 days, |beta| > 2 SE, otherwise not-enough-data with n and days.
- Group z: `(V_g - median)/(1.4826*MAD)`; MAD = 0 gives `undefined` for all groups (no flag). Weak group: z < -3 in >= 3 of the last 5 complete parked checks in the same SOC bin, identified by group index; fewer than 5 checks never flags. Spread (mV) series gets the same fit with sigma from the 0.1 mV tick; a step > 3 mV between consecutive same-bin checks is a flag.
- Capacity outlier: newest point outside `fit +- 3*sqrt(sigma^2 + SEpred^2)` (only when a trend fit exists). 12 V: resting voltage more than 0.3 V below its own median in two consecutive checks (`twelveVolt` report). Codes: a DTC not in the previous check. Drives: a group in `groupsUnderLoad.flagged` in >= 2 drives.
- `powerBySoc`: `P = -I*V/1000` kW with the `powerCheck` pairing (voltage within `MAX_GAP_S` after the current sample), charge window only, 5 % SOC bins, median per bin. No flag yet.
- All numbers in the report carry the label "BMS-referenced capacity index, not state of health" and the one-car limitation from `report.ts`.

## Risks / open questions
1. The repo has no real multi-session series, so no trend can be shown on real data; all trend evidence in Stage A is synthetic and labeled so in the artifact (AGENTS.md rule 11).
2. `sigma = band/2` is an assumption, not a calibrated error; the output states it. BM2 replaces it.
3. Wall-clock time for recordings comes from the filename date; two same-day drives span 0 days, so they exercise only the drive-group rule.
