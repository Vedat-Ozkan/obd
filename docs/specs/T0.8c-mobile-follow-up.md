# T0.8c: Mobile contrast and Metro resolver follow-up

## Goal

Close T0.8 review round 3 findings 1–4 without changing the console's BLE, command, or recording behavior. Every enabled native Android button has a specified background whose white label contrast is at least 4.5:1 in both app palettes; the light console surface remains legible without placing the forbidden-service byte text `2F` in `App.tsx`; and the Metro `.js`-to-TypeScript compatibility resolver applies only to repository source importers and suppresses only an expected path-resolution miss.

- No dependency, lockfile, Expo app configuration, EAS build, generated native project, or package-script change.
- No T0.5 work, roadmap/task-record edit, recording creation/edit, or cleanup of concurrent work.
- No custom button component, design system, accessibility redesign, iOS behavior, or broader Metro/monorepo configuration.
- No new automated test file. The bounded resolver checks below exercise the exported Metro configuration directly.

## Interfaces

There is no new public package API.

`App.tsx` extends both internal palette objects with the same explicit Android button background:

```ts
buttonBackground: "#005A9C"
```

Pass `color={colors.buttonBackground}` to every `Button` rendered by `App`, including the device-row button. React Native renders enabled Android `Button` labels in white, giving white on `#005A9C` a WCAG contrast ratio of 7.14:1 in either palette. Disabled-button rendering is platform controlled and is outside the requested enabled text contrast check.

Change the light palette's `consoleBackground` from `#F2F2F2` to `#F4F4F4`. Black console text on that surface is 19.09:1 and the existing `#767676` console border is 4.13:1, so this change preserves or improves the existing light-console contrasts while removing the accidental `2F` text match.

The Metro resolver keeps its existing signature and default-config fallback behavior:

```js
(context, moduleName, platform) => Resolution
```

For a relative `.js` specifier whose `context.originModulePath` is not under a `node_modules` path segment, try the equivalent `.ts`, then `.tsx`, then the original `.js`. Treat only an error whose constructor name is exactly `FailedToResolvePathError` as a missing candidate and continue. Rethrow every other caught value unchanged. If `originModulePath` has a `node_modules` segment using either `/` or `\` separators, resolve the original specifier immediately and do not probe TypeScript alternatives.

Do not add a direct `metro-resolver` import or dependency merely to perform `instanceof`: under pnpm it is transitive and is not resolvable from `apps/mobile` as a declared package. The constructor-name check is deliberately narrow and is covered by the verification harness.

- [ ] The following contrast calculation prints ratios at or above their stated thresholds: button `7.14` (minimum `4.5`), light console text `19.09` (minimum `4.5`), and light console border `4.13` (must not regress below the prior rounded `4.06`):

```bash
node - <<'NODE'
const pairs = [
  ["button", "FFFFFF", "005A9C", 4.5],
  ["light console text", "000000", "F4F4F4", 4.5],
  ["light console border", "767676", "F4F4F4", 4.06],
];
const luminance = (hex) => {
  const channels = hex.match(/../g).map((value) => Number.parseInt(value, 16) / 255);
  const linear = channels.map((value) => value <= 0.04045 ? value / 12.92 : ((value + 0.055) / 1.055) ** 2.4);
  return 0.2126 * linear[0] + 0.7152 * linear[1] + 0.0722 * linear[2];
};
for (const [name, foreground, background, minimum] of pairs) {
  const values = [luminance(foreground), luminance(background)];
  const ratio = (Math.max(...values) + 0.05) / (Math.min(...values) + 0.05);
  console.log(name, ratio.toFixed(2));
  if (ratio < minimum) process.exitCode = 1;
}
NODE
```

- [ ] `! rg -n '2F' apps/mobile/App.tsx` passes. The existing validator/test references under `apps/mobile/src` and `apps/mobile/test` remain unchanged and continue proving that service `2F` is rejected.
- [ ] This direct resolver harness passes. It proves repository `.js` imports try `.ts` then `.tsx`, a path miss is the only swallowed error, an unrelated error is rethrown by object identity, and importers under POSIX and Windows-style `node_modules` paths never receive rewritten candidates:

```bash
node - <<'NODE'
const assert = require("node:assert/strict");
const resolver = require("./apps/mobile/metro.config.js").resolver.resolveRequest;
class FailedToResolvePathError extends Error {}

const attempted = [];
const sourceContext = {
  originModulePath: "/repo/apps/mobile/App.tsx",
  resolveRequest(_context, name) {
    attempted.push(name);
    if (name.endsWith(".ts")) throw new FailedToResolvePathError("missing candidate");
    return { type: "sourceFile", filePath: name };
  },
};
assert.equal(resolver(sourceContext, "./feature.js", "android").filePath, "./feature.tsx");
assert.deepEqual(attempted, ["./feature.ts", "./feature.tsx"]);

const fallbackAttempts = [];
const fallbackContext = {
  originModulePath: "/repo/apps/mobile/App.tsx",
  resolveRequest(_context, name) {
    fallbackAttempts.push(name);
    if (name.endsWith(".ts") || name.endsWith(".tsx")) {
      throw new FailedToResolvePathError("missing candidate");
    }
    return { type: "sourceFile", filePath: name };
  },
};
assert.equal(resolver(fallbackContext, "./feature.js", "android").filePath, "./feature.js");
assert.deepEqual(fallbackAttempts, ["./feature.ts", "./feature.tsx", "./feature.js"]);

const boom = new Error("resolver bug");
const errorContext = {
  originModulePath: "/repo/packages/obd-core/src/example.ts",
  resolveRequest() { throw boom; },
};
assert.throws(() => resolver(errorContext, "./feature.js", "android"), (error) => error === boom);

for (const originModulePath of [
  "/repo/node_modules/example/index.js",
  "C:\\repo\\node_modules\\example\\index.js",
]) {
  const names = [];
  const dependencyContext = {
    originModulePath,
    resolveRequest(_context, name) {
      names.push(name);
      return { type: "sourceFile", filePath: name };
    },
  };
  assert.equal(resolver(dependencyContext, "./feature.js", "android").filePath, "./feature.js");
  assert.deepEqual(names, ["./feature.js"]);
}
NODE
```

## Risks / open questions

- **Largest risk: coupling the narrow catch to Metro's error class name.** A future Metro release could rename its missing-path error. In that case the resolver will fail loudly during `expo export`, which is safer than swallowing an unexpected resolver failure. The locked current version and direct harness make the present behavior explicit.
- React Native owns disabled native-button styling. This spec verifies enabled white labels against the explicit Android button background, matching the reported finding. A future custom accessible disabled state belongs to a separate UI task if phone inspection finds it necessary.
- Metro packages may contain NodeNext-style relative imports of their own. Excluding every `node_modules` importer is intentional: dependencies must be resolved according to their published layout rather than rewritten by this repository-specific compatibility rule.
- No material question blocks implementation.

## Decisions

- Use `#005A9C` for enabled buttons in both palettes and `#F4F4F4` for the light console surface.
- Identify an expected Metro candidate miss by exact constructor name, without adding a transitive package as an application dependency.
- Treat `node_modules` as a full path segment with either slash convention; do not rely on a substring match.
- Keep the original `.js` fallback and all import specifiers unchanged so NodeNext typechecking and genuine JavaScript files continue to work.
