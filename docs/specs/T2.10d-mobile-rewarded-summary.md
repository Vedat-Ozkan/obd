# T2.10d: Phone opt-in summary, then rewarded flow

Ordered stages: **D1 development phone trigger after C1**, before T2.10b; **D2 complete rewarded flow after b/C2**. Each is at most one implementation session and ten files. D1 has no native dependency or ad and does not complete T2.10. D2 retains the PLAN signed-SSV/ad/native-phone acceptance gates.

## Goal

D1: on a saved diagnosis detail screen the owner can opt in separately to OpenRouter/DeepSeek processing and tap once to request a checked summary from the local laptop Worker. Offline template stays available; any failure or invalid output shows it unchanged. The development view also exposes sanitized, selectable attempt metadata so the owner can save the required phone evidence without debugger access. D2 later adds the user-chosen rewarded ad and uses only server-verified credit, preserving the same checks and both-hop consent.

## Non-goals

No provider key on phone, BYOK, production development-credit bypass, subscription, billing, general report/summary export, assistant chat, new car scan, beta-consent reuse or new native/ad dependency in D1.

### D1 development evidence capture

This is a repair of the required phone artifact capture, within the same six files. No C1 backend change or paid call is part of this repair. `DevelopmentUsage` is a fresh allowlisted projection of C1's `SummaryUsage`: `model`, `provider`, `promptVersion`, `adapterPromptVersion`, `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningTokens`, `providerCostUsd`, `estimatedUsd`, `latencyMs`. Never retain, spread, stringify or reflect arbitrary response keys or the original HTTP object. Validate known fields before copying; unknown keys are ignored. Missing/malformed usage becomes `null`, independently of whether the structured summary passes the existing local checker. Preserve valid usage on a server fallback and on a locally rejected summary: billing may have occurred. A malformed envelope, network failure or timeout retains only locally known attempt metadata and null unknown measurements. Neither missing usage nor missing cost implies free execution.

Use C1's exact allowed model alias/canonical slug and prompt version literals (`promptVersion` `t2.10-v4` and `adapterPromptVersion` `t2.10-openrouter-v7`; usage naming any other version projects to `null`); provider must be the literal `DeepSeek`, which denotes **configured pin only**. Token counts are finite safe nonnegative integers, input <= 1,048,576 and output <= 1,024; nullable cache <= input and reasoning <= output. Missing optional cache/reasoning/cost remains `null`. Cost and estimate must be finite nonnegative numbers bounded by C1's US$1 development ceiling; latency must be a finite safe nonnegative integer. Any invalid known usage field invalidates the usage projection rather than clamping or retaining a partial untrusted object. These are development policy bounds from C1, not new OBD constants. The existing 32 KiB HTTP response bound also applies to status; no unbounded metadata string is accepted. The final evidence object contains only this finite key set, enums, numbers and the locally generated UUID, with a maximum serialized size of 4 KiB (development evidence policy); overflow yields fixed unknown/null metadata, never truncation of a response body.

Generate and validate the UUID before the HTTP attempt; accept only C1's bounded UUID spelling from the injected factory, never a request ID from server JSON. The normal phone factory remains existing `uuid.v4()`. Invalid factory output fails locally with the fixed template reason and no HTTP request. Each accepted tap with valid setup retains its ID even for unexpected HTTP responses. `requestedModel` is C1's fixed alias; `returnedModel` is the validated `usage.model` (including the canonical slug when actually returned), or `null`. `configuredProvider:"DeepSeek"`, `observedProvider:null`, and `routingEvidence:"configured-pin-only"` make the distinction explicit: C1's `usage.provider` is not a measured provider response. Do not infer an observed route, generation ID, canonical model, zero cache/reasoning/cost or successful key-limit inspection from configuration or from a checked summary. `displayCategory` is only `llm` or `template`. `failedCheck` is the Worker's failed-check word (`envelope`, `bounds`, `provider`, `json`, `shape` or `facts`) copied only from a fallback envelope whose reason is `invalid-response`; any other value, reason or an `llm` result gives `null`, and it never carries reply text. The phone's own local checker failure is not recorded (X-2026-09-29-summary-placeholders). `phoneLatencyMs` measures elapsed POST attempt time with an injected clock for deterministic fixtures, separately from backend/provider `usage.latencyMs`; it excludes the subsequent status wait.

After one POST attempt, optionally obtain a single authenticated `GET /v1/status` while the view/session is still current, using the same validated private origin and in-memory development token. This request has no body or report facts, does not inspect a provider key, invoke a model, reserve/consume credit or retry either request. Do not send status on screen open, URL/token entry, consent alone, release mode, invalid setup or duplicate tap. Bound the status attempt at two seconds (development evidence policy), with no polling/auto retry. Explicitly project only `uses` (nonnegative safe integer), `headroomMicroUsd` (integer 0–1,000,000), `enabled` (boolean); compute `chargedOrReservedMicroUsd` from validated headroom. Malformed, redirected, non-success, timed-out or unavailable status becomes `budget:null` without changing checked summary/template behavior. Budget is a post-attempt snapshot of C1's conservative local charged-or-reserved ledger, **not** actual provider spend, a refund claim, or the whole T2.10 US$5 ledger. Timeout/ambiguous billing may leave a reservation; do not turn that into an actual cost. Status completion is subject to the same withdrawal/navigation epoch check as the summary.

Show this freshly constructed evidence as selectable JSON (`Text selectable`) under a development-only "Development run metadata" heading after a current attempt completes. The owner can select/copy it manually into the laptop artifact; no clipboard/native dependency, filesystem persistence, automatic share/export or debugger is required. Include no summary/claims, template, projected facts, report/recording/garage IDs, timestamps from the report, URLs/headers, auth token, provider key, raw error, raw provider reply or free-text server reason. It is acceptable for the metadata to report honest nulls on failure. Keep one current attempt only. New attempt clears previous evidence; withdrawal, disconnect, navigation, unmount and credential edits discard evidence along with summary/auth and invalidate both pending POST and status completions. Access must not retain the envelope, usage or status after returning; the flow/UI owns only the projected current evidence. Release builds have no metadata view or status request. Do not log evidence automatically.
