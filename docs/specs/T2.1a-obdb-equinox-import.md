# T2.1a: Vendored Equinox OBDb signals and replay decoding

## Goal

Vendor the Chevrolet Equinox EV OBDb v3 signalset with its CC-BY-SA-4.0 license, import its six signals as `community`, and decode each Mode 22 signal answered in the committed 2024 Equinox spike recordings. `pnpm replay` must print a repeatable, attributed summary of those readings without claiming battery health or promoting any signal to `verified`. T2.1b adds the profile that sends the requests.

## Non-goals

- Sending CAN setup or polling commands (T2.1b), app integration (T2.8), dash-value comparison and explicit verified promotion (T2.2), or candidate signals discovered outside OBDb (T2.3).
- Treating OBDb's model-year `dbgfilter` as proof that a command cannot answer on 2024. The two own-car recordings show the opposite for the three `DACB` commands.
- Changing the read-only guard, relay, mobile app, existing recordings, or standard J1979 decoders.

## Interfaces

```ts
export type SignalTier = "community" | "verified";
export interface ObdbMode22Signal {
  id: string;
  name: string;
  module: string;        // two hex digits from OBDb hdr DAxx
  did: string;           // four hex digits from cmd {"22": ...}
  bix: number;           // zero-based bit index after the 62 DID echo
  len: number;
  mul: number;           // OBDb default 1
  div: number;           // OBDb default 1
  add: number;           // OBDb default 0
  min?: number;          // OBDb valid scaled range when supplied
  max?: number;
  unit: string;
  tier: SignalTier;      // always community at import
}
export function importObdbMode22(input: unknown): readonly ObdbMode22Signal[];
export type SignalReading =
  | { ok: true; id: string; name: string; value: number; unit: string; tier: SignalTier; ecu: string }
  | { ok: false; id: string; reason: "header" | "echo" | "negative" | "length" | "format"; ecu: string };
export function decodeObdbMode22(did: string, frame: Frame, signals: readonly ObdbMode22Signal[]): readonly SignalReading[];
export async function replayRecording(lines: readonly RecordingLine[], options?: { signals?: readonly ObdbMode22Signal[] }): Promise<string[]>;
```

The importer validates an OBDb v3 **subset** with existing `zod`: `commands[]`, `hdr: DAxx`, `cmd: {"22": four-hex-digit DID}`, `signals[]`, and the `fmt` fields present in this Equinox file (`bix`, `len`, `mul`, `div`, `add`, `min`, `max`, `unit`). Unsupported service/header/format fails closed with an actionable error; this is not a universal OBDb importer. Preserve source signal order. Reject duplicate IDs or duplicate `(module,DID,id)` entries. `bix` is measured from the first data bit **after** `62 <DID>`; absent is zero. Extract unsigned, big-endian bits, then calculate `(raw * mul) / div + add`; reject non-finite operands, zero divisor, and values outside a supplied valid scaled range. Return `community` regardless of `dbgfilter`. No `verified` value is created by an import or a mere positive response. Verification and evidence-driven promotion belong to T2.2.

For a Mode 22 response, accept only the `18DAF1<module>` reply header and exact `62 <DID>` echo, then require enough bytes for each signal's bit span. A `NO DATA`, negative, malformed, truncated, wrong-module, or wrong-DID response yields no successful reading. Existing ISO-TP reassembly stays responsible for frames. The replay CLI may select the vendored Equinox signalset only when recording meta identifies `chevrolet-equinox-ev-2024`; any other recording retains current output. Keep VIN redaction unchanged. The CLI output identifies each signal ID, number, unit, tier, and ECU and remains stable enough to diff.

### Isolated tests, only for parser failures not present in the recordings

Failure modes are listed **before code**; one test per listed mode, and no test solely mirrors the happy-path importer shape already observed by E2E:

1. Unsupported service/header or malformed DID could cause the importer to create a sendable unsafe or misaddressed definition → one table-driven rejection test for those invalid command forms.
2. Zero/non-finite divisor, bit span outside the response, or a scaled value beyond OBDb's supplied valid range could yield `NaN`, `Infinity`, or a plausible false reading → one rejection/invalid-reading test for invalid arithmetic/span/range.
3. Duplicate IDs could make one reading silently replace another → one duplicate-ID rejection test.
4. Wrong module header or wrong DID echo could assign another ECU's bytes to a named battery signal → one wrong-source/echo decoder test.

## Risks / open questions

- **Largest risk:** upstream `dbgfilter` metadata conflicts with observed 2024 responses; importer and replay must keep the source data intact while decoding the observed replies. The pinned source pair is now available in the temporary upstream clone.
- Upstream's `dbgfilter` excludes the 2024 `DACB` commands, while the own-car recordings show they answer. Keep that metadata attributed but decode the observed responses. Do not rewrite upstream JSON here; T2.2 handles upstream correction.
- OBDb's `33E5` is at most 25.5 V by its format, and our car returned `NO DATA`; no pack voltage claim is permitted from this signal.
- Output numeric formatting must avoid false precision; keep unrounded `value` in code and format deterministically for replay.

## Decisions

- Use commit `15ee122df435d541d928dac8e7532bf43e39bdd4`, the revision already cited in the repo and now verified by exact blob hashes. The parent records any different source pin before implementation.
- Import alone never promotes a signal. T2.2 records dash/plausibility evidence and deliberately promotes individual definitions with recording citations.
