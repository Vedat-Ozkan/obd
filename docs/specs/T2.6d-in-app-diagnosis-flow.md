# T2.6d: Selected-car battery diagnosis and in-app report history

## Goal

After T2.6c is independently approved, wire the fresh scan into the now-released mobile app. From a selected, verified 2024 Equinox EV garage entry (`mine` or `checked`), the user connects the Veepeak and runs one read-only battery diagnosis. The app keeps the scan privately, builds the T2.6a typed report from those bytes, saves it under that **specific garage entry ID**, and opens the report. The same entry's history and detail reopen after app restart; another entry of the same catalog model shows only its own reports. Capacity reads **NOT MEASURED** and battery health **not assessed** without charge evidence. This is the UI/action successor to unapproved T2.6b; it does not erase T2.6b's findings or repair count.

## Non-goals

- No external report file, PDF, Markdown export, SAF folder, share sheet, backend, cloud sync, or pre-purchase product name. A private JSON history and private scan recording are internal persistence/evidence, not a user report export.
- No T2.4 charge log/estimate, pack-voltage inference, new health threshold, new verified vehicle year, signal-tier promotion, VIN request, Mode 04, or other write.
- No change to T0.9b's separate one-and-done debug capture/codes report exports; do not redirect battery reports through `finishRun`.
- No new dependency, native module, app config change, or dev-client rebuild.

## Interfaces

Keep the approved T2.6a `BatteryDiagnosisReport`, `batteryDiagnosisFromRecording`, `renderBatteryDiagnosis`, `createBatteryReportHistory`, and `batteryReportsDocumentStore` contracts. Keep T2.6b's `runBatteryDiagnosisScan`, `batteryReportRows`, `removeGarageVehicleWithReports`, `hasEquinoxSocFingerprint`, and `keepPrivateBatteryScan`, subject to the T2.6c retry repair. Add one pure application action so the persisted result, not React state, is the source of truth:

```ts
// apps/mobile/src/batteryDiagnosisFlow.ts
export async function runAndSaveBatteryDiagnosis(input: {
  entry: GarageVehicle;
  transport: Transport;
  recording: RecordingBuffer; // already started with this connection's truthful meta
  scannedAt: string;
  keepScan: (garageId: string, at: string, jsonl: string) => string | Promise<string>;
  history: ReturnType<typeof createBatteryReportHistory>;
  importedSignals: readonly ObdbMode22Signal[];
  getInterruption: () => "cancelled" | "disconnected" | undefined;
  onProgress: (message: string) => void;
}): Promise<
  | { status: "saved"; report: BatteryDiagnosisReport; recording: string }
  | { status: "no-fingerprint"; recording: string; scanStatus: "complete" | "partial"; reason: string }
  | { status: "stopped"; cause: "cancelled" | "disconnected"; recording: string; reason: string }
>;
```

The action refuses any entry except `catalogId === "chevrolet-equinox-ev-2024"` with a verified catalog row. It calls the T2.6c runner once, **keeps the private recording before** building/saving a report, uses that returned private label as report provenance, builds only from the just-frozen JSONL, and saves only if `hasEquinoxSocFingerprint(report)` holds. A partial scan with a valid sourced SOC may be saved as `partial`, never `complete`; a scan with no verified `CB` SOC is retained privately with a visible no-report reason. A private write, replay, or history write failure is surfaced; never claim the report was saved. `createBatteryReportHistory.save` rechecks the actual garage row to prevent attachment to a removed or mismatched entry. The action does not export the recording or report.

**Repair round 1 cancellation contract:** `getInterruption` reads a mutable UI ref; it is `undefined` for an ordinary run. A Cancel tap or unexpected BLE disconnect sets its respective value synchronously **before** initiating transport close. The action reads it immediately after the runner settles and **before** announcing `Keeping private scan`, replaying the bytes, or writing history. This is the acceptance boundary: if it is set, append a truthful interruption meta note to the already recorded bytes, keep that scan privately, and return `stopped` with its cause and private recording label. Do not build or save a report, even if the final response was already received and the runner returned `complete`. The earlier runner meta may still describe the acquired bytes; the later interruption note and `stopped` result describe the abandoned diagnosis. A failed private keep throws and must never claim a kept scan. Once `Keeping private scan` is announced, the UI closes cancellation synchronously; later taps are ignored and must not display “Cancelling.” Do not retroactively relabel a committed report. This adds no new OBD command or scan-runner change.

**Repair round 2 close-rejection contract:** The current `runBatteryDiagnosisScan` awaits `Elm327Session.close()` in `finally`; `BleTransport.close()` awaits `cancelConnection()`, which can reject. In that case the scan runner rejects before adding its final meta line or returning `DiagnosisRun`, although the already-started `RecordingBuffer` still holds the observed TX/RX bytes. `runAndSaveBatteryDiagnosis` must catch this runner rejection as a distinct unsettled-scan path. Read `getInterruption()` before the `Keeping private scan` boundary, append a truthful close-failure meta note to the buffer and, if set, an interruption note with `cancelled` or `disconnected`; announce `Keeping private scan`, then call `keepScan` exactly once with `recording.toJsonl()`. Never replay those bytes into a report or write history on this path, even if the last response was recorded. If interrupted, return the existing `stopped` result with its cause and private label. If no interruption was signaled, surface the close error with the retained private label so the UI says the diagnosis failed and where its evidence is; do not return `saved`, `no-fingerprint`, or `complete`. A failed private keep still throws and must never claim retention. Do not infer an interruption merely from a close rejection. No change to `runBatteryDiagnosisScan`, the approved T2.6c init/scan contract, BLE transport, OBD commands, or the public action signature is needed for this repair.

`App.tsx` passes the **selected `GarageVehicle.id`** into its connection/diagnosis view, rather than relying on the existing hard-coded catalog vehicle. Give `EquinoxConsole` (or a small contained diagnosis view using its same BLE connection) one Run battery diagnosis action while connected. Close any debug `ConsoleSession` first; disable Send, Run capture, Run codes report, Disconnect, and Back while diagnosis owns the transport. Provide an explicit Cancel that closes the transport, awaits the runner's settled result, keeps that recording, and only then leaves the running state. `Elm327Session.close()` closes that BLE transport on completion or failure, so clear the UI connection state and require reconnection for another run; never leave a stale “Connected” label or concurrent writer. An unexpected BLE disconnect follows the same retained-recording path and does not create a completed report. The UI must never label a cancelled run complete. Keep T0.9b debug capture/share behavior separate.

For the repair, the UI must use one synchronous active-scan ref for the Cancel handler and the `Keeping private scan` boundary, plus the interruption ref passed to the action. On an accepted tap, set `cancelled` and disable another tap before calling `transport.close()`; remain in the running state until the action has kept the recording. On an unexpected disconnect during the active scan, set `disconnected` before closing. Handle the action's `stopped` result with a cause-specific message and retained private path, never with a saved or complete-report message. The action alone decides whether a diagnosis was saved; React state cannot override that result.

The garage card shows a per-entry report count/history action and blocks Remove through `removeGarageVehicleWithReports` when reports exist, with its retention message. An ownership toggle retains reports. A saved report opens in a detail view rendered from the persisted report using `renderBatteryDiagnosis`; the list is scoped by ID and newest first. Loading a corrupt/future report history fails visibly rather than showing an empty history. On restart, read the private history before showing report counts/details. Update the verified Equinox availability copy to reflect that battery diagnosis is available after a fresh scan; beta rows remain unavailable. The UI must display source/tier and missing-data limits, including `community` cell values, adapter-supply context, codes, `capacity: NOT MEASURED`, and health not assessed.

## Risks / open questions

- Largest risk: `App.tsx` currently owns the BLE connection for its debug console, while the core session closes the transport at the end of a diagnosis. The UI must prevent simultaneous writers, preserve the partial recording on disconnect/cancel, and show disconnected/reconnect state truthfully. A passing Node replay alone cannot verify Android lifecycle behavior.
- Repair round 1 risk: the last reply can arrive before the BLE close promise resolves. The cancellation boundary must be checked in the production action after that await but before private keep/report persistence. The deferred-close replay proves this ordering and output; only the owner phone run can verify actual tap and BLE timing.
- Repair round 2 risk: an Android BLE close can reject after the recording wrapper has unsubscribed, so the runner's `finally` suppresses its `DiagnosisRun`. The action must retain the `RecordingBuffer` directly on this exceptional path; its report-building path must remain closed. Synthetic replay proves retention and labeling, while the owner phone run remains the only hardware lifecycle check. No scan-runner or core change is specified, so the T2.6c approval stands; the reviewer still reruns its affected regression artifacts as an integration gate.
- T0.9b is committed at HEAD `1b4364b`, so `App.tsx` is available, but its separate capture/export flow and owner phone checklist remain as recorded in `docs/task-runs/T0.9b.md`.
- The combined phone diagnosis sequence has no committed redacted recording. Synthetic E2E and real Mode 22 tails are mandatory software evidence, but the manual car run remains a separate hardware-only gate. T2.4's charge-log/capacity gate remains open.
- The parent's authorization decision for a **new material-revision implementation/review cycle after T2.6b's 2/2 repair cap** also applies before starting this ordered stage. Do not treat the owner's “Claude finished” handoff as an approval of the rejected scan code.
