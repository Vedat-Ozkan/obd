# T2.3a: Equinox EV discovery session (read-only DID scan and watch)

## Goal

A one-command laptop tool, `uv run tools/spike/discover.py`, that the user runs once at the 2024 Equinox EV (Ready, Park, home charger within reach) and that writes one immutable recording `fixtures/recordings/chevrolet-equinox-ev-2024/<date>-discovery.jsonl` in the standard recording format. In about 25 minutes it runs three phases. (A) A standard sweep: supported-PID bitmaps, every flagged Mode 01 PID, and Mode 09 per module. (B) A read-only Mode 22 DID scan with physical addressing over fixed ranges on the BECM (`CB`) and DMCM (`17`), plus `F180`–`F1FF` on all five known modules. The scan has a hard time budget. (C) A watch phase that repeatedly polls every DID that answered positively on `CB` and `17`, plus `ATRV`. Meanwhile the user presses Enter to mark five states: idle baseline, heater max on, heater off, plugged in and charging, unplugged. The test-visible outcome here is the tool plus an offline pytest suite that uses a fake BLE client and passes with no Bluetooth. The suite proves that the tool cannot send anything except allowlisted AT commands and service `01`/`09`/`22` reads, and that it never requests the VIN. The hardware-visible outcome, which is NOT RUN until the user's session, is a recording from which a pack-current candidate can be judged. That candidate is a value that changes with heater load and flips sign when charging, the Gate B plausibility criterion in `docs/PLAN.md` T2.3. The recording is then the citation for every DID it contains (AGENTS.md hard rule 1).

## Non-goals

- No decoding or analysis in the tool. It classifies each Mode 22 reply only as positive, negative, NO DATA, or other, so it can build the watch list and print progress. Deciding which DID is pack current, and its scaling, is post-session analysis. That goes in the run card, and later T2.3 / T2.1 profile work.
- No Gate B decision by the tool. The run card gets a Gate B section with the PLAN criteria, marked `NOT DECIDED`. Per PLAN T2.3 the owner approves every signal.
- No services other than `01`, `09`, `22`. Never `04`, `10`, `11`, `14`, `27`, `28`, `2E`, `2F`, `31`, `3E`, or anything else. No session change: DIDs that need an extended session stay undiscovered, and that is accepted.
- No VIN reads. `0902` and `22 F190` are refused by the allowlist even if a bitmap flags them.
- No AT commands beyond the explicit list under Interfaces. In particular no `ATST` change, no `ATAT` change, no `ATAR`, no `ATMA`, no `ATI` (the `ATZ` banner already carries the version string, recording line 2).
- No multi-PID or multi-DID batching. One PID or one DID per request.
- No resume. An interrupted run is kept as-is and the user reruns into a new file.
- No changes to `tools/spike/spike.py`. Its behavior stays under `docs/specs/T0.2-hardware-spike.md`.
- No product code under `packages/*/src`, `apps/`, or `tools/hil-bridge/`. The one exception, a test-timeout argument in `packages/obd-core/test/recordings.test.ts`, is explained under Files.
- No changes to `docs/ELM327.md`. Adding the `0900` support query and the bitmap bit convention to it, citing the discovery recording, is a follow-up (open question 1).
- No MCP/relay/phone path. T2.3 proper uses the phone relay (ADR-013). This is a laptop spike like T0.2.

`tools/spike/discover.py` (PEP 723 header identical to `spike.py`: `requires-python >=3.11`, `dependencies = ["bleak>=0.22"]`; `bleak` imported only inside `main`). Public names, and no more:

```python
from go import ask, find_dongle, next_out_path
from spike import CARS, CHUNK, CODEC, SERVICE, Recorder

CAR = CARS[2]                                   # "chevrolet-equinox-ev-2024"
MODULES = ("17", "28", "40", "45", "CB")        # recording line 84 (090A replies)
INIT = ["ATZ", "ATE0", "ATL0", "ATS0", "ATH1", "ATSP0", "ATDPN", "ATRV"]
MODE01_BITMAPS = [0x00, 0x20, 0x40, 0x60, 0x80, 0xA0, 0xC0]
SCAN = [("CB", 0x2000, 0x2FFF), ("CB", 0x4000, 0x43FF), ("CB", 0x8300, 0x83FF),
        ("17", 0x2000, 0x2FFF), ("17", 0x4000, 0x43FF),
        *[(m, 0xF180, 0xF1FF) for m in MODULES]]   # scanned in this order; F190 skipped
WATCH_MODULES = ("CB", "17")
STATES = ("idle baseline", "heater max on", "heater off", "plugged in and charging", "unplugged")
SCAN_BUDGET_S = 15 * 60       # phase B hard stop
WATCH_CYCLE_S = 15            # target upper bound for one watch cycle
CMD_TIMEOUT_S = 5             # wait for '>' per command (longest seen: 2.3 s, 0100 with SEARCHING...)

def check_allowed(cmd: str) -> None: ...
    # The single allowlist. Raises ValueError unless cmd is EXACTLY one of:
    #   an AT command in ALLOWED_AT (below), or
    #   "01" + 2 hex digits, or
    #   "09" + 2 hex digits, except "0902", or
    #   "22 " + 4 hex digits, except "22 F190".
    # Upper-case hex only; no other spacing; no trailing '\r' (send() appends it).
ALLOWED_AT = {"ATZ", "ATE0", "ATL0", "ATS0", "ATH1", "ATSP0", "ATSP7", "ATDPN", "ATRV",
              "ATCP 18", "ATFCSD 300000", "ATFCSM 1",
              *(f"ATSH DA{m}F1" for m in MODULES), *(f"ATCRA 18DAF1{m}" for m in MODULES),
              *(f"ATFCSH 18DA{m}F1" for m in MODULES)}

def bitmap_replies(reply: str, service: int, pid: int) -> dict[str, int]: ...
    # module id -> 32-bit bitmap, from single-frame lines "18DAF1<mm>06<service+0x40:02X><pid:02X><8 hex>";
    # every other line (SEARCHING..., stray frames after BUFFER FULL, other headers) ignored.
def flagged(base: int, bits: int) -> list[int]: ...
    # PIDs base+1..base+0x20 whose bit is set, MSB of the first byte = base+1 (J1979 convention; see Sources).
def classify_22(reply: str, module: str, did: int) -> str: ...
    # "positive": a line from 18DAF1<module> that is a single frame "0L 62 <did>" or a first frame "1L LL 62 <did>";
    # "negative": a line from 18DAF1<module> "03 7F 22 xx"; "nodata": NO DATA; else "other".
    # The DID echo check means a late reply to an earlier DID is never counted as positive for this one.

class Elm:
    def __init__(self, client: object, write_char: object, notify_char: object,
                 without_response: bool, rec: Recorder) -> None: ...
    async def start(self) -> None: ...               # start_notify; rx callback records every chunk as an rx line
    async def send(self, cmd: str) -> str: ...
    # check_allowed(cmd) FIRST (raises before any byte is written); then same framing as spike.py:
    # 20-byte ISO-8859-1 chunks, one tx line "cmd\r", wait for '>' up to CMD_TIMEOUT_S, return the rx text.
    # On timeout: meta note "timeout waiting for '>' after <cmd>" and return "".
    # On any BaseException while waiting (Ctrl+C, BLE drop): meta note
    #   "timeout waiting for '>' after <cmd> (interrupted: <exception type>)", then re-raise.
    # On "CAN ERROR" in the reply: wait 0.5 s, resend once, return the second reply.

async def select(elm: Elm, module: str) -> None: ...  # ATSH DA<m>F1, ATCRA 18DAF1<m>, ATFCSH 18DA<m>F1
async def sweep(elm: Elm, rec: Recorder) -> None: ...  # phase A
async def scan(elm: Elm, rec: Recorder) -> dict[str, list[tuple[int, float, bool]]]: ...
    # phase B; returns {module: [(did, ms, single_frame), ...]} for positives on WATCH_MODULES
async def watch(elm: Elm, rec: Recorder, positives: dict[str, list[tuple[int, float, bool]]],
                marks: "asyncio.Queue[str]") -> None: ...  # phase C
def main() -> None: ...
```

Behavior per phase follows. Every command goes through `Elm.send`, one in flight at a time, as in spike.py.

**Setup.** Prompt `Battery % on the dash` and `Outside temperature in C` (go.`ask`). `find_dongle()`. `next_out_path(CAR, <local date>, "discovery")`. Connect, pick write and notify characteristics exactly as spike.py does, with the same missing-characteristic dump and exit. First meta line: the spike.py keys (`car`, `dongle`, `note`, `script: "tools/spike/discover.py"`, `bleak`, `platform`, `write_char`, `notify_char`, `mtu`) with `note = "ready, park, dash SOC <n>%, ambient <c> C"`. Before connecting, print the plan: phases, request counts, and estimated minutes at 75 ms per request.

**Phase A: standard sweep (under 1 min expected).** Meta `{"phase": "A"}`.
1. Send `INIT` in order. Each of `ATE0 ATL0 ATS0 ATH1 ATSP0` must contain `OK`, otherwise write meta and stop. `ATZ`, `ATDPN`, `ATRV` replies are only recorded.
2. Functional Mode 01 bitmap walk under `ATSP0`, with no header or filter set. Send `0100`. Keep sending the next entry of `MODE01_BITMAPS` (`0120`, `0140`, …, at most `01C0`) only while at least one module's previous bitmap has its lowest bit set. If `0100` yields no bitmap at all (for example `UNABLE TO CONNECT`), write meta `note: "no Mode 01 reply; is the car in Ready?"` and stop.
3. Build the union of all flagged PIDs, excluding the bitmap PIDs themselves. Send each one once, ascending, as `01<pid>`. Write meta `{"phase": "A", "mode01_pids": [...]}` first, so the request list can be traced to the bitmaps in the same file.
4. `ATSP7`, `ATCP 18`. Then for each module in `MODULES`: `select(m)` (after the first `select` only, also `ATFCSD 300000` and `ATFCSM 1`, matching the order in recording lines 129–150), `0900`, then `09<t>` for every infotype `t` in `0x01`–`0x1F` flagged by that module's `0900` bitmap, plus `0x0A` in every case, never `0x02`. There is no `0920` walk.

**Phase B: Mode 22 scan (hard stop at `SCAN_BUDGET_S`).** Meta `{"phase": "B", "plan": [["CB","2000","2FFF"], ...], "budget_s": 900, "skip": ["F190"]}`. For each `SCAN` entry, in order: meta `{"phase": "B", "module": m, "range": "2000-2FFF"}`, then `select(m)`, then `22 <did>` for every DID in the range except `F190`. The tool records the reply, classifies it with `classify_22`, and times it (monotonic, send to return). When the budget is spent, it finishes the current request and stops the whole phase. There are no skip heuristics inside a range: a silent module costs its NO DATA time and nothing more. At the end, meta `{"phase": "B", "stopped_early": bool, "last": ["CB","2A13"] | null, "counts": {module: {"positive": n, "negative": n, "nodata": n, "other": n}}, "positives": {module: ["27C6", ...]}}` covering all five modules.

**Phase C: watch (about 6–8 min, user-paced).** Build the watch list from the positives on `CB` then `17`. Order it single-frame first, then multi-frame, keeping discovery order within each group. Keep DIDs while the sum of their phase-B times stays within `WATCH_CYCLE_S`. Meta `{"phase": "C", "watch": {"CB": [...], "17": [...]}, "dropped": [...]}`, then meta `{"phase": "C", "state": "idle baseline"}`. Each cycle is `ATRV`, `select("CB")`, its DIDs, `select("17")`, its DIDs. Between cycles, if `marks` has an item, write meta `{"phase": "C", "state": <next of STATES>}`. After the Enter that follows `unplugged`, write meta `{"phase": "end"}` and disconnect. The console shows the current state, the next instruction, time in state, and cycles in state, and suggests holding each state for at least 60 s and at least 3 cycles. Instructions shown (wording is the implementer's):
- idle baseline: "HVAC off, car in Ready, Park. After about 60 s set the heater to max (hot, fan high) and press Enter once hot air flows."
- heater max on: "After about 60 s turn the heater off and press Enter."
- heater off: "After about 60 s plug in the home charger. Press Enter once the car/charger shows it is charging. Leave the laptop in the car."
- plugged in and charging: "After about 90 s unplug the charger and press Enter."
- unplugged: "After about 60 s press Enter to finish."

`main` feeds `marks` from a stdin reader task that reads exactly `len(STATES)` lines with `asyncio.to_thread(sys.stdin.readline)` and then stops, so no blocked reader thread survives to `asyncio.run` shutdown.

**Progress and ETA.** During phase B, print one line at most every 5 s: module, range, done/total for the range, counts, average ms over the last 256 requests, phase-B ETA (remaining requests × average, capped at the time left in the budget), and a warning if the projection shows the budget will cut ranges. Phase A prints one line per step. Phase C prints as described above.

**Abort rules.** An `LV RESET` or `UNABLE TO CONNECT` reply after phase A step 2 makes the tool write meta `note: "aborted: <reply>"` and exit non-zero (`docs/ELM327.md` §Responses: re-init / surface). It never retries silently. Every other outcome is recorded and the run continues.

**Recording contract.** Unchanged from `docs/specs/T0.2-hardware-spike.md` (the tool uses `spike.Recorder`). The new meta keys (`phase`, `mode01_pids`, `plan`, `budget_s`, `skip`, `module`, `range`, `stopped_early`, `last`, `counts`, `positives`, `watch`, `dropped`, `state`) are free-form meta, which T0.3's schema passes through. Every `tx` is followed by its `rx` before the next `tx`, or by a meta note starting `timeout waiting for '>'`, which is what `packages/obd-core/test/recordings.test.ts` requires.

## Time budget

Measured basis: 75 ms per physical Mode 22 request tx-to-tx (S1 152–162), ~100 ms per functional Mode 01 request with five modules answering (S1 42–62), 30 ms per AT command (S1 6–20), 243 ms per NO DATA (S1 144).

| Step | Requests | Estimate |
|---|---|---|
| Prompts, BLE scan (10 s), connect | — | ~1 min |
| A: init + `0100` with SEARCHING | 9 | ~3 s |
| A: bitmaps `0120`–`0160` (+`0180` if flagged) | 3–4 | <1 s |
| A: flagged Mode 01 PIDs | 47 + ≤31 | ~5–8 s |
| A: `ATSP7`/`ATCP` + 5 × (3 AT + `0900` + ≤6 infotypes) | ~55 | ~5 s |
| B: `CB` 2000–2FFF | 4096 | 5.1 min |
| B: `CB` 4000–43FF | 1024 | 1.3 min |
| B: `CB` 8300–83FF | 256 | 0.3 min |
| B: `17` 2000–2FFF | 4096 | 5.1 min |
| B: `17` 4000–43FF | 1024 | 1.3 min |
| B: `F180`–`F1FF` × 5, minus `F190` | 635 | 0.8 min |
| B total | 11,131 | 13.9 min at 75 ms (12.1 at 65 ms); hard stop 15 min |
| C: watch, 5 states × 60–90 s + walking to the charger | cycles ≤ 15 s | 6–8 min |
| Total | | about 21–25 min, within the 30 min budget |

The budget does not fit if a present module answers unsupported DIDs with NO DATA instead of `7F 22 xx`. At 243 ms per request, phase B would need about 45 min. The hard stop keeps phase B at 15 min regardless, and the fixed order decides what is cut: `CB` 2000–2FFF is covered almost entirely (15 min / 243 ms ≈ 3,700 DIDs, through about `2E70`), and everything after it is not. The phase-B end meta line and the console say exactly what was covered. Trim recommendation if the user wants coverage over depth: drop `17` 2000–2FFF (5.1 min), which is the largest non-BECM block (open question 5). Nothing in the tool shortens NO DATA waits (see open question 2).

## Risks / open questions

Risks:

- **Biggest: phase-B rate.** The plan assumes present modules answer unsupported DIDs with a fast `7F 22 xx`. If they stay silent (NO DATA, ~243 ms), the 15 min stop cuts everything after `CB` 2000–2FFF. The ranges that motivated the scan for pack current may then be uncovered, and a second session is needed. The console ETA shows this in the first minute of phase B, so the user knows early.
- Pack current may not be in any scanned range, or may need an extended session. Service `10` is forbidden, so that DID would simply not answer. A negative Gate B from this session is a valid outcome: the PLAN fallback (charger-reported kWh) applies.
- The car may not charge while in Ready, and turning it off may put the modules to sleep (all NO DATA). Either outcome is recorded; see open question 6.
- If the car auto-powers-off or BLE drops mid-run, the result is a partial recording that ends with the interrupted-timeout meta note. It still replays, and the user reruns into `-discovery-2.jsonl`. There is no resume.
- After a per-command timeout, a late `>` can satisfy the next wait early, so a `7F` (which carries no DID) could be attributed to the wrong DID. Positives are protected by the DID echo check. The recording is the authority.
- About 18k `tx` lines, roughly 2–4 MB. The replay test goes from ~40 ms to ~20 s per `pnpm test` and CI run while the file is in the tree. That is handled by the timeout change, but it is a lasting cost.
- About 13 requests per second of physical Mode 22 reads to the BECM and DMCM for 15 minutes. These are reads, which AGENTS.md rule 5 treats as safe, and scan tools do the same. There is no repo source for any rate limit, so none is claimed either way.
- The watch-list cap assumes a current signal fits a single frame. If it is only inside a long multi-frame DID and more than 15 s of DIDs answered, it could be dropped. The dropped list is in the meta line, and the phase-B reply is still in the recording.
