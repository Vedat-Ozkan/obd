# T2.6a: In-app battery diagnosis report model and recording replay

## Goal

Create a deterministic, typed battery diagnosis report from one 2024 Equinox EV scan. The report groups observed SOC, cell voltage and spread, 12 V supply observations, and the T0.7 codes section; every displayed number names its scan command, ECU, signal tier and recording. It says **capacity: NOT MEASURED** and **battery health: not assessed** when no completed charge evidence exists. Add private local report history keyed by the stable garage entry ID. A CLI replays a committed redacted Equinox recording through `Elm327Session` and generates a repeatable report artifact. This is the data/storage stage for the later screen and fresh-scan flow in T2.6b.

## Non-goals

- No PDF, Markdown export/share action, externally visible report file, backend, cloud sync, or “pre-purchase report” product name. The CLI artifact is a development verification output, not an app export.
- No capacity estimate, health score, pass/fail verdict, cell fault threshold, pack voltage, current, or group-voltage decode. T2.4 charge evidence and independent signal validation are absent from committed redacted fixtures.
- No promotion of OBDb cell signals: `EQUINOXEV_HVBAT_C_V_AVG/MIN/MAX` stay `community`; only the two recorded SOC signals have the T2.2a `verified` overlay. A positive response alone does not promote a signal.
- No new vehicle command, write guard change, recording edit, app UI, or change to the active T0.9b files.
- No combined report built by joining observations from different recording sessions. One report describes one scan and one garage entry.

## Interfaces

Add package exports so app and replay code use the same pure code. `obd-core` also exposes its existing `./elm/session` and `./transport/replay` through package subpaths; no implementation there changes:

```ts
// obd-core/vehicles (new public subpath): existing named exports only
export { genericProfile, equinoxEv2024Profile, scanMode22Profile };
export { importObdbMode22, decodeObdbMode22, withEquinoxEv2024Evidence };
export type { Mode22Outcome, SignalReading, ObdbMode22Signal };

// obd-battery/report (new public subpath)
export interface ReportSource { recording: string; command: string; ecu: string }
export interface ObservedBatterySignal {
  id: string; name: string; value: number; unit: string;
  tier: "verified" | "community"; source: ReportSource;
}
export interface BatteryDiagnosisReport {
  version: 1;
  garageVehicleId: string; // stable GarageVehicle.id; never catalog ID in its place
  catalogId: "chevrolet-equinox-ev-2024";

  recording: string; // same one-scan source for all observations
  scanStatus: "complete" | "partial";
  signals: readonly ObservedBatterySignal[];
  cellSpread?: { volts: number; tier: "community"; min: ReportSource; max: ReportSource };
  twelveVolt: TwelveVoltReport;
  codes: CodesReport;
  capacity: { status: "not-measured"; reason: string };
  health: { status: "not-assessed"; reason: string };
}
export function buildBatteryDiagnosis(input: {
  garageVehicleId: string; catalogId: "chevrolet-equinox-ev-2024";
  scannedAt: string; recording: string; scanStatus: "complete" | "partial";
  signalReadings: readonly { reading: SignalReading; command: string }[];
  twelveVolt: TwelveVoltReport; codes: CodesReport;

export function renderBatteryDiagnosis(report: BatteryDiagnosisReport): string;
export function parseBatteryDiagnosis(value: unknown): BatteryDiagnosisReport;
export function batteryDiagnosisFromRecording(
  jsonl: string,
  input: { garageVehicleId: string; catalogId: "chevrolet-equinox-ev-2024";
    scannedAt: string; recording: string; scanStatus: "complete" | "partial" },
  importedSignals: readonly ObdbMode22Signal[],
): Promise<BatteryDiagnosisReport>;

// apps/mobile/src/batteryReports.ts (pure app flow; no Expo import)
export interface ReportTextStore { read(): Promise<string | undefined>; write(text: string): Promise<void> }
export function createBatteryReportHistory(store: ReportTextStore, garage: {
  load(): Promise<GarageState>;
}): {
  load(): Promise<void>;

  save(report: BatteryDiagnosisReport): Promise<void>;
  hasReports(garageVehicleId: string): Promise<boolean>;

```

`batteryDiagnosisFromRecording` is the shared **pure public entry point** for the app and fixture CLI. It parses the single JSONL, verifies the Equinox meta, replays its TX/RX through `Elm327Session` + `ReplayTransport` (no retries), applies the existing Equinox evidence overlay to the supplied imported OBDb definitions, gathers Mode 22 decodes and `ATRV` observations, and obtains `codesReportFromRecording` from the **same** JSONL. It then calls `buildBatteryDiagnosis`. This prevents the phone and CLI from implementing different decode rules. `buildBatteryDiagnosis` accepts only `reading.ok === true` decoded by the existing OBDb decoder, and records the actual `22 <DID>`/ECU plus the single scan's recording label. It does not accept free-form numeric observations from the UI. It keeps both SOC readings distinct, with their tier and provenance. It calculates spread only from valid min/max readings returned by the **same** `CB/2AF5` reply, and labels the result `community`. A missing, failed, or mismatched read renders “not read” or “unavailable,” never zero or normal. The full `CodesReport` is retained; the renderer uses the existing `renderCodesReport` so empty/unknown code data is not presented as “no codes.” The existing `buildTwelveVoltReport` and renderer preserve the distinction between adapter supply and 12 V battery health. `parseBatteryDiagnosis` validates loaded JSON at the package boundary, including finite values, tiers, source/garage IDs, capacity/health status, and the nested report shape; malformed or future versions must fail visibly.

The Node-only `packages/obd-battery/scripts/battery-diagnosis.ts` accepts exactly one committed `*.redacted.jsonl` path and explicit `--garage-id` and `--scanned-at` inputs. It reads the checked-in Equinox OBDb signalset, calls the same pure `batteryDiagnosisFromRecording` as the app, and prints only `renderBatteryDiagnosis`; no VIN or raw response bytes. On replay mismatch, malformed input, or no Equinox meta, it exits nonzero. The script does not write a report to the fixture tree.

`createBatteryReportHistory` stores a versioned JSON document in private app storage. Before each save it loads the actual garage and rejects a missing entry or one whose `catalogId` differs from the report. Two garage rows with the same catalog model retain separate histories by their `GarageVehicle.id`. History is newest first with stable ordering on equal timestamps. A malformed/future history file fails visibly and is never replaced by an empty one. Mutations are serialized and publish in-memory state only after the store write succeeds. The Expo adapter writes a complete pending file then moves it over `battery-reports.json`, following the existing garage adapter pattern; it does not claim native atomic rollback. No SAF picker, share sheet, or public file URI is involved. `hasReports` lets T2.6b block deletion of a garage entry until a separate reviewed deletion/retention design exists, avoiding silent loss of the only copy.

## Risks / open questions

- Largest risk: a plausible cell voltage is still `community` evidence. No spread threshold or fault diagnosis is supported by the current committed recordings. T2.2b needs a distinct-SOC run and independent cell check before tier promotion.
- The two spikes have Mode 22 plus only part of the later T0.9 codes list. They prove report rendering from one real scan, not the exact full new phone-scan sequence; T2.6b needs an owner car recording for that final hardware acceptance.
- The original PLAN T2.6 charge-log verification and capacity milestone remain open until T2.4 produces a charge log and estimator. This sub-spec cannot close them.
- The user authorized the in-app battery diagnosis name and deferred PDF export to beta. The parent must amend PLAN/ARCHITECTURE/DECISIONS; this architect role does not edit those shared documents.

## Decisions

- Owner, 2026-09-24: the feature is “battery diagnosis” and produces a report kept inside the app under the selected garage car; PDF export is deferred to beta. A tap starts a **fresh scan**. The parent recorded this answer.
- Implementation order: T2.6a model/replay first; T2.6b app scan/history only after T0.9b releases `App.tsx`. No report is built from a separate car/session's data.
