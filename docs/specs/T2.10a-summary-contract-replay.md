# T2.10a: Pure summary contract, number check, and replay evidence

Order: first of four T2.10 stages. This stage can proceed while T2.9 owns mobile and beta-backend files. It makes no paid call.

## Goal

Given a typed `BatteryDiagnosisReport` built from one committed Equinox recording, produce a minimal, VIN-free model request and validate a saved structured response before displaying it. A valid response yields a plain-language summary with cited report fields; any malformed, unsupported, or wrong-number response yields the existing deterministic `renderBatteryDiagnosis(report)` text. Emit a repeatable replay artifact showing both paths.

## Non-goals

- No provider HTTP call, API key, backend, ad, credit, phone UI, subscription, training, or hardware request.
- No new diagnosis, capacity estimate, or claim that a community signal is verified.
- No change to T2.9, recordings, `obd-core`, report calculations, or the battery template.

## Interfaces

```ts
// obd-assist/summary (pure TS; named exports)
export interface SummaryFact {
  id: string; label: string; value: string; unit?: string;
  tier?: "verified" | "community"; status?: string;
}
export interface SummaryRequest {
  version: 1; promptVersion: "t2.10-v4";
  facts: readonly SummaryFact[]; // allowlisted projection, no raw report; the report's facts, then ten app-rating facts
}
export interface SummaryClaim { text: string; factIds: readonly string[] }
// The v1 claim set. checkFacts and renderClaims still check and render it (the claim corpus, the assistant).
export interface StructuredSummary { version: 1; claims: readonly SummaryClaim[] }
// The v2 reply (X-2026-09-29-explanatory-summary): a takeaway, then exactly five areas in fixed order, 1-3 claims each.
export type SummaryArea = "soc" | "cells" | "capacity" | "twelveVolt" | "codes";
export interface AreaSummary { version: 2; takeaway: SummaryClaim; areas: readonly { area: SummaryArea; claims: readonly SummaryClaim[] }[] }
export interface LlmClient {
  generate(request: SummaryRequest, options: { model: string; effort: "none" | "low" }): Promise<unknown>;
}
export function prepareSummaryRequest(report: BatteryDiagnosisReport): SummaryRequest;
export function checkSummaryFacts(request: SummaryRequest, response: unknown): AreaSummary;
export function checkSummary(report: BatteryDiagnosisReport, response: unknown): AreaSummary;
export async function summarize(report: BatteryDiagnosisReport, client: LlmClient,
  options: { model: string; effort: "none" | "low" }): Promise<
    { kind: "llm"; text: string; summary: AreaSummary } |
    { kind: "template"; text: string; reason: string }
  >;
```

The projection contains only facts needed for the summary: measured signals with units, tier and availability; capacity/health status and reasons; 12 V status; codes/readiness roll-ups across modules; the per-module facts stay in the assistant's tools. It excludes garage ID, timestamp, recording path, ECU/header, VIN, free text/notes, raw bytes, and unreviewed fields. The prompt instructs the model to explain only supplied facts, retain `community` and missing-data labels, avoid health verdicts, and return the schema. Facts and schema are validated with zod at the boundary. The response is displayed only after `checkSummary` succeeds. A numeric phrase in a claim must match a cited fact's exact value **and unit** after defined formatting; a matching number with the wrong unit or unrelated citation fails. DTC identifiers are allowed only when cited exactly. Unrecognized number formats, uncited numbers, invented percentages/ranges, source IDs containing a digit, underscore or slash, empty claims, and future schema versions fail closed. The fallback catches provider errors as well as check failures and never copies provider error text into user-visible output. This deterministic check does not prove semantic truth; BM5 scores unsupported claims and omissions separately.

`checkSummaryFacts` is the same check against the transmitted projection for the T2.10c proxy. `checkSummary` first recomputes that projection from the local typed report, so a phone never trusts the server's version of the facts.

## Risks / open questions

- Numeric formatting is adversarial: fail closed on any form the checker cannot tie to a cited value and unit. The reviewer should inspect examples, not just counts.
- A matching value can still sit in a false sentence. The BM5 semantic eval and owner labels remain required before broad release.
- T2.4 has no qualifying committed real charge log; this stage must not imply measured capacity. The single-scan fixture is adequate for summary plumbing, not capacity validation.
