# T2.10c: Hosted DeepSeek proxy, cost guard, and live evaluation

Order: after T2.10a/b and after T2.9 releases root config files. This stage may be implemented before the phone UI, but a real model run needs the owner's API key and the approved US$5 evaluation ceiling. No production deployment follows automatically.

## Goal

A one-use server entitlement permits one bounded DeepSeek Flash structured summary request. The provider key stays on the Worker. The Worker validates the minimized request, reserves worst-case cost under a configured global cap, calls the provider once, checks the returned summary against cited facts, records non-sensitive usage/cost/latency, and returns either a verified summary or a template-fallback reason. A repeatable live eval runs a small fixed report set and writes per-item evidence without spending above US$5 for all T2.10 evaluation runs combined.

## Non-goals

- No subscriptions, purchases, assistant chat, model fine-tuning, raw recording upload, or app UI.
- No claim that the model is reliable merely because its JSON and numbers pass. BM5 later grades unsupported claims, omissions, and owner/judge agreement.
- No second provider or automatic model routing. DeepSeek is a candidate whose promotion depends on eval.

## Interfaces

```ts
POST /v1/summaries
Authorization: Bearer <installId>:<secret>
body: { requestId: string; request: SummaryRequest } // prepared by obd-assist; no raw report
response: { kind: "llm"; summary: StructuredSummary; usage: {
  model: string; promptVersion: string; inputTokens: number;
  cachedInputTokens: number; outputTokens: number; estimatedUsd: number; latencyMs: number;
}} | { kind: "fallback"; reason: string }
```

The server accepts only `SummaryRequest` v1 with bounded body size, fact count and field lengths, no unknown fields, and one configured model/effort. It strips all client-supplied model IDs/price claims. It consumes/reserves a credit with request ID before calling DeepSeek; retries with the same ID return the prior result if safely cached or a fixed fallback, never a second paid call. Provider timeout/errors, invalid JSON/schema, failed numeric/citation check, and cap exhaustion produce fallback and no raw provider text. The server stores only request ID, credit state, usage, cost and limited error category; summary/report content is not persisted in D1 or logs. A bounded reservation uses configured peak cache-miss input price and peak output price plus hard request/output token limits; the global daily and monthly USD caps are enforced atomically before any outbound call. The Worker fails closed when cap, key or pricing config is missing. Actual usage settles against the reservation; never refund a potentially billed call merely because the response is unusable. A secret rotation/kill switch path is documented.

Client-side T2.10a rechecks the returned output against the local typed report before display. The server check uses the supplied projection to prevent a compromised model response from bypassing the proxy; it does not authenticate the vehicle data. All real-report transmission is opt-in, with clear disclosure of DeepSeek and transfer to the People's Republic of China before the call; the server receives the minimized VIN-free projection only.

## Experiment and verification

Use the pinned `t2.10-v1` prompt, `deepseek-flash`, `reasoning.effort: none` first, fixed temperature/defaults as actually supported by the selected API, and one immutable fixture manifest: the committed first and second Equinox redacted spike recordings (separate sessions), the committed phone-console recording with no Mode 22 battery values, and labeled synthetic missing/incorrect-data cases only where recordings lack that branch. Derive typed reports through `batteryDiagnosisFromRecording`; do not send raw transcripts. Report source grouping by recording session; no training, augmentation or tuning on held-out items. Store prompt version, model ID/revision returned, date, code SHA, fixture paths/digests, response category, number-match result, unsupported-claim and missed-flag owner labels where available, input/cache/output tokens, latency and actual estimated cost per item in `/tmp/t2.10c-live-eval.json`; real and synthetic rows remain separate. Save only redacted/synthetic model responses for CI after owner review, and never put real private report text in the repo. A valid negative result (poor quality) is reportable; it blocks model promotion.

**Evaluation spend guard:** the owner approved **US$5 total across T2.10 live model evaluation** on 2026-09-26. Every live eval call goes through the same Worker and its durable D1 evaluation-budget ledger, with an immutable `EVAL_MAX_USD=5` cap, current peak cache-miss rate reservation and hard token ceilings. The eval CLI prints the ledger's cumulative reservation and actual spend and refuses a call when headroom is insufficient. A fresh local `/tmp` file cannot reset the budget; a new database or ledger reset requires a new owner spending decision. The parent records prior paid calls and authorizes any new ceiling. No production monthly budget was approved; that is a separate deployment prerequisite.

## Risks / open questions

- Largest risk is paid-call amplification from races/retries or cap arithmetic errors. Reserve worst-case cost atomically, use server-enforced token ceilings and inspect concurrent tests.
- API terms, model availability, response schema and price must be rechecked before live calls; model alias may move revisions. Cache hits reduce actual cost but never justify a lower cap reservation.
- The US$5 cap covers only evaluation. Owner must choose production daily/monthly cap, max uses per install, retention and public-launch anti-abuse posture. No promised ad profit or reliability claim follows from these tests.
- DeepSeek policy is provider-level disclosure; app/operator privacy obligations still need review before beta distribution. Explicit opt-in is a project requirement, not a legal-compliance proof.
