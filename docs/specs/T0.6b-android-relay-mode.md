# T0.6b: Android phone relay mode

## Redesign reconciliation (2026-09-28)

The 2026-09-26 revision was written against a single `apps/mobile/App.tsx`. The app redesign (commits `1f41022`..`37041bb`, spec `docs/specs/X-2026-09-28-app-redesign.md`) split it into a route stack (`App.tsx`), a runtime module (`src/app/runtime.ts`), theme/kit (`src/ui/`), and screens (`src/screens/`). This revision edits every stale location in place. What changed, and nothing else:

- **Where BLE lives.** `App.tsx` no longer touches BLE. The BleManager, the `BleConnection`, and every local BLE flow (debug Send, Run capture, Run codes report, Run battery check, Start charge log, Cancel check, Disconnect, scan/connect) live in `EquinoxConsole` in `apps/mobile/src/screens/ConsoleScreen.tsx`, mounted only on the `check` route. A charge log that outlives the screen is owned by the module-level `chargeRun` record in `src/app/runtime.ts` (`src/chargeRun.ts`, T2.4 Decision 20). Everything this spec previously assigned to "App" now belongs to `EquinoxConsole`. `App.tsx`, `runtime.ts` and `navigation.ts` are not modified.
- **Where the relay UI goes.** The redesign spec defers a relay-mode *screen* (its Non-goals), so there is no new route. The relay controls are a "Relay" section inside the check screen's collapsed **Developer tools** card, built from the existing kit (`SectionLabel`, `Button tonal`, `Text`, and the screen's `inputStyle`/`inputColors` text fields). They render only while a dongle is connected and no charge log runs, and only in development builds (`__DEV__`, the same gate as the T2.10d AI-summary route). The owner confirmed the gate on 2026-09-28 (Decisions).
- **Ownership gate.** Section "Console integration" below states the single synchronous gate, where it lives, and each start and teardown path in the current `ConsoleScreen.tsx`.
- **T2.10 D1 rewarded summary.** `summaryFlow.ts`, `summaryAccess.ts` and `DevelopmentSummary.tsx` use the network only and never touch BLE. They need no guard. The `aiSummary` route cannot be pushed while the check screen is on top, because the check screen has no route to it.
- **Interface fix.** `onTerminal` now fires on every end the client did not initiate, with a `bleUncertain` flag. Before, a clean remote close (for example `pnpm hil:smoke` closing the broker after its last reply) left the screen showing relay as the owner with no event to clear it.
- **Artifact.** It no longer contains response digests. It holds byte counts and escaped text, per the owner's no-hash rule (commit `8072e9a`).
- **T0.6 follow-ups.** None of the three open follow-ups in `docs/task-runs/T0.6.md` is in T0.6b scope. See Notes for a separate task.

## Goal

Add a foreground relay mode to the check screen's Developer tools. After the user connects to the Veepeak, they enter the WSL2 relay URL and per-process token, connect the platform WebSocket, and forward one server-authorized ELM command at a time over the existing `BleTransport`. The phone checks T0.6a's policy itself, waits for a complete `>` response, reports the exact bytes and elapsed time, and rejects malformed or concurrent requests. For each exact Mode 04 request, it shows an explicit native confirmation before any BLE write. The test-visible outcome is the recording-backed replay through `RelayClient` and its artifact `/tmp/t0.6b-relay-replay.json`. The hardware outcome is `pnpm hil:smoke` passing through the phone. T0.6a (closed) supplies the wire protocol and the broker. T0.6a and T0.6b together complete T0.6. The owner-arranged hardware gate is the final evidence.

## Non-goals

- No MCP SDK or MCP protocol inside the app. The phone speaks only T0.6a's authenticated WebSocket protocol.
- No new npm or native dependency, no EAS/app.json/plugin change, APK rebuild, background service, screen-lock prevention, reconnect loop, TLS, QR scanner, token persistence, or secure-store work. No new route or screen, and no change to `App.tsx`, `navigation.ts`, `runtime.ts`, theme or kit.
- No back-navigation lock for relay. Leaving the check screen ends the relay session through the unmount teardown (Console integration, T4).
- No local relay recording buffer or file export. The Node relay owns start/stop and the raw original. Run capture/codes and their automatic save are unchanged outside relay mode.
- No vehicle profile, signal display, DTC-clear button, generic arbitrary-command UI, or automatic Mode 04 approval. Confirmation is per request and cannot be remembered.
- No UDS writes (`2E`, `31`, `2F`), session changes, unknown services, unknown AT commands, or arbitrary binary traffic, even if a malformed or compromised relay requests them.
- No simultaneous debug Send, capture/codes, battery check, charge log, and relay. One BLE transport has one response reader at a time.
- No edits to recordings, `tools/relay/`, `packages/obd-core/`, planning/decision/task-run documents, or `docs/ELM327.md`. The T0.6 follow-ups are excluded too (Notes).

### Relay client

`apps/mobile/src/relay/RelayClient.ts` (no React Native import, so vitest runs it directly):

```ts
import type { Transport } from "obd-core/transport";

export interface RelayWebSocket {
  readonly readyState: number;
  send(data: string): void;
  close(code?: number, reason?: string): void;
  addEventListener(type: "open" | "message" | "error" | "close", listener: (event: unknown) => void): void;
  removeEventListener(type: "open" | "message" | "error" | "close", listener: (event: unknown) => void): void;
}

export interface RelayPhoneMeta {
  vehicle: "chevrolet-equinox-ev-2024";
  dongle: "veepeak-obdcheck-ble";
  writeChar: string;
  notifyChar: string;
  mtu: number;
}

export type ConfirmMode04 = () => Promise<boolean>;

export class RelayClient {
  constructor(
    socket: RelayWebSocket,
    transport: Transport,
    meta: RelayPhoneMeta,
    confirmMode04: ConfirmMode04,
    timeoutMs?: number,          // default 20_000, matching ConsoleSession
    nowMs?: () => number,        // monotonic clock for `ms`
    onTerminal?: (bleUncertain: boolean) => void,
  );
  close(): void;
}
```

Behavior:

1. On WebSocket open, send the exact T0.6a `hello` (`protocol: 1`, `vehicle`, `dongle`, `writeChar`, `notifyChar`, `mtu`; schema in `tools/relay/broker.ts` `helloSchema`). The token lives only in the URL built before construction. It is never logged, never shown in status or the transcript, and never persisted.
2. Validate each inbound message as a JSON `{ type: "command", id, command, confirmMode04 }` object, one outstanding at a time. Independently call `authorizeRelayCommand(command)` from `obd-core/transport/relay`. Reject without any BLE write: binary or non-string frames, invalid JSON or schema, traffic before open, a duplicate ID, a second request while one is pending (reply `busy`), or any policy mismatch (reply `invalid-command`).
3. A normal allowed command requires `confirmMode04 === false`. Exact `04` requires `confirmMode04 === true`, then awaits the injected confirmation. Denial sends `confirmation-denied` and writes nothing. Approval covers only that request and sends exactly one `04\r`. A true flag on any other command, or a false flag on `04`, is `invalid-command`.
4. Subscribe to the transport, create a fresh `ElmLineReader`, and send `{ type: "started", id }` immediately before `transport.write()` of the command plus one `\r`. Collect notification bytes unchanged and settle at the first `>`. Send a `result` with `ok: true`, `dataBase64` (standard base64 via `base64-js`, never `Buffer`/`btoa`/a UTF-8 decoder) of every byte through and including that prompt, and `ms`. A denied or invalid command never sends `started`. A write failure after `started` yields `transport-error` if the socket still allows a result. A timeout yields `timeout`.
5. Unsolicited RX, bytes after the first prompt, or a second response are never attached to a later request. They end the client with `bleUncertain = true`.
6. Settle once, unsubscribe, and reset the reader on every end path: timeout, write failure, socket send failure, socket close/error, BLE disconnect, or `close()`. Late callbacks cannot settle a later request. `close()` is idempotent, never calls `onTerminal`, and does not close the shared transport. `EquinoxConsole` owns BLE teardown.
7. `onTerminal(bleUncertain)` fires exactly once, after the client's listeners are removed, whenever the client ends by any cause other than `close()`. `bleUncertain` is true if a command or Mode 04 alert was unresolved, a timeout or possibly partial write happened, or RX arrived outside a pending request. In that case the ELM may be busy (`docs/ELM327.md` §Write safety), so the BLE link must be closed and not reused. `bleUncertain` is false for a close while idle.

A small adapter maps React Native's `WebSocket` to `RelayWebSocket`. Tests inject a fake.

### Console integration (`apps/mobile/src/screens/ConsoleScreen.tsx`)

**The gate.** Add one ref in `EquinoxConsole`, `bleOwner = useRef<"send" | "capture" | "relay" | undefined>()`, and one function `bleBusy()`. It returns true when any of these holds: `bleOwner.current !== undefined`, `chargeStarting.current`, `diagnosingRef.current`, or `chargeRun.current() !== undefined`. `chargeRun.current()` is the module-level record, so it stays correct after the activity recreates the screen and before React state renders. The ref records the owners that today exist only as React state (`pending`, `capturing`) or not at all (relay). The existing refs stay as they are. Every start handler begins with `if (bleBusy()) return;` and sets its owner synchronously before its first `await`. The same condition also goes into the existing `disabled` props. The props are presentation only; the gate is the check.

**Start paths.** Each needs the gate:

| Handler | Owner set | Owner cleared |
|---|---|---|
| `send` | `"send"` before `debug.send` | its `finally` |
| `capture` (Run capture, Run codes report) | `"capture"` before `startRecording` | its `finally`, after `finishRun` saved the file |
| `diagnose` | `diagnosingRef` (existing) | existing `finally` (after keep-scan, beta queue and `onSaved`) |
| `chargeLog` | `chargeStarting` (existing) through permission, picker and `chargeRun.begin`; after that, `chargeRun.current()` | `release` → `chargeRun.end` (existing) |
| `connectRelay` (new) | `"relay"` before the socket is created | relay end (below) |

`connectRelay` first closes any idle debug `ConsoleSession` (`closeDebugSession()`), and relay never resumes it. The next Send creates a fresh session, which starts in the unknown state and so must begin with ATZ/ATI (X-2026-09-24-first-write). Starting relay never cancels an active run. The charge log keeps its own link and manager until its normal stop and save.

**Relay end paths.** Each one removes the relay's BLE reader and closes its socket before ownership is released:

- **T1, Disconnect relay button.** `relay.close()`, then close the socket. If a command or alert was pending, treat it as uncertain and run `teardown(...)` (closes BLE). Otherwise keep BLE. In both cases clear `bleOwner`.
- **T2, `onTerminal(bleUncertain)`.** Clear the relay ref and `bleOwner`. If `bleUncertain`, run `teardown("Relay ended mid-command; reconnect the dongle.")`. Otherwise set a "Relay disconnected" status and keep BLE.
- **T3, BLE Disconnect button and `manager.onDeviceDisconnected`.** Both reach `teardown()`. `teardown` closes relay first (`relay.close()`, socket close, clear `bleOwner`) and then runs its existing steps. The Disconnect button's `disabled` expression must not block it while relay is active.
- **T4, unmount cleanup** (system or on-screen back, activity destruction). The `useEffect` cleanup closes relay and its socket first, then runs the existing cleanup. Relay and a charge log are exclusive, so the existing `unmountRun()` branch is unaffected.
- **T5, Mode 04 alert open during any of T1–T4.** Closing invalidates the pending confirmation. A later tap on the destructive button resolves into a closed client and can never write.

The diagnosis teardown branch (`teardown` returns early while `diagnosingRef` is set) cannot coincide with relay because of the gate.

**UI** (in the Developer tools card, `__DEV__` only, shown when `connection && !chargeLogging`). Under a `SectionLabel` "Relay":

- a blank URL field with the placeholder `ws://<WSL-host>:8765`, and a `secureTextEntry` token field;
- a tonal Connect relay / Disconnect relay button, disabled by `bleBusy()` for connect;
- one status line: disconnected, connecting, connected, busy `<command>`, or error.

Connect builds `/phone?token=…` with `URL`/`URLSearchParams`. The token field is cleared once the socket opens. Neither status nor the transcript ever shows the URL query or the token. Relay connect and end also set the hero status line, so the state stays visible with the card collapsed. The placeholder is UI guidance, not an OBD constant. The user enters the address that `pnpm relay`/`pnpm hil:smoke` prints.

**Mode 04 alert.** `confirmMode04` calls React Native `Alert.alert`, following the existing destructive-alert pattern in `App.tsx` `deleteBeta`. The message says clearing DTCs also clears freeze-frame data, and asks the user to confirm this one operation. The buttons are Cancel (`style: "cancel"`), which resolves false, and a destructive button, which resolves true. The options are `{ cancelable: true, onDismiss: () => resolve(false) }`, so back or a tap outside counts as denial. No timeout, earlier answer, MCP argument or server message counts as approval. The client stays busy while the alert is open.

### Isolated scenarios (synthetic, one per listed failure)

These are labeled synthetic fake-socket/fake-transport cases through the public `RelayClient`. Each covers exactly one failure below and is recorded in the artifact under `synthetic: true` with the failure name. None establishes Android or car behavior. Do not copy the core guard's command table into the tests. One unsafe command (for example a `2E…` request) and one confirmation-flag mismatch are enough.

1. A malformed, binary, duplicate-ID or pre-open command reaches BLE.
2. A second request overlapping a pending write or an open alert reaches BLE instead of getting `busy`.
3. A policy refusal or confirmation-flag mismatch writes or sends `started` (includes a true flag on `0100` and a false flag on `04`).
4. Mode 04 denial or dismissal writes or sends `started`, or does not return `confirmation-denied`. Approval writes other than exactly one `04\r` after `started`. A second `04` reuses the earlier approval. A late approval after `close()` writes.
5. `started` follows the write instead of preceding it.
6. Timeout, write failure, socket send failure, socket close/error, BLE-side close or `close()` leaves a pending result or listener, settles twice, or lets late data satisfy a later request.
7. Unsolicited RX or bytes after the prompt reach a later result instead of ending the client with `onTerminal(true)`.
8. Non-UTF-8 bytes (for example `0xFF`) change during base64 conversion, or a result is sent before the prompt.
9. `onTerminal` is not called exactly once with the right flag: true after a mid-command socket close, false after an idle remote close, never after `close()`.

11. An address with userinfo (`ws://user:pw@host:8765`) is accepted.
12. A non-numeric or out-of-range port (`:8765x`, `:0`, `:65536`) is accepted.

## Decisions

- Keep the Android half separate and ordered after T0.6a, so the wire, the server policy and the fake phone were stable before UI integration.
- Reuse `BleTransport` directly with a dedicated relay response reader. All local flows and relay are mutually exclusive through one synchronous gate in `EquinoxConsole`. They never share a response buffer.
- Apply the shared allowlist on both server and phone. The server stays authoritative for MCP. The phone refuses unsafe traffic from a malformed or compromised peer.
- Use a per-request native alert for Mode 04. Denial or dismissal is the normal physical acceptance path. No real DTC clear is required.
- Keep relay changes JavaScript-only and inside the check screen (2026-09-28 reconciliation), with no new route.
- Owner, 2026-09-28: the Relay section renders only in development builds (`__DEV__`). No release exposure and no `app.json` cleartext change.
- Owner, 2026-09-28 (review round 1): the two expo-doctor findings come from dependencies already in HEAD's `apps/mobile/package.json`, which this spec may not change; the verification item accepts them as baseline. Fixing them is a separate task.
- Reviewer-accepted, 2026-09-28 (review round 3): when the token field is non-empty, a query pasted into the address is ignored and never decoded; the typed token wins, and only the base address is kept in the field.
- Reviewer-accepted deviations, 2026-09-28 (review round 1): `RelayClient` takes an optional 8th constructor parameter `onActivity(command | undefined)` for the busy status and T1's pending check; the prompt is detected by byte `0x3E` (`>`, docs/ELM327.md §Framing), equivalent to `ElmLineReader`'s split; one transport subscription lives for the client's lifetime so unsolicited RX between commands is caught; malformed, binary, duplicate or pre-open frames end the client fail-closed with no BLE write; the URL is built with `URLSearchParams` after a host:port check; a timeout or write failure sends its result, then calls `onTerminal(true)`.
