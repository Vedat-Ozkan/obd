# T2.16 Stage A: bounded manufacturer-code capture

## Goal

Prepare one read-only, default-session UDS `ReadDTCInformation` request and an owner-operated **Developer tools → Record module codes** capture for the 2024 Equinox EV. The capture records the verbatim request and response from the five modules already known to answer targeted reads, preserves partial runs, and gives a replayable private JSONL artifact. Stage A is desk implementation; every vehicle result remains **NOT RUN** until Stage B.

## Non-goals

- No vehicle contact in Stage A, no UDS response decoder, DTC labels, report section, verdict change, scan integration, automatic rescan, or further-module search. Stage B obtains the car recording; Stage C decodes and reports from that evidence (PLAN T2.16; ADR-023).
- No diagnostic session change, Mode 04, UDS write, ECU reset, security access, or arbitrary `19` subfunction/mask. No free-form console expansion.
- No beta upload/intake integration. This Developer-tools recording is owner-private. T2.9 Stage D phone boundary and its scrubber have not been reviewed for a Mode 19 capture; never route the new raw capture to `queueForBeta` or make it a tester feature (ADR-019; `docs/specs/T2.9-beta-data-upload.md`).
- No new dependency, package, backend, Python runtime feature, or recording hand edit.

## Interfaces and design

Only normalized `1902FF` (display `19 02 FF`) is admitted by `allowedCommand()`. `19` is UDS ReadDTCInformation, `02` is reportDTCByStatusMask, and `FF` asks for all status bits. This is a project capture choice, **not** a claim that the Equinox implements it or that an empty reply means no codes. A later positive response is expected to start `59 02`, then a status-availability byte and zero or more 3-byte DTC plus 1-byte status records; Stage A stores bytes only. A negative response, `NO DATA`, truncation, `BUFFER FULL`, and timeout remain visible as capture outcomes, never decoded into “no codes.”

The new mobile entry point is `runModuleDtcCapture(transport: Transport, recording: RecordingBuffer, onProgress: (message: string) => void): Promise<{ jsonl: string; status: "complete" | "partial"; stopReason?: string }>` in `apps/mobile/src/moduleDtcCapture.ts`. It uses an `Elm327Session` over a recording transport so `allowedCommand`, prompt/stale behavior, reply framing, and header sequencing remain the core implementation. Initialize with the existing generic profile, then set 29-bit protocol and the existing module-target header/filter/flow-control pattern (the sequence in `scanMode22Profile`, `packages/obd-core/src/vehicles/scan.ts`). Target **17, 28, 40, 45, CB**, once each, in that order; send exactly `19 02 FF` once per selected module. A clean ELM `OK` is required for each setup command. Do not issue a second `19` after `NO DATA` or a negative response. Stop on setup error, malformed/partial response, timeout, transport failure, or disconnect; keep every observed byte and state why the run stopped. A `59 02 ...` frame may be marked *raw reply received* only; no Stage A record count or code interpretation. The run completes only after all five commands have prompt-terminated replies, including explicit `NO DATA` or UDS negative replies, with their per-module outcomes in the capture progress and final status.

The screen places one button under Developer tools, available only for the selected 2024 Equinox with an active dongle and no concurrent BLE owner. It asks the same non-empty vehicle-state note. Start a **dedicated** `RecordingBuffer` with the same metadata fields as the console capture, acquire BLE ownership, and pass a single recorded transport to `runModuleDtcCapture`. Do **not** call `startRecording()`: that creates a `ConsoleSession` subscriber and would duplicate RX recording beside the new `Elm327Session`. Freeze the dedicated buffer after the helper returns (or throws) and release ownership in `finally`. Show current module, request, and reply class/partial reason. Save through `finishRun("recording", ..., phoneTargets)` **without its upload callback**; the recording remains in private app storage if folder/share delivery fails. The status names the saved path or failure. No report is generated. The button cannot trigger from the normal battery-check or buyer flow.

Guard rule: the core guard special-cases exact normalized `1902FF`, not the service prefix. Keep `19` out of `READ_LENGTHS` so `19 02 00`, `19 0A`, masks other than `FF`, suffixes, response-count digits, control bytes, and odd/incomplete hex all refuse before write. Existing relay `authorizeRelayCommand()` and phone `RelayClient` use that guard; broker header state still gates 29-bit setup. The Python HIL bridge forwards relay commands rather than defining an independent UDS allowlist; the legacy spike/discovery Python allowlist is out of this phone path and remains unchanged.

**Dropped-character analysis to add under `docs/ELM327.md` §Write safety.** With CAF1 and a busy adapter, one leading character lost from `1902FF` leaves `902F` plus count digit `F`; two leave `02FF`; three leave `2F` plus `F`; four leave `FF`; five leave count digit `F`. These remnants are **not** established safe commands, and the exact request guard does not cure a busy adapter. The existing no-write-until-prompt, fresh-session `ATI`/`ATZ`, and stale/resync rules are the safety boundary; no dropped-character experiment is authorized on the car. The ELM datasheet also defines an odd trailing nibble as a response-count digit (§Write safety); document these byte strings without claiming ECU behavior.

## Risks / open questions

- The pinned primary source defines the service layout, but cannot establish Equinox support or a successful five-module capture. The largest Stage A risk is an apparently complete raw capture whose per-module outcomes are `NO DATA`/negative replies or truncated multi-frame messages; preserve those outcomes verbatim for Stage B decisions.
- A standard `19 02 FF` layout does not establish the Equinox's accepted subfunction, status mask, response length, status meaning, or DTC display format. Stage B must supply real bytes. If `BUFFER FULL`, multi-frame loss, or negative replies occur, preserve the raw evidence and stop; do not tune requests on the car in this stage.
- New Mode 19 payloads may contain identifiers outside T2.9's reviewed scrub patterns. The owner-private capture boundary is mandatory until a later beta scrub review and test explicitly cover these files.
- The five-module evidence is a Mode 09 response set, not proof that all five accept Mode 19. Stage B must report each module separately; `NO DATA` is coverage missing, not a clean DTC list.
