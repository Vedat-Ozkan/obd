# T0.6a: Node phone relay, MCP tools, and HIL smoke

## Goal

Create the Node relay in WSL2, the pure `obd-core` `RelayTransport`, and the `pnpm hil:smoke` entry point. The relay accepts one authenticated outbound phone WebSocket, exposes the four ADR-013 MCP tools over stdio, enforces a source-backed command allowlist before anything can reach the phone, serializes commands, records byte-exact exchanges in the standard JSONL format, and fails pending work promptly on disconnect. This is the first of two ordered T0.6 specs: its automated tests use a fake phone; T0.6b supplies the Android client required by the hardware check.

## Non-goals

- No Android relay UI or phone WebSocket client; T0.6b owns them.
- No vehicle signal definitions, scaling formulas, OBDb import, or profile expansion. `list_signals` exposes the current repository truth: the Equinox profile has no defined signals yet, so it returns an empty `signals` array with a `not-defined-until-T2.1` status. T2.1/T2.3 populate it later.
- No HTTP MCP transport, browser UI, cloud relay, TLS termination, account system, persistent daemon, reconnect loop, command batching, or multiple phones/vehicles.
- No change to `Elm327Session` policy. Its ordinary `send()` continues to block Mode 04. Only the MCP relay path can request Mode 04, and only the phone can approve that individual request.
- No UDS session changes or services other than the allowlisted reads. UDS `10`, writes `2E`, routine control `31`, input/output control `2F`, and all unknown services are rejected.
- No creation or editing of a hardware recording during implementation or fixture tests. The HIL section creates a new raw original only during an owner-arranged phone/car session.
- No edits to planning, decision, task-run, T0.8 baseline, Python redactor, or existing recording files.

## Interfaces

All new exports are named.

### Pure relay policy and transport

`packages/obd-core/src/transport/relay.ts`:

```ts
import type { Transport } from "./types.js";

export type RelayCommand =
  | { command: string; confirmation: "none" }
  | { command: "04"; confirmation: "on-phone" };

export function authorizeRelayCommand(input: string): RelayCommand;

export interface RelayCommandExchange {
  /** Settles when the phone is about to hand the bytes to BLE; rejects if it never will. */
  started: Promise<void>;
  /** Settles when the prompt-terminated response or a terminal relay error arrives. */
  result: Promise<{ bytes: Uint8Array; ms: number }>;
}

export interface RelayCommandChannel {
  request(command: RelayCommand): RelayCommandExchange;
  close(): Promise<void>;
}

export class RelayTransport implements Transport {
  constructor(channel: RelayCommandChannel);
  write(bytes: Uint8Array): Promise<void>;
  onData(callback: (bytes: Uint8Array) => void): () => void;
  onError(callback: (error: Error) => void): () => void;
  close(): Promise<void>;
}
```

`authorizeRelayCommand` trims outer spaces, uppercases, and collapses spaces in AT commands. Hex OBD requests remove spaces. It rejects non-printable ASCII, embedded CR/LF/tab, missing or multiple commands, odd-length/non-hex requests, and trailing `\r` from callers of this string API. It returns only:

- exact AT commands `ATZ`, `ATI`, `ATE0`, `ATL0`, `ATS0`, `ATH1`, `ATSP0`, `ATSP6`, `ATSP7`, `ATDPN`, `ATRV`, `ATCP 18`, `ATFCSD 300000`, and `ATFCSM 1`;
- header/filter commands matching `ATSH DAxxF1`, `ATCRA 18DAF1xx`, and `ATFCSH 18DAxxF1`, where `xx` is exactly two uppercase hex digits;
- hex services `01`, `02`, `03`, `06`, `07`, `09`, `0A`, and `22`, with any complete even-length hex payload;
- exact `04`, classified as `confirmation: "on-phone"`.

It rejects `2E`, `31`, and `2F` explicitly, then rejects every other command as unknown. No prefix such as `04FF` is accepted: the only clear request is exact Mode 04 `04`.

`RelayTransport.write` accepts exactly one printable-ASCII command ending in one `\r`, delegates authorization to `authorizeRelayCommand`, and calls the injected channel. It permits one exchange at a time; a concurrent write rejects as busy until `result` settles. `write` resolves on `started`, preserving the `Transport` contract that a write resolves when bytes are handed to the underlying layer. A successful `result` sends the returned bytes to every current data subscriber as one chunk; a result failure calls error subscribers and emits no data. `close()` is idempotent, rejects future writes, closes the channel, clears subscribers, and causes an outstanding exchange to fail through the channel's disconnect handling. It imports no Node, WebSocket, React Native, BLE, `fetch`, or MCP module.

Add package export `obd-core/transport/relay` for this file.

### Phone WebSocket wire protocol

The Node relay listens on `0.0.0.0`, port `8765` by default, with `OBD_RELAY_PORT` as an integer override. It creates a cryptographically random per-process token unless `OBD_RELAY_TOKEN` is set. The token and `ws://<host>:<port>` setup hint go to stderr because stdout is reserved for MCP stdio. Tokens and full WebSocket messages never enter recordings or task reports.

The phone connects to `/phone?token=<url-encoded-token>`. Reject a missing/wrong token before upgrade where the library permits, reject a second phone while one is active, disable per-message compression, cap messages at 1 MiB, and accept text JSON only. Zod validates every boundary object:

```ts
type PhoneHello = {
  type: "hello";
  protocol: 1;
  vehicle: "chevrolet-equinox-ev-2024";
  dongle: "veepeak-obdcheck-ble";
  writeChar: string;
  notifyChar: string;
  mtu: number;
};

type RelayRequest = {
  type: "command";
  id: string;
  command: string;
  confirmMode04: boolean;
};

type PhoneReply =
  | { type: "started"; id: string }
  | { type: "result"; id: string; ok: true; dataBase64: string; ms: number }
  | { type: "result"; id: string; ok: false; error: "confirmation-denied" | "busy" | "disconnected" | "invalid-command" | "transport-error" | "timeout" };
```

The hello must arrive before commands. The server sets `confirmMode04` true only for the `on-phone` policy result and false otherwise. Exactly one request may be outstanding across all MCP calls. The phone sends `started` immediately before its BLE write, after any Mode 04 approval; denial or validation failure sends only a failed `result`. A success result must follow exactly one `started`. Unknown IDs, duplicate/out-of-order replies, invalid base64, a response over 1 MiB decoded, negative/non-finite `ms`, protocol violations, socket error, or disconnect fail the outstanding request and close that phone connection. A phone disconnect also stops an active recording with a final meta note; subsequent MCP calls return a disconnected error until a new authenticated phone completes hello. No command is retried automatically.

### MCP tools

`tools/relay/broker.ts` owns the authenticated WebSocket broker, one-phone/one-command state, and exclusive recorder. `tools/relay/server.ts` wires that broker to the MCP tools and starts an MCP stdio server only when executed as the CLI. Both export construction functions used by tests. Use `McpServer` plus `StdioServerTransport` from the official TypeScript SDK. All successful tools return a short text content block and matching `structuredContent`; expected policy, state, phone-denial, and disconnect failures return `isError: true` without terminating MCP.

```ts
send_command({ cmd: string }): Promise<{ lines: string[]; ms: number }>;
start_recording({ path: string }): Promise<{ path: string }>;
stop_recording(): Promise<{ path: string; sha256: string; lines: number }>;
list_signals({ vehicle: string }): Promise<{
  vehicle: "chevrolet-equinox-ev-2024";
  status: "not-defined-until-T2.1";
  signals: [];
}>;
```

- `send_command` authorizes before sending. It waits for the phone's full raw response (including `>`), derives `lines` by splitting the pre-prompt data on CR/LF, trimming and dropping empty lines, and returns the phone's measured `ms`. It rejects a response without a final `>` and never records or returns partial success.
- `start_recording` requires an authenticated phone and no active recording. `path` must be exactly a repository-relative `fixtures/recordings/chevrolet-equinox-ev-2024/YYYY-MM-DD-<lowercase-slug>.jsonl`; reject absolute paths, `..`, alternate separators, `.redacted.jsonl`, discovery names, symlinks, and an existing target. Create the file exclusively and write a `t: 0` meta line using the hello metadata and `note: "phone relay; raw original; redact before commit"`.
- While recording, write each command as `tx` with exactly one trailing `\r` only when its `started` reply proves the phone is about to attempt the BLE write. On a successful response, write its decoded raw bytes as one `rx` entry. A denial before `started` records only a meta note, never a false tx. A write failure after `started` keeps the truthful attempted tx and appends a meta note without inventing rx bytes. Timestamps are monotonic seconds since start, nonnegative and rounded to three decimals. Await each append; `stop_recording` flushes/closes the immutable original, computes SHA-256, and then clears recording state. It never overwrites, resumes, edits, or produces a `.redacted.jsonl` file.
- `list_signals` rejects unknown vehicle strings. For the one supported ID it returns the empty result above. This keeps the promised MCP surface without inventing T2.1 signal constants or tiers.

### Commands

Root package scripts:

```json
{
  "relay": "tsx tools/relay/server.ts",
  "hil:smoke": "tsx tools/relay/hil-smoke.ts"
}
```

`pnpm relay` runs MCP on stdio and the phone WebSocket server in the same process. `pnpm hil:smoke` runs the same relay components without MCP, waits up to 60 seconds for one authenticated phone, chooses the first unused raw path `fixtures/recordings/chevrolet-equinox-ev-2024/<local-date>-relay-smoke[-N].jsonl`, starts recording, sends sourced `0100`, requires a prompt-terminated reply containing a whitespace-insensitive `4100`, stops recording, parses the written JSONL, replays `0100\r` through `ReplayTransport`/`ElmLineReader`, and exits 0 only when the replay contains the same response. It prints the raw path and the exact follow-up redaction command. It does not send init commands or Mode 04.

## Risks / open questions

- **Largest risk: two control planes share one fragile physical session.** MCP calls, recording state, WebSocket lifecycle, and the dongle's one-command rule can race. The broker has one global pending slot, every failure clears it exactly once, and disconnect tests are mandatory.
- The relay binds a LAN-reachable socket. A high-entropy per-process token prevents an unauthenticated peer on that network from driving the phone. Traffic remains plaintext on the local network; TLS and remote use are out of scope, so do not expose the port through public forwarding.
- `@modelcontextprotocol/sdk` 1.30.0 is the maintained compatibility line although the modular v2 SDK is now available. Choosing v1 minimizes client compatibility and file count for this local stdio server. A later migration is separate work; do not mix v2 packages into this task.
- `list_signals` is intentionally empty because no repository vehicle signal profile exists. Populating it before T2.1 would invent a second source of truth. The tool surface is testable now and its data grows with the profile task.
- A raw recording can contain a VIN. Gitignore protects the original, but the implementation and reviewer must still inspect `git status` and run the redactor before any recording is considered commit-ready.

No material design question remains open. The session token, local stdio MCP transport, empty current signal catalog, and raw-original/redacted-copy boundary are fixed here to avoid unsafe or invented behavior.

## Decisions

- Split T0.6 into ordered T0.6a (Node relay, policy, MCP, recording, core transport, HIL command) and T0.6b (Android relay mode). Each stays within one implementer session and ten implementation files.
- Use the official `@modelcontextprotocol/sdk` 1.30.0 compatibility line and stdio; use `ws` only on Node. React Native's built-in WebSocket remains dependency-free.
- Enforce one shared source-backed policy function in pure `obd-core`, called independently by the Node server and, in T0.6b, by the phone. The Node server remains the authoritative allowlist boundary required by ADR-013.
- Exact Mode 04 is a distinct policy result. It cannot carry an agent-provided confirmation flag; the server always asks the phone and only the on-phone UI can approve that one request.
- Save raw originals exclusively under the gitignored recording path, never auto-name them `.redacted`, and require the existing tested redactor for a commit-ready copy.

## Amendment 2026-09-24: shared write guard

Architect, 2026-09-24. This amendment is one implementer session on top of the reviewed-but-unapproved T0.6a code (Codex security repair included). Where it conflicts with the text above, the amendment wins. It supersedes these parts: the `authorizeRelayCommand` paragraph and its bullet list in Interfaces; the allowlist rows in Sources (lines for `ATZ`…`0100`, `ATSP7`…`ATFCSM 1`, read services); and in Commands, the sentence saying `hil:smoke` sends only `0100` with no init.

### Goal

The relay stops carrying its own allowlist. `authorizeRelayCommand` delegates to `packages/obd-core/src/elm/guard.ts`, so the relay and `Elm327Session` refuse the same commands. The broker is the single place where every phone-bound command is checked. It adds the two stateful rules the stateless check cannot enforce: the header/protocol sequence rule, and a stale rule for the unknown ELM state after a new phone connection or a failed write. What a test sees: `0100FF`, `ATCAF0`, `08 01`, `""` and `0600` are refused before the fake phone gets a request. Exact `04` still reaches the phone only with `confirmMode04: true`. On a new phone connection, `0100` is refused until an AT command gets a clean reply. `ATSH DA1DF1` is refused until `ATSP7` was answered `OK`.

### Non-goals

- No T0.6b work, no phone code, and no edits to `docs/specs/T0.6b-android-relay-mode.md`. What the phone must do is listed under "T0.6b obligations".
- No hardware session. No change to `guard.ts`, `session.ts` or `Elm327Session` behaviour, and no new guard export (everything needed is already exported). No new package `exports` entry: `relay.ts` imports `../elm/guard.js`. The broker keeps importing `obd-core` sources by relative path, as it does today.
- No fix for the round-3 follow-ups that belong to T0.7: sourcing the Mode 06 length, rewriting the "no spare payload" sentence, pinning `02 <pid> 00`, or the fresh `Elm327Session` starting not stale.
- No new phone wire message (for example a "late prompt seen" notice), no retry, and no automatic `ATZ` sent by the relay.
- No new dependencies.

### Design decisions

**1. `authorizeRelayCommand` is the guard plus two relay deltas.** It stays stateless and pure, with the signature unchanged:

```ts
// packages/obd-core/src/transport/relay.ts
import { allowedCommand, NON_PRINTABLE, normalize } from "../elm/guard.js";
export function authorizeRelayCommand(input: string): RelayCommand; // signature unchanged
```

Order: (a) reject if `NON_PRINTABLE.test(input)`. (b) `command = input.trim()`. (c) If `normalize(command) === "04"`, return `{ command: "04", confirmation: "on-phone" }`. The guard refuses `04` for `Elm327Session` on purpose; this exact-match branch is the only way it reaches the phone, and the phone still asks every time. `04FF`, `0400` and `044` fall through to (d) and are refused. (d) If `allowedCommand(command) === undefined`, throw `relay: refused, not on the read-only allowlist`. (e) If `normalize(command)` starts with `06`, throw `relay: refused, Mode 06 is not exposed` (decision 3). (f) Otherwise return `{ command, confirmation: "none" }`.

The command on the wire is the caller's text with outer spaces trimmed, as `Elm327Session` writes it. It is not the normalized form. Every tracked recording sends spaced forms such as `ATSH DA1DF1` and `22 2B43` (spike lines 129–162). No unspaced multi-token AT form has been recorded on the Veepeak. `authorizeRelayCommand(r.command)` returns `r` again, so the phone's independent re-check agrees. Delete the old `AT` set, `atPattern`, `printable` and the service list. `RelayTransport.write` stays unchanged.

**2. The broker has one choke point and tracks state.** Add a private `dispatch(text: string): RelayCommandExchange`. `request(command)` becomes `dispatch(command.command)`, and `send(text)` uses `dispatch(text)`. The caller's `confirmation` field is ignored and derived again, so a hand-built `{ command: "04", confirmation: "none" }` or `{ command: "ATCAF0", … }` cannot get past the check. `dispatch` checks in this order:

1. `authorizeRelayCommand(text)`.
2. Connected, then busy (existing errors).
3. The stale rule.
4. `beforeWrite(this.header, normalize(command))`. `undefined` means `relay: refused, header/protocol sequence`. Otherwise store the in-flight state before the request is sent, as `session.ts` `run()` does.

Every `relay: refused…` outcome writes one line through the broker's `logger`, with the command JSON-quoted and the reason (`docs/ARCHITECTURE.md` §tools/relay: "rejected and logged"). The logger must be stored as a field; today it is used only for the setup hint. Refusals return a rejected exchange and send nothing to the phone.

Two per-connection fields, both set when a valid `hello` is accepted:

- `header: HeaderState = UNKNOWN_STATE`.
- `idle = false`.

On a successful result (it already passes the prompt check and the canonical-base64 check), compute `kind = parseElmResponse(raw.slice(0, -1), command).status.kind` (`packages/obd-core/src/elm/reader.ts`). Then set `header = afterReply(header, normalize(command), kind)` and `idle = kind !== "error"`. A failed result or a disconnect never calls `afterReply`, so the restrictive in-flight state stays, as in the session.

*Header/protocol rule: track it rather than refuse `ATSH`/`ATSP`.* The broker already sees every prompt-terminated reply. With `beforeWrite`, `afterReply` and `parseElmResponse`, tracking costs about ten lines. All three are reviewed code, with reply-kind handling (`ATZ` answered `STOPPED`) closed in write-safety round 1. Refusing the class is not simpler. The Equinox needs `ATSP7` plus `ATSH`/`ATCRA`/`ATFCSH` for every Mode 22 read (§2024 Chevrolet Equinox EV), which is what the relay exists to serve (ADR-013, T2.3). Refusing only the header class would still leave `ATSP6` unsafe on a connection whose earlier session set a header, so `ATSP*` would have to go too.

A success result must hold exactly one response. Add to the existing base64/prompt check: the decoded bytes contain `>` (0x3E) only as the last byte, otherwise it is a protocol error. The T0.6b phone settles at the first `>`, so an interior `>` means two responses were merged, and `afterReply` would classify the wrong one.

**3. Stale rule, which also covers the fresh connection (write-safety round-3 finding 2).** A new phone connection starts with unknown ELM state, and the relay cannot see an unsolicited late `>`. Instead of waiting for one, the broker allows only a write that a busy ELM cannot turn into a service. While `idle` is false, only commands whose normalized form starts with `AT` are admitted. Anything else gets `relay: refused, ELM state unknown; send an AT command first`. `idle` becomes false:

- when a `hello` is accepted;
- when the phone's `started` reply arrives, because a write is being attempted.

It becomes true only on a successful result whose parsed kind is not `error`. A denial before `started` (Mode 04 `confirmation-denied`, `busy`, `invalid-command`) writes nothing and leaves `idle` unchanged. After a phone `timeout` or `transport-error`, a `STOPPED` or `?` reply, or a reconnect, the next write is therefore an AT command.

Why this is safe: a busy ELM discards the first character it receives (§Write safety, Input rules; DS p.9, p.48). For an AT command that character is `A`, and the rest, `T…`, is neither an AT command nor hex. Input the ELM does not understand is answered with `?` and not acted on (DS pp.8–9; write-safety spec Sources row). Any extra bytes that follow are the phone's problem to reject (T0.6b step 4 closes the relay on bytes after completion), and a close resets the state again. Refusing everything until reconnect was rejected: a reconnect proves nothing about the ELM, so the first-write question comes back unchanged.

**4. Mode 06: refused.** No code, recording or spec in the repository sends Mode 06 (`grep` 2026-09-24: only the guard table, the old relay list, the console constant and tests). Its request length `4` is unsourced (write-safety round-3 finding 1, owner-accepted for T0.7). Exposing it to agents would put an unsourced request on the car. T0.7 decides it for both paths; until then the relay and the session differ on `06` alone.

**5. `hil:smoke` starts from a reset.** Under decision 3, `0100` alone is refused on a new connection. `hil:smoke` sends the sequence the phone already captured on this car, dongle and phone: `ATZ`, `ATE0`, `ATL0`, `ATS0`, `ATH1`, `ATSP0`, `0100` (`fixtures/recordings/chevrolet-equinox-ev-2024/2026-09-24-phone-console.redacted.jsonl` lines 3–37; §Init sequence). It requires the `0100` reply to be prompt-terminated and to contain whitespace-insensitive `4100`, as today. It replays every tx in order through `ReplayTransport`/`ElmLineReader` and requires each replayed response to equal its live response. It still never sends Mode 04.
