# T0.10a: Fixture format and labeling README

## Goal

Create `fixtures/README.md` as the repository entry point for fixture authors and reviewers. It documents the recording JSONL contract that `obd-core` implements today, the current tracked fixture inventory and synthetic markers, the ADR-017 workflow for producing commit-safe redacted recordings, and the future companion-label shape defined by `docs/EVAL.md`. The README must clearly distinguish implemented recording validation from the planned `obd-eval` label schema so that readers cannot mistake a proposed field shape or placeholder number for existing validation or evidence.

This is the documentation-only T0.10a subtask authorized by the user. It does not satisfy the full T0.10 plan item: labeled healthy Equinox baseline fixtures, labeled synthetic cases, and the `pnpm test` replay/exercise gate remain outstanding for a later bounded spec.

## Non-goals

- Do not create or modify any recording, synthetic fixture, `.label.json` file, replay artifact, source file, test, plan entry, decision, or task record.
- Do not invent healthy/fault labels, capacity references, consent/provenance values, vehicle observations, or hardware results for the existing Equinox recordings.
- Do not implement the future `obd-eval` zod label schema or claim that labels are currently validated. No `packages/obd-eval` label implementation or tracked `.label.json` file exists at this baseline.
- Do not complete or weaken the full `docs/PLAN.md` T0.10 verification gate. In particular, documentation and existing spike recordings do not substitute for labeled healthy Equinox baseline sessions or labeled synthetic cases.
- Do not change ADR-017, the VIN-redaction script, ignore rules, recording format, parser behavior, or replay behavior.
- Do not add tests or dependencies for a documentation-only change.

## Interfaces

No runtime or public TypeScript interface changes.

`fixtures/README.md` is the documentation interface. It must contain these sections and boundaries:

1. **Directory and tracked inventory**
   - Explain `recordings/<car>/<date>-<slug>.redacted.jsonl`, the future sibling `.label.json` and Phase 2 `.log.jsonl` names, and `synthetic/<slug>.jsonl` with a future companion `.label.json`.
   - List the two tracked real recordings at this baseline:
     - `recordings/chevrolet-equinox-ev-2024/2026-09-22-spike.redacted.jsonl`
     - `recordings/chevrolet-equinox-ev-2024/2026-09-22-spike-2.redacted.jsonl`
   - List the three tracked synthetic recordings at this baseline:
     - `synthetic/elm-framing.jsonl`
     - `synthetic/session-branches.jsonl`
     - `synthetic/standard-decoding.jsonl`
   - State that none of those five tracked files has a companion `.label.json` at this baseline. The two spike recordings are protocol captures, not labeled healthy baseline fixtures.

2. **Implemented recording JSONL contract**
   - Attribute the authoritative implementation to `packages/obd-core/src/recording/format.ts` and the replay semantics to `packages/obd-core/src/transport/replay.ts`; link `docs/ARCHITECTURE.md` for the architectural format.
   - Document one JSON object per line and the implemented discriminated union:
     - every line has a non-negative numeric `t` in seconds and `dir` equal to `tx`, `rx`, or `meta`;
     - `tx` and `rx` require `data`, whose characters must all fit ISO-8859-1 byte values (`U+0000` through `U+00FF`);
     - `meta` requires only `t` and `dir` and retains free-form additional keys.
   - Separate parser enforcement from capture conventions. The parser does not enforce non-decreasing timestamps, a first meta line, command terminators, or a final ELM prompt. Captures conventionally put `\r` in transmitted commands and preserve received notification chunks; protocol completion at `>` is defined elsewhere.
   - State that `ReplayTransport` skips meta lines, requires each caller write to exactly match the next `tx.data`, and emits intervening `rx.data` values in recorded order while preserving their chunk boundaries. Do not claim it uses `t` for delays.
   - Use a short illustrative JSONL fragment only if every value is either copied from the architectural format or clearly labeled illustrative. Do not copy a VIN or imply that an example is a baseline label.

3. **Current metadata conventions**
   - Explain that metadata keys are descriptive and open-ended because the implemented meta schema is loose; do not present the current examples as universally required fields.
   - Use the tracked recordings to show the current real-capture examples: `car`, `dongle`, `note`, `script`, `bleak`, `platform`, `write_char`, `notify_char`, and `mtu` on their capture meta line.
   - Explain the ADR-017 trailing marker with its current keys: `redacted: "vin-serial"`, `source`, `source_sha256`, `script`, `script_version`, and `masked_messages`.
   - Use the tracked synthetic fixtures to document their current first-line convention: `synthetic: true`, `car: "none"`, `dongle: "none"`, and a `note` that states why the data is hand-written and where its sources live. Do not prescribe the existing note text verbatim for all future fixtures.

4. **ADR-017 redaction and immutability workflow**
   - State that raw originals stay local, gitignored, and untouched; recordings are never hand-edited.
   - Give the exact command `uv run tools/spike/redact_vin.py <recording.jsonl>` and state that it writes a sibling `<stem>.redacted.jsonl` without overwriting an existing output.
   - State that the generated copy masks VIN characters 12–17 in place with ASCII `0`, retains characters 1–11, preserves original line numbering, and appends the provenance meta line described above. Only script-produced `*.redacted.jsonl` copies are committed under `fixtures/recordings/`.
   - Link ADR-017 and the script rather than restating its frame-reassembly algorithm. Mention that the script refuses unsafe input or output and that a failure must be resolved without hand-editing either file.

5. **Future session label schema**
   - Label the section explicitly as **planned and not implemented at this baseline**. Its source is `docs/EVAL.md`; future zod ownership is `obd-eval`.
   - Document one companion label per labeled session with the planned fields and allowed values: `car`; `session` (`charge` or `snapshot`); `condition` (`healthy` or `fault`); optional `reference` with `method` (`integrated-energy` or `charger-kwh`), `capacity_kwh`, `soc_start`, and `soc_end`; optional `fault` with `id`, `detail`, and `injected_at_s`; `notes`; and boolean `synthetic`.
   - State the EVAL conditions precisely: `reference` is present only for charge sessions with enough SOC change to compute one; `fault` is only for injected synthetic faults; values shown in `docs/EVAL.md` are shape placeholders and are not measurements or labels for a current fixture.
   - Explain the two layers of synthetic identification without implying current companion labels exist: current hand-written JSONL fixtures carry `synthetic: true` in recording metadata and live under `fixtures/synthetic/`; when companion eval labels are added, those labels also carry `synthetic: true`. Real and synthetic results remain separate.

6. **Adding fixtures safely**
   - Provide a concise checklist: capture rather than hand-edit real sessions; retain the raw original locally; run ADR-017 redaction; commit only the generated redacted copy; put authored/injected data under `fixtures/synthetic/` with `synthetic: true`; add a companion label only from actual evidence and according to the future implemented schema; cite source/provenance; replay through the public entry point required by the task that introduces the fixture.
   - State that real vehicle claims require a recording path and that synthetic data cannot satisfy a real-data baseline or table.

- `fixtures/synthetic/session-branches.jsonl` has a pre-existing modification at this task baseline. Its exact current hash above is the preservation boundary; this task must not revert or edit it.
- No material open question blocks implementation. The user already selected the bounded documentation scope, and no schema or evidence decision is needed because implementation and label creation remain out of scope.

## Decisions

1. User-approved scope: T0.10a is one documentation file, `fixtures/README.md`, covering recording format, label schema, ADR-017 redaction rules, and synthetic labeling.
2. The implemented recording schema and the future EVAL label schema are documented as separate contracts with separate implementation status.
3. Full-plan T0.10 baseline-label fixtures and its replay/labeled-synthetic verification gate remain explicitly outstanding; this subtask cannot close or weaken them.
4. Existing recordings and synthetic fixtures are evidence inputs, not editable documentation examples. Their baseline bytes are preserved.
