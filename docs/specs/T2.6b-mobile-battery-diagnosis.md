# T2.6b: Fresh battery diagnosis scan and per-car report screen

## Goal

From a selected, verified 2024 Equinox EV garage entry, the user taps **Run battery diagnosis** once. The Android app starts a new read-only scan over the connected Veepeak, keeps its recording privately, builds the T2.6a typed diagnosis from that same scan, saves it under the selected `GarageVehicle.id`, and opens the in-app report. The garage shows that car's saved report history after app restart. Reports for two entries of the same model never mix. Capacity remains **NOT MEASURED** until T2.4 supplies a completed logged charge and a later reviewed integration. T0.9b must finish its active `App.tsx` implementation and review before this sub-spec edits that file.

## Non-goals

- No PDF, external Markdown/report file, share sheet, SAF folder choice, report export, backend, new native module, or “pre-purchase report” label. A private internal JSON document and scan recording are persistence/evidence, not an exported report.
- No unsourced PID, DID, signal scaling, health verdict, “good/bad” state, capacity estimate, new model-year support, or changing `verified` tiers. Only the already verified 2024 Equinox entry can run this battery path. Beta entries retain their unavailable message.
- No charge logger or T2.4 estimator; no T2.7 capacity integration or beta PDF export.
- No changes to T0.9b's one-and-done debug capture/codes report saving policy. Its public files still export as that separate debug flow specifies.
- No vehicle write, VIN request, Mode 04 clear, relay mode, or guard/ELM protocol change.

## Interfaces

`obd-core` adds a public `./vehicles/equinox-signalset` subpath to its existing checked-in JSON; T2.6a already exposes the existing session and vehicle APIs. The app imports `Elm327Session`, `genericProfile`, `equinoxEv2024Profile`, `scanMode22Profile`, and `importObdbMode22` through the public subpaths. It passes the imported signalset to T2.6a's pure `batteryDiagnosisFromRecording`, which owns decoding and tiers for both CLI and phone. The app's new pure orchestrator is:

```ts
export interface DiagnosisRun {
  jsonl: string; // recording captured during this run only
  scanStatus: "complete" | "partial";
  stopReason?: string;
}
export async function runBatteryDiagnosisScan(
  transport: Transport,
  recording: RecordingBuffer,
  onProgress: (message: string) => void,
): Promise<DiagnosisRun>;
```

The runner wraps the injected `Transport` to append each actual TX/RX to the existing `RecordingBuffer` before `Elm327Session` processes it; subscription and close order prevent bytes arriving after freeze. It calls `Elm327Session.init(genericProfile)` once, then sends the already sourced post-init T0.9 codes commands (including readiness, elapsed/distance counters, Mode 03/07/0A and frame-0 freeze data), then calls public `scanMode22Profile(session, equinoxEv2024Profile)`. It uses `Elm327Session` guard and its one-command queue; it does not add header commands to `ConsoleSession` or hard-code a second allowlist. On a no-prompt timeout, disconnect, or setup failure, it stops and marks the scan partial; it never blindly sends the next command. The report is built from the frozen recording via T2.6a, and missing fields remain unavailable. A car/model identification claim requires more than generic `0100`: battery data is shown only when the selected catalog entry is verified **and** the expected `CB/27C6` or `CB/2B43` response is decoded with the correct `18DAF1CB` source. If that fingerprint is absent, the app keeps the scan privately, shows a mismatch/no-response error, and does **not** save a battery report for the selected entry.

App orchestration uses the actual selected `GarageVehicle`, not the current hard-coded `consoleVehicle` alone. Close T0.9b's debug session before starting, disable Send/Run capture/Run codes report/Disconnect while the battery run owns the BLE transport except a deliberate cancellation that closes the session and saves the partial recording. Create a unique private `Paths.document/battery-scans/<garage-id>/<timestamp>[-N].jsonl` copy before saving the report. The report's `recording` field is this private label. `createBatteryReportHistory.save` is called only after recording keep succeeds; a failure leaves the recording and a visible error, never a falsely saved report. On success the report appears immediately and can be reopened from the selected garage card after app restart. Show the source/tier and limits from `renderBatteryDiagnosis` on the detail screen; render from the saved report, not ephemeral scan state. The history list shows timestamp/status and is scoped to that card's ID. Entries with reports cannot be removed silently: disable/remove action with a clear retention message until a reviewed delete/export policy exists. Ownership changes (`mine` ↔ `checked`) do not move or erase reports.

## Risks / open questions

- Largest risk: the exact combined codes + Mode 22 phone sequence has no committed redacted recording. Synthetic command replay can check software and the two real spike tails check the Mode 22 portion, but the full car run remains hardware-only. Do not claim a vehicle-verified fresh diagnosis before that run.
- A beta garage model/year can be added but has no validated battery scan path. Keep its action disabled; `0100` is not a model identity check. T2.8 first-connect mismatch acceptance remains open for other entries.
- Private scan recording and report history are two writes, not an atomic transaction. Keep the raw recording first and report only after both writes succeed; surface both outcomes. The Expo move API does not promise crash-safe replacement, so phone restart verification matters.
- The original PLAN T2.6 charge-log artifact remains unsatisfied. T2.7's later single-scan diagnosis and capacity attachment need a plan amendment that keeps their underlying verification, with PDF export moved to beta.

## Decisions

- Owner, 2026-09-24: use the name **battery diagnosis**, keep reports inside the app attached to the selected car, defer PDF export to beta, and start a **fresh scan** on tap. Parent recorded the answer.
- No report from a partial/mismatched scan is labeled complete or healthy. The report UI may show partial data with explicit missing fields only when the verified SOC fingerprint was obtained and the recording was saved.
- T0.9b owns `App.tsx` until its role/review stops; T2.6b app integration waits for the handoff.
