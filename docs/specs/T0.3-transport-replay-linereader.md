# T0.3: `Transport` interface, `ReplayTransport`, `ElmLineReader`

## Goal

Land the first source in `obd-core`: the `Transport` interface every real transport will implement, a zod schema and parser for the T0.2 recording format, a `ReplayTransport` that plays a parsed recording back through that interface and fails loudly when the caller sends a command the recording does not contain, and an `ElmLineReader` that turns the byte stream into complete `>`-terminated responses and classifies each one (echo stripped, lines split, `SEARCHING...` / `NO DATA` / `OK` / the error strings in `docs/ELM327.md` §Responses). When done, `pnpm -F obd-core test` runs one synthetic test per response class in `docs/ELM327.md`, replays a hand-written synthetic recording end to end, and runs a recording-backed test over every `fixtures/recordings/**/*.jsonl` that is visibly skipped with a `NOT RUN` reason while that directory is empty and becomes live, unchanged, when the T0.2 recordings land.

## Non-goals

- No `Elm327Session`: no init sequence, protocol selection, command queue, timeouts, retries, ISO-TP reassembly, ECU routing, or `Frame` type. Those are T0.4. `ElmLineReader` yields lines; it does not parse hex, headers, or PCI bytes.
- No `pnpm replay` CLI (T0.4's verify line) and no `HttpTransport` / `BleTransport` (T0.6 / T0.8).
- No decoding of anything (T0.5). `ELM327 v1.5`, `12.6V`, `A6`, and hex frame lines are all just "data" lines to this task.
- No package entry point (`main`/`exports`/`src/index.ts`) for `obd-core`. Nothing outside the package imports it yet; T0.4 adds the entry when `pnpm replay` needs it. Tests import by relative path.
- No delays: `ReplayTransport` ignores the `t` field. T0.4 tests timeouts with a recording that lacks a `>` for a command, not with wall-clock waits.
- No `remaining()` / "recording fully consumed" accessor on `ReplayTransport`. T0.4 adds one if its session tests need it.
- No handling of the "garbage after ATZ" quirk or of `LV RESET` recovery beyond classification; both are session behavior (T0.4).
- No edits to `docs/ELM327.md`, no new rows for response strings it lacks (see Open questions 1).
- No `.label.json` for the synthetic recording; it is a framing fixture, not an eval case (see Open questions 2).
- No lint rule enforcing `obd-core` purity; the reviewer checks imports by hand (see Risks).

## Interfaces

All exports are named. Relative imports use `.js` extensions (tsconfig is `NodeNext`). No `import` from `node:*`, `react-native`, or anything platform-specific under `packages/obd-core/src/`.

### `src/transport/types.ts` — verbatim from `docs/ARCHITECTURE.md` "Core interfaces"

```ts
export interface Transport {
  /** Send raw bytes. Resolves when the bytes are handed to the underlying layer. */
  write(bytes: Uint8Array): Promise<void>;
  /** Subscribe to incoming bytes. Chunk boundaries are meaningless. */
  onData(cb: (bytes: Uint8Array) => void): () => void;
  close(): Promise<void>;
}
```

### `src/recording/format.ts` — the package boundary for recording files

```ts
import { z } from "zod";

/** One line of a fixtures/recordings/*.jsonl file. `meta` keeps unknown keys (loose object). */
export const recordingLineSchema: z.ZodType<RecordingLine>;   // discriminated union on `dir`
export type RecordingLine =
  | { t: number; dir: "tx"; data: string }
  | { t: number; dir: "rx"; data: string }
  | { t: number; dir: "meta"; [key: string]: unknown };

/** Parses a whole .jsonl file. Throws Error("recording line <n>: <reason>") on the first bad line (n is 1-based). */
export function parseRecording(text: string): RecordingLine[];

/** ISO-8859-1: char code i <-> byte i. Hand-rolled: WHATWG TextDecoder("latin1") is windows-1252, which remaps 0x80–0x9F. */
export function latin1Encode(text: string): Uint8Array;   // throws if any char code > 0xFF
export function latin1Decode(bytes: Uint8Array): string;
```

Schema rules: `t` is a non-negative number; `data` on `tx`/`rx` is a string whose every char code is ≤ 0xFF (refine); `meta` requires only `t` and `dir` and passes other keys through (zod 4 `z.looseObject`, or `.passthrough()` if the resolved major is 3). `parseRecording` splits on `\n`, ignores one trailing empty segment, and applies `JSON.parse` then the schema per line. It does not check that `t` is non-decreasing (the T0.2 spike test does; not needed for replay).

### `src/transport/replay.ts`

```ts
export class ReplayMismatchError extends Error {
  readonly line: number;               // 1-based line in the recording, or the line after the last one when the recording is exhausted
  readonly expected: string | undefined; // next tx data, undefined when exhausted
  readonly actual: string;             // what was written, latin1-decoded
}

export class ReplayTransport implements Transport {
  constructor(lines: readonly RecordingLine[]);
  write(bytes: Uint8Array): Promise<void>;
  onData(cb: (bytes: Uint8Array) => void): () => void;
  close(): Promise<void>;
}
```

Behavior, exactly:

1. A cursor starts at line 0. `meta` lines are always skipped.
2. `write(bytes)`: decode with `latin1Decode`. Scan forward from the cursor: `rx` lines encountered before the next `tx` go into this write's batch (data that arrived before any command was sent; only possible at file start). If no `tx` remains, or the next `tx.data !== decoded`, reject with `ReplayMismatchError` (cursor unchanged). Otherwise continue past the matched `tx`, appending every `rx` line until the next `tx` or end of file; leave the cursor on that next `tx`.
3. The batch is delivered after `write()` resolves, asynchronously (never inside the synchronous part of `write`), one `onData` callback per `rx` line, in file order, each chunk encoded with `latin1Encode`. Chunk boundaries are the real BLE notification boundaries from the recording; that is the point of replaying them. A subscriber registered after `write()` resolves may miss chunks, exactly as with a real transport.
4. `onData` returns an unsubscribe function. `close()` marks the transport closed: later `write` calls reject, pending or later callbacks are not delivered.
5. Everything between two consecutive `tx` lines belongs to the earlier one. This includes a late `>` after a timeout meta line (T0.2 reviewer note); `ReplayTransport` does not try to re-attribute it. A `tx` with no `rx` before the next `tx` simply delivers nothing, which is how T0.4 will replay a timeout.

### `src/elm/errors.ts` — one trimmed line → its class

```ts
export type ElmErrorKind =
  | "unable-to-connect" | "can-error" | "bus-init-error" | "buffer-full"
  | "stopped" | "unknown-command" | "lv-reset" | "data-error" | "err-code";

export interface ElmError { kind: ElmErrorKind; line: string }   // line = the text as received, e.g. "ERR94"

export type ElmLineClass =
  | { kind: "searching" }
  | { kind: "nodata" }
  | { kind: "ok" }
  | { kind: "error"; error: ElmError };

/** Exact, case-sensitive match on an already trimmed line. undefined = a content line (data, version string, voltage, ...). */
export function classifyLine(line: string): ElmLineClass | undefined;
```

Match table (the strings are in Sources; nothing else is matched):

| Line | Class |
|---|---|
| `SEARCHING...` | searching |
| `NO DATA` | nodata |
| `OK` | ok |
| `UNABLE TO CONNECT` | error `unable-to-connect` |
| `CAN ERROR` | error `can-error` |
| starts with `BUS INIT:` and ends with `ERROR` | error `bus-init-error` |
| `BUFFER FULL` | error `buffer-full` |
| `STOPPED` | error `stopped` |
| `?` | error `unknown-command` |
| `LV RESET` | error `lv-reset` |
| `DATA ERROR` or `<DATA ERROR` | error `data-error` |
| `ERR` followed by exactly two digits (`ERR94`) | error `err-code` |
| anything else | undefined (content) |

### `src/elm/reader.ts` — bytes → complete responses → classified lines

```ts
/** Accumulates transport chunks; emits the text of each response once its '>' prompt has arrived. */
export class ElmLineReader {
  /** Returns the raw text (without the '>') of every response completed by this chunk: zero, one, or more. Text after the last '>' stays buffered. */
  push(chunk: Uint8Array): string[];
  /** Drops any buffered partial response. */
  reset(): void;
}

export interface ElmRawResponse {
  /** Verbatim text between the previous '>' and this one, '>' excluded. Never lost, whatever the classification. */
  raw: string;
  /** Content lines: split on '\r', trimmed, empty lines dropped, echo and status lines removed. */
  lines: string[];
  /** A SEARCHING... line was present (and removed from lines). */
  searching: boolean;
  status:
    | { kind: "data" }     // lines hold whatever the ELM printed; an empty response ('>' only) is data with lines: []
    | { kind: "ok" }       // the only line was OK
    | { kind: "nodata" }
    | { kind: "error"; error: ElmError };
}

/** Pure. `cmd` is the command that was sent (without '\r'); when given, one leading line equal to it is dropped as echo. */
export function parseElmResponse(raw: string, cmd?: string): ElmRawResponse;
```

`parseElmResponse` rules, in order:

1. `lines = raw.split("\r").map(trim).filter(nonEmpty)`. Trimming also removes the `\n` of `\r\n` endings (`ATL1`) and stray spaces.
2. If `cmd` is given and `lines[0] === cmd.trim()`, drop `lines[0]` (echo before `ATE0` takes effect).
3. Classify every remaining line. Remove all lines that classified (searching, nodata, ok, error) from `lines`; `searching = true` if any was `searching`.
4. `status`: the first `error` line if any → `{ kind: "error", error }`; else any `nodata` → `nodata`; else if the response had exactly one classified line `ok` and no content lines → `ok`; else `data`.
5. `raw` is the input, untouched.

`ElmLineReader.push` decodes with `latin1Decode`, appends, and splits off every complete segment ending in `>`. It has no knowledge of commands; the T0.4 session pairs each completed response with the command it sent and calls `parseElmResponse(raw, cmd)`.
