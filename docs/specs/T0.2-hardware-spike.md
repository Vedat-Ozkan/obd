# T0.2: Hardware spike (no product code)

## Goal

Produce a throwaway `bleak` script that the user runs on the laptop next to each car to send the fixed spike command list to the Veepeak dongle and write an immutable recording in the `ARCHITECTURE.md` recording format, plus a skeleton of `docs/spike-2026-09.md` that the user fills in after the car session. When the task is complete, three recordings exist under `fixtures/recordings/<car>/`, the spike doc has one outcome and timing per command per car, the write/notify characteristic assignment and the laptop bridge's LAN reachability from WSL2 are recorded, and the doc ends with a go/no-go line for Phase 2. In the implementer's session in this WSL2 shell (no Bluetooth, no car), only the script, its offline format check, and the doc skeleton can be produced and verified; every car-facing item is NOT RUN until the user runs the session.

## Non-goals

- No product code. Nothing under `packages/`, `apps/`, or `tools/hil-bridge/src` changes. T0.3 (`ReplayTransport`, `ElmLineReader`) and T0.6 (bridge `bleak` client, `/cmd`, `/record`) consume this task's output; they do not import the spike script.
- No decoding. The script records raw bytes and prints raw lines; it does not parse PIDs, VIN, or DTCs. Classifying each response (data / `NO DATA` / `?` / `UNABLE TO CONNECT` / timeout) is done by the user in the spike doc from the printed raw lines.
- No Mode 04, no Mode 22 beyond the four listed DIDs, no UDS, no multi-PID batching (`010C0D0405`), no `ATAT`/`ATST`/`ATCAF` experiments, no Mode 06. The `--interactive` tail exists so the user can try extra read-only commands by hand; anything typed there is recorded but is not part of the table.
- No changes to `tools/hil-bridge/pyproject.toml` or `uv.lock`; `bleak` is not added to the bridge here (T0.6 does that).
- No changes to `pnpm check`, CI, or `.gitignore`. The offline format check is run by hand and by the reviewer; it is not part of `pnpm check` because it needs an ephemeral `bleak`-free env outside the bridge.
- No hand-written recordings. A phone terminal app is a triage fallback only: its output goes into the spike doc as pasted text and does not satisfy the "three files under `fixtures/recordings/`" verify line.
- No editing of `docs/ELM327.md` in this task. Replacing its **(verify)** markers with recording line references is a follow-up after the user has filled the spike doc (suggest an `X-` spec, half a day).
- No "recently cleared" fixture on the Chrysler (T0.7 follow-up; it requires Mode 04, which this script never sends).

## Interfaces

### Script

`tools/spike/spike.py`, a single file with PEP 723 inline metadata so `uv` builds an ephemeral environment on either laptop OS:

```python
# /// script
# requires-python = ">=3.11"
# dependencies = ["bleak>=0.22"]
# ///
```

Command line (argparse; nothing else is public):

```text
uv run tools/spike/spike.py --scan
    Print every advertising BLE device as: address, name, advertised service UUIDs. Exit.

uv run tools/spike/spike.py --car <car> --address <ble-address> --out <path> --note "<free text>" [--timeout 20] [--interactive]
    Connect, discover FFF0 characteristics, send the fixed command list for <car>,
    write the recording to <path>, print one markdown row per command, disconnect.
```

- `--car` is one of `chrysler-200-2013`, `hyundai-elantra-2019`, `chevrolet-equinox-ev-2024` (these are the `fixtures/recordings/<car>/` directory names and the `car` value in the meta line; `chrysler-200-2013` matches `docs/EVAL.md`).
- `--out` must not already exist; the script refuses to overwrite (hard rule 2).
- `--note` is required and is stored verbatim in the meta line (vehicle state, ambient, anything the user wants T0.3+ to know).
- `--timeout` is the per-command wait for `>` in seconds, default 20. On timeout the script writes a `meta` line `{"note": "timeout waiting for '>' after <cmd>"}` and continues with the next command; it does not abort.
- `--interactive` after the fixed list reads commands from stdin (one per line, empty line or EOF ends) and sends/records each identically.

Internal structure (the implementer keeps to this; no more):

```python
class Recorder:
    """Appends one JSON object per line; flushes after each line."""
    def __init__(self, path: str) -> None: ...        # opens with encoding="utf-8", newline="\n"; sets t0 = time.monotonic()
    def event(self, dir: str, data: str) -> None: ...  # {"t": round(now - t0, 3), "dir": "tx" | "rx", "data": data}
    def meta(self, **fields: object) -> None: ...      # {"t": ..., "dir": "meta", **fields}

COMMANDS: list[str]        # the standard list, in order (see Sources)
EV_COMMANDS: list[str]     # appended when --car chevrolet-equinox-ev-2024

async def main() -> None: ...   # imports bleak inside, so the offline test does not need a BLE stack
```

BLE behavior (all cited under Sources):

1. Connect to `--address`. Find service `0000fff0-0000-1000-8000-00805f9b34fb`. Among its characteristics pick `write_char` = the one whose properties include `write-without-response` (preferred) or `write`; `notify_char` = the one whose properties include `notify`. If the service or either characteristic is missing, print every service and characteristic with its properties, write a meta line with that dump, and exit non-zero. Never assume `FFF1`/`FFF2` roles.
2. Write the first meta line: `car`, `dongle: "veepeak-obdcheck-ble"`, `note`, `script: "tools/spike/spike.py"`, `bleak` (from `importlib.metadata.version("bleak")`), `platform` (`platform.platform()`), `write_char`, `notify_char`, `mtu` (`client.mtu_size`).
3. For each command: clear the receive buffer; write `cmd + "\r"` as ISO-8859-1 bytes in 20-byte chunks (`response=False` if the characteristic supports write-without-response, else `response=True`); write one `tx` line whose `data` is the full string including `\r`; then wait until the concatenated notifications since the write contain `>` or the timeout fires. Every notification payload is written as its own `rx` line, decoded as ISO-8859-1, at the time it arrived.
4. Print one markdown row per command: `| <tx line number in file> | <cmd> | <ms from write completion to '>'> | <repr of all rx bytes for this command> |`. `repr` keeps the output ASCII-safe on a Windows console and shows `\r` explicitly. The user pastes these rows into the spike doc.
5. Disconnect. On any exception, let it propagate after the recorder has flushed; whatever was recorded stays on disk.

### Recording format contract (what T0.3's `ReplayTransport` may rely on)

`fixtures/recordings/<car>/<date>-spike.jsonl` (a second run the same day: `<date>-spike-2.jsonl`), UTF-8, `\n` line endings, one JSON object per line, in the order events happened:

```json
{"t": 0.000, "dir": "meta", "car": "chrysler-200-2013", "dongle": "veepeak-obdcheck-ble", "note": "...", "script": "tools/spike/spike.py", "bleak": "x.y.z", "platform": "...", "write_char": "0000fff2-...", "notify_char": "0000fff1-...", "mtu": 23}
{"t": 0.004, "dir": "tx", "data": "ATZ\r"}
{"t": 0.410, "dir": "rx", "data": "\r\rELM327 v1.5"}
{"t": 1.012, "dir": "rx", "data": "\r\r>"}
```

- `t`: seconds since the recorder opened, three decimals, non-decreasing.
- `dir`: `"tx"` (one line per command, `data` includes the trailing `\r`), `"rx"` (one line per BLE notification, chunk boundaries are real and meaningless), `"meta"` (free-form keys, always a `note` or the connect fields above).
- `data`: the byte sequence decoded as ISO-8859-1, so every byte value 0–255 round-trips and ASCII content is unchanged. `ReplayTransport` re-encodes with the same codec.

This matches the `ARCHITECTURE.md` example; the only additions are the extra meta keys and the statement of the codec.

### Spike doc skeleton

`docs/spike-2026-09.md`, written by the implementer with every result cell `NOT RUN`, filled by the user. Sections, in order:

1. **Session setup**: date, laptop OS, `bleak` version, dongle, which characteristic turned out to be write and which notify (from the meta line), MTU, vehicle state per car (from `--note`), recording paths.
2. **Bridge reachability from WSL2**: laptop LAN address, the exact command run on the laptop, the `curl` output from WSL2 (see Verification), PASS / FAIL / NOT RUN.
3. **Per-car tables**, one per car, one row per fixed command in list order, columns: `line` (tx line number in the recording), `command`, `ms`, `raw (repr)`, `outcome` (one of `data`, `NO DATA`, `?`, `UNABLE TO CONNECT`, `CAN ERROR`, `BUFFER FULL`, `timeout`, `other: <text>`), `notes` (for example "answered by 7E8 and 7E9", "SEARCHING... preceded data"). The EV table has the extra Mode 22 block.
4. **Extra commands tried** (from `--interactive`), free text with line references, optional.
5. **Findings for later tasks**: a short bullet list the user writes (dongle version string, `ATDPN` value per car, which ECUs answered `0100`, whether `0902` was multi-frame, anything that surprised).
6. **Phase 2 go/no-go**: one line, initially `NOT DECIDED`. The skeleton states the criteria so the user can decide honestly:
   - `GO`: EV recording shows `ATSP7` accepted and at least one of the four Mode 22 requests answered with a `62 <DID> ...` frame from the expected `18DAF1xx` header. Phase 2 proceeds as planned; T2.1 has its replay fixture.
   - `RE-SCOPE`: standard OBD works on the EV (at least `0902` answers) but all four Mode 22 requests return `NO DATA`, `?`, or time out. Phase 2 starts with T2.3 discovery instead of T2.1; the user decides whether that is worth the calendar.
   - `NO-GO`: the dongle cannot talk to the EV at all (`UNABLE TO CONNECT` on `0100` under `ATSP0` and nothing under `ATSP7`). Phase 2 is blocked pending a different dongle or approach.

## Risks / open questions

Risks:

- The largest risk is a format or BLE bug that is only discovered at the car, wasting the session. Mitigations: the offline format test, `--help` proving the environment resolves, flush-per-line so a crash keeps partial data, and `--interactive` so the user can recover a command without editing the script. If the script still fails at the car, the user should keep the partial recording under a `-partial` name and rerun into a new `--out`; never edit.
- `bleak` on Windows may deliver notifications coalesced or split differently than BlueZ; the recording captures whatever happened, which is exactly what T0.3 needs.
- The EV 29-bit block is entirely **(verify)** in `docs/ELM327.md`. Any `?` on `ATCP`, `ATFCSH`, `ATFCSD`, or `ATFCSM` (clone quirk) is a finding, not a failure; the user records it and, if `22 33E5` still answers, that is still `GO`.
- If `ATSP0` on the EV never finds a protocol, the standard list will time out per command (up to 20 s each). The user can lower `--timeout` for that car.
- The bridge default bind (`127.0.0.1`) contradicts `ARCHITECTURE.md`'s "listens on all interfaces"; this task works around it with a manual `--host 0.0.0.0` and leaves the default to T0.6. No decision needed here.
- The task record already notes `fixtures/recordings/` is empty and untracked; the three car directories only appear once the user copies the files in.
