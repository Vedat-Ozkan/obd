# T2.6c: Preserve ELM init retries in the battery scan

## Goal

Repair the rejected T2.6b fresh-scan path so an informational initialization reply is judged **after** `Elm327Session` has applied its documented retry policy. A first `CAN ERROR` or `DATA ERROR` at `ATI`, `ATDPN`, or `ATRV` may recover; an exhausted error or `LV RESET` stops before another command, retains a partial recording, and never reports a complete diagnosis. The new regression must reproduce the T2.6b final review's `ATDPN` failure before product code changes. T2.6b remains unapproved with **2/2 repairs exhausted**; this spec is a material successor to its init error policy, not a reset or an approval of that stage. T2.6d follows only after this stage is independently reviewed.

## Non-goals

- No `App.tsx` action, report screen, garage navigation, or hardware claim in this stage; T2.6d owns the app integration.
- No new command, PID, DID, scaling, retry count, retry interval, vehicle write, `ConsoleSession` allowlist change, or `scanMode22Profile` rewrite.
- No report export, PDF, share action, new native module, or dependency.
- No reopening or altering the independently approved T2.6a model/history behavior. Do not edit recordings. Only committed `*.redacted.jsonl` may be read.

## Interfaces

Add an **optional, backward-compatible** observation hook to the existing core init API:

```ts
// packages/obd-core/src/elm/session.ts
export interface InitOptions {
  /** Called synchronously after core's final reply, including any built-in retry,
   * and before the next init command, for ATI, ATDPN, and ATRV only.
   * Throwing aborts init. No raw, first-attempt callback is exposed. */
  onInformationalReply?: (command: "ATI" | "ATDPN" | "ATRV", response: ElmResponse) => void;
}
// Before: init(profile: VehicleProfile): Promise<InitResult>
init(profile: VehicleProfile, options?: InitOptions): Promise<InitResult>;
```

Keep `Elm327Session.run()` in sole control of retry and `runInit()` in sole control of required-step checks and fixed-protocol `0100` fallback. Invoke the hook only once per informational step, after its **final** `ElmResponse`, with `attempts === 2` when a retry occurred. If the hook throws, no next init command is sent. Existing callers without options see the same behavior. Do not notify on every RX chunk or close the session from a transport notification callback.

In `apps/mobile/src/batteryScan.ts`, remove the app-side `ElmLineReader`/`parseElmResponse` init observer and first-error close. Pass the hook to `session.init(genericProfile)`. For any final `response.kind === "error"` at those informational steps, throw a reason containing the classified ELM response and command. `NO DATA` and non-error informational replies retain core's existing behavior. The app's `StopOnElmErrorSession.send()` continues to evaluate the **final** response for post-init codes and Mode 22 reads; it must not suppress core's retry. The existing `try/finally` closes the session only after the final reply/throw, freezes one partial recording, and sends no following command. `LV RESET` is surfaced as a stopped scan requiring a new run, not an automatic continuation into Mode 22.

## Risks / open questions

- Largest risk: a callback at the wrong layer or before `run()` finishes can recreate the first-error-close bug. The hook must report only the final reply, after the built-in retry and before the next init write.
- The synthetic fixture proves control flow, while the two committed real recordings cover the Mode 22 tail. No committed recording contains a complete phone diagnosis scan; a full real-car claim requires T2.6d's owner session.
- This is a **new material revision** after T2.6b exhausted both allowed repairs. The parent must resolve whether the owner explicitly authorizes a new implementation/review cycle under the workflow cap before handing this spec to an implementer. Do not relabel this as T2.6b repair 3.
